# 多路取证书的判定逻辑：检查「主人」而不是「陌生人」

> 2026-11-25｜起因：加固 + 去校验组合包在"主人自己签名"的情况下闪退。
> 本文用一个比喻讲清**为什么**，代码注释里重复一遍同样的话（防文档丢失）。

---

## 一、问题现象

一个逆向者用我们的**去校验**模块绕过了 App 自带的签名校验，然后想保护自己的成果，
于是给这个包加上我们的**加固**模块（基准证书 = 逆向者自己的证书 `d82e48da`）。

真机日志：

```
【防线0·锁箱】解锁 rc=0: 解锁成功          ← 锁箱正常（证书就是主人自己的）
| open      size=60954012  fp=3c81b429      ← origin.apk（去校验的诱饵，原开发者证书）
| openat    size=60954012  fp=3c81b429
| openat64  size=60954012  fp=3c81b429
| syscall   size=70772547  fp=d82e48da      ← 真实 base.apk（内联 svc，hook 拦不住）
| svc       size=70772547  fp=d82e48da
| sysfd     size=70772547  fp=d82e48da
ok=6/6 mismatch=1
【失败】【防线1·sig_check】多路证书指纹不一致(疑似 APK 读取被劫持)
【防线2·sig_guard2】多路证书指纹不一致 → SIGKILL
```

**6 路全部成功、3:3 分裂、进程被杀**——而主人明明在场（`d82e48da` 就是基准）。

## 二、比喻

> 门卫的工作是**确认房间里有没有陌生人**。
> 只要看到一张不认识的脸，他就开枪。
>
> 但今天房间里坐着的人是**主人**（`d82e48da`），
> 另外三个是主人自己带进来的**化妆师/替身**（`origin.apk` 里的 `3c81b429`，
> 去校验模块故意放在那的诱饵）。
>
> 门卫不认识主人，只认识"陌生人"，于是把主人也一起打了。

**门卫该做的不是"清点陌生人"，而是"确认主人在不在场"。**
主人在场 → 放行（哪怕有再多替身）；
主人不在 → 才说明这房子被别人占了 → 开枪。

### 为什么"替身"是合法的

去校验模块的**工作原理**就是把 `open(base.apk)` 重定向到 `origin.apk`，
让 App 自己读到原开发者的证书。这是它的**设计功能**，不是入侵行为。

所以当加固与去校验同时存在时：

```
libc 路线（open/openat/openat64） → 被去校验重定向 → 读到替身（原开发者证书）
内联 svc 路线（syscall/svc/sysfd）→ hook 够不到     → 读到真身（当前安装包）
```

**内联 svc 路线读到的，才是"房间里真正坐着的人"。**

## 三、代码里的错误

`scripts/guard/src/sig_check.c` 的 `sig_collect_fp()`：

```c
/* 现在的逻辑（错） */
采集 6 路指纹
if (任意两路不一致) {           ← 只看"有陌生人"
    return -2;                  ← 直接杀，根本没机会问"主人是谁"
}
把多数派指纹返回 → 交给 sig_compare_fp 比对基准
```

`return -2` 发生在**比对基准之前**，所以：

- 它不知道基准是谁（`SIG_HASH_STORED` 里存的是主人的证书派生）
- 它只回答"这 6 路彼此一致吗"
- 不一致 → 一律判"被劫持" → 杀

**后果**：攻击者反而可以利用这一点——不需要伪造证书，
**只要让任意一路读错文件，就能触犯 fail-closed 让正常包崩溃**。

## 四、正确逻辑

```
① 把「内联 svc 路线」标记为【可信路线】
   （syscall / svc / sysfd —— 它们不经过 libc，inline hook 无从下手）
② 如果可信路线有成功的结果：
     用它读到的指纹去和基准（SIG_HASH_STORED）比对
       一致   → 放行（主人自己在场，其他人的替身不管）
       不一致 → 杀（主人真的被换掉了）
③ 只有可信路线全部失败（seccomp 拦、平台不支持）时，
   才退回旧逻辑："任意两路不一致就杀"（这一步是保底，宁可误杀不可漏防）
```

### 为什么这样仍然是安全的

| 攻击手段 | 结果 |
|---|---|
| 改 dex / 资源后重签 | ❌ svc 路线读到新证书 ≠ 基准 → 杀 |
| Hook 所有 libc 文件函数 | ❌ svc 路线不受影响 → 读到真证书 → 但那份 ≠ 基准 → 杀 |
| 连内联 svc 都被改（需逆向 `.ncx` 加密段） | ⚠️ 超出"通用"手段范围，属针对性逆向 |
| 拥有官方私钥签出合法包 | ⚠️ 密码学意义的攻破，任何方案都防不住 |
| **去校验模块（本项目的另一条线）** | ✅ **放行** —— 它读到的真身就是基准 |

最后一行是关键：**这本来就是设计意图**——去校验和加固由同一个使用者控制，
使用者是"主人"。加固要防的是**第三方**重签，不是防自己的另一个模块。

---

## 五、配套改动

- `sig_guard2.c`（第二独立线）同一逻辑，但它**零代码共享**，
  所以要在它自己的 `g2_collect_fp` 里独立实现一遍（形态相似、实现独立）。
- 日志要能看出来用了哪条判据：`【通过】可信路线与基准一致` /
  `【失败】可信路线与基准不一致`。

## 六、验收

| 场景 | 期望 |
|---|---|
| 加固包（无去校验） | ✅ 放行（原有行为不变） |
| 加固 + 去校验（主人自己签） | ✅ **放行**（本次修的目标） |
| 加固包 + 陌生证书重签 | ❌ 杀（原有行为不变） |
| 加固包 + 去校验 + 陌生证书 | ❌ 杀（svc 路线读到陌生证书） |

⚠️ 前两条是回归，后两条是防线。
