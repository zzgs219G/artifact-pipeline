## 二、`libnc_so_加密强度分析.md`（3.2 / 5.0）的评分明细

**这是唯一一份按维度打分的报告**，保留了它就能看出各层相对强弱：

| 维度 | 评分 | 依据 |
|---|---|---|
| 结构设计 | ★★★★☆ 4.0 | 6 个自定义段、双层加密、段插空布局、`SHF` 自定义标志位——架构完整，不是随手加的壳 |
| 算法选型 | ★★★☆☆ 3.0 | CRC32→SHA-256→PBKDF2→RC4 链条合理，但 **CRC32 当密钥材料（密码学强度≈0）、RC4 已不推荐** |
| 密钥保护 | ★★★★☆ 4.0 | **全篇唯一真正生效的防线** |
| 符号表 | ★☆☆☆☆ 1.0 | `nm -D` 一条命令拿到全部 JNI 入口名 + 精确大小 |
| 字符串保护 | ★☆☆☆☆ 1.0 | 旧实现是 8 字节全局固定 key 单字节重复 XOR，无消息域分离 |

**已修复项**（见 `docs/变更历史.md` 2026-10-21 / 10-22 条目）：
- 符号表 0.0 → 有实质改善（`--strip-all` + version script 白名单 `Java_*` + `--undefined-version`）
- 字符串保护 1.0 → `LSG_KEY = os.urandom(32)` 每构建随机 + `SHA256(key‖msg_id‖counter)` 每消息独立密钥流

### 该报告的独特结论（勿丢）

> **"壳能藏『函数体是什么』，藏不了『函数在哪、有多大』。"**
>
> 用 `grep -l "Lcom/xixin/tc/MainActivity;" *.dex` 直接扫二进制即命中 `classes4.dex`，
> 从而定位 native 入口。这是 so 自身的第一个致命缺陷。

> **"Java 层配合的存在，恰恰说明 so 自身缺少独立完整的校验闭环。"**

**RC4 选型的实测否决记录**（该报告 + 变更历史共同确认，重要）：
- 软件 AES 比软件 RC4 慢 **2.6×**
- 硬件 AES 快 11× 但 **v7a 无该指令**，强制全局开会生成 `aese` → v7a SIGILL 硬崩
- RC4 在本场景（一次性加密、高熵机器码明文、无密钥复用、每包仅 3 段）**不满足任何已知攻击前提**
- → **换算法收益≈0 而风险实存。此结论仍然有效，别再提案换 RC4。**

## 三、`逆向分析报告.md`（已删除）的独有结论

### 3.1 点名的 `.rodata` 明文串（已修）

报告 §6.3 明确点名这批串，称其"相当于把校验流程的伪代码印在了 `.rodata` 里"：

```
apk path from maps: %s
nc: fp=
der_len=
data/app scan exhausted
```

**已修**（2026-10-22，11/11 全清零）：`sig_guard2.c` 的 4 条路径串改走 LSGS
（新增 `G2_SUFFIX_APK`/`G2_DIR_LIB`/`G2_PATH_PROC`/`G2_PATH_ROOT`）；
`sig_check.c` 的 22 处裸 `LOGI/LOGE` 中 9 处紧邻下一行就是中文 LSG 版本（同一信息印两遍的纯重复泄漏），直接删英文。

### 3.2 报告 F-12：`debuggable=true` 会架空反调试

`debuggable=true` 的 release 包等于从系统层面架空 `ptrace(TRACEME)`/`PR_SET_DUMPABLE` 的前提
（`run-as` 可进私有目录、调试器可直接 attach）。

**已修**：新增 `patch-debuggable.py`（复用 `patch-extractnativelibs.py` 的 AXML 解析，原位等尺寸改写），
接进 `protect.sh` 对所有组合生效。
⚠️ 与 `extractNativeLibs` 语义相反：`debuggable` 属性**可能不存在**，不存在即默认 false，
若照搬"缺则报错"会让绝大多数正常 App 构建失败。

### 3.3 报告 F-13：dex2c 僵尸符号 `Java_amimo_dcc_DccApplication_init__`

实测是纯僵尸（`protect.sh` 传 `--no-build` → `dcc.py:997` 的 loader 注入分支不执行 →
APK 的 6 个 dex 里没有该类 → ART 永不 dlsym 它）。

**version script 的三种写法均失败**（`local: Java_amimo_dcc_*` 不优先于 `global: Java_*`；
收窄白名单到 `Java_com_nc_link_*` 会连带隐藏 dex2c 业务方法 → ULE）。
**最终用编译期改名** `-DJava_amimo_dcc_...=ncg_zombie_dcc_init`。

### 3.4 报告 v2 的两处误判（维护者实测反驳，重要）

| 报告说法 | 实测结论 |
|---|---|
| "`0x210a0` 是定制哈希、IV 非标准" | **错**。`0xdce0` 处就是**标准 SHA-256 IV**（小端存储） |
| "追溯 `sp+0x360` 的 16 字节密钥生成" | 那其实是 `k_so`，来自 `master`（用 `k_stub` 解 `.ncxhr`）+ 证书 + 包名。 **报告卡住是因为把 `.ncxhr` 的 `addr=0x4aa20` 当文件偏移读，而真实 `off=0x49a20`** |

### 3.5 报告否定的方案（勿再提案）

| 方案 | 否决理由 |
|---|---|
| MAC 校验改数据依赖 | **不可做**：RC4 流密码改 1 位只翻明文 1 位，`if (diff != 0) return -11` 专门拦单字节篡改，改掉就丢失该保护 |
| `.rela.dyn` 构造器地址加密 | **放弃**：`.init_array` 6 个构造器只有 4 个是本项目的，另 2 个是编译器运行时（`init_have_lse_atomics`/`__init_cpu_features`）不能动；且即使加密 addend，`.eh_frame` 仍暴露函数边界、`strings` 仍能找到特征串；改 `.rela.dyn` 属动态链接器契约，改错即 so 加载失败 |
| 静默降级 | **未做**：会误伤定制 ROM 用户，且需真机验证（`a7d9cbc` 已有前车之鉴） |
| 抄 XopProtector | **无可抄**：其 RC4/AES 均为纯软件实现无硬件加速；其 `obfuscate.h` 的 MBA 异或被 clang `InstCombine` 还原成异或，实测指令数 11→11 零收益；假分支方案体积 +109%；其真正强的 LLVM 层其文档自承 `stock NDK clang rejects -mllvm -fla` 需自编译工具链 |

## 四、`libnc_破解复盘文档最新.md`（已删除）的独有结论

**这是唯一一份完整的「攻击者视角全过程记录」**，最有价值的是它暴露的三个结构性弱点：

### 4.1 分层评分（攻击者自评）

| 防御层 | 攻击者评分 | 被攻破方式 |
|---|---|---|
| 代码段加密 `.ncx`/`.ncxh` | ★★★★☆ | — |
| 多层密钥派生 | ★★★★☆ | — |
| 环境检测 | ★★★★☆ | — |
| 看门狗线程 | ★★★☆☆ | — |
| 字符串混淆 | ★★★☆☆ | — |
| **非标准段名** | **★★☆☆☆** | 一眼识别出壳类型 |
| **`.ncks` 明文配置** | **★☆☆☆☆** | **直接读出全部布局** |
| `.ncxh` RC4 | ★★☆☆☆ | init 解密窗口被 dump |
| CRC32 密钥绑定 | ★★★★☆ | 尚未破解（卡住点） |

> **注：`.ncks` 明文这条已在 2026-10-28 的 T4 中修复**（槽段加密）。

### 4.2 三条给加固者的建议（其中两条仍有效）

1. **「解密与校验原子化，不要在 init 里一次性解密全部调度器，改为按需分页解密」**
   → 仍是待办（见交接文档 §五「分页解密」）

2. **「`.ncks` 配置表明文等于把地图交给攻击者，哪怕整体加密一次也好」**
   → **已修**（T4）

3. **「检测失败后别用 SIGILL（会暴露检测点位置），改为静默返回错误码」**
   → **未采纳**，理由：SIGILL 的 PC 地址虽然暴露偏移，但静默返回会让攻击者更容易继续跑；
   且本项目 2026-10-28 的实测表明 kill 链与解密流程耦合反而让"改 PLT 桩"失效，是有效防御

### 4.3 一个必须记住的实测事实

> **伪造 JNIEnv 直接调 JNI 函数时，`.ncx` 有 36506/38208 字节被改写（95.5%），
> 但内容仍不是合法代码（熵 7.99）**
>
> → 说明 JNI 函数被直接调用时**也会走解密路径**，但密钥不对。
> 建议：在 native 函数入口加 JNIEnv 合法性校验。

## 五、`简盒-so层静态防御实测报告.md`（2.5 / 10，第一版基线）

**这是所有报告里最详细的一份（3089 行）**，价值在于它是**第一版的完整攻破记录**——
70 分钟产出可运行绕过包。核心结论：

| 项 | 第一版实测 |
|---|---|
| `master` 位置 | `.rodata 0x13e80` 明文，`od` 一条命令读出（**10 秒**） |

## 六、`简盒-加固后复测报告.md`（6.5 / 5.5，第二版）

**第二版相对第一版的四项根本性修复**：

| 维度 | 第一版 | 第二版 | 判定 |
|---|---|---|---|
| `master` 位置 | `.rodata` 明文 | **不在明文，零命中** | ✅ 根本性修复 |
| 判定函数 | `0x238bc` 明文 | `0x504a0` **`.ncx` 密文** | ✅ |
| SHA256/HKDF 实现 | 明文 `.text` | **`.ncx` 密文** | ✅ |
| `.ncx` 可解密 | 是（10 分钟） | **否（死锁）** | ✅ |
| kill 链 | 独立，改 PLT 即废 | **内联 svc + 与解密耦合** | ✅ 双重加固 |
| JNI 符号 | 303 个暴露 | **303 个暴露** | ❌ 已回退 |
| `.rodata` 字符串 | 全明文 | **全明文** | ❌ |

### 该报告最重要的发现（维护者认可，务必保留）

> **"kill 链与解密流程耦合"——改 `abort@plt`/`_exit@plt`/`raise@plt`（第一版的有效手法）
> 会让 `.ncx` 无法解密 → SIGILL 起不来。这个结构第一版没有，是本版最有价值的加固。
> ⚠️ 建议保留，避免后人『优化』掉。**

### 该报告的两处误判（维护者实测反驳）

| 报告说法 | 实测结论 |
|---|---|
| "`.ncks+0x40` 的 32B HMAC tag 含运行时数据、静态不可定" | **错**。`HMAC(.ncks[0x30:0x40] ^ XOR_KEY, .ncxh 密文)` 逐字节匹配，纯静态可算。报告失败是因为字段名判错（把 `0x30` 处的值当作"要和 key16 异或的 mix"） |
| "`.ncx` 是分块惰性解密、应保留" | **前提错误**。实测单次 RC4 解出全部 39340 字节，1024/1024 指令合法。报告看到的"逐块循环"是按页 `mprotect` 权限切换，不是按块换密钥 |

### 该报告的"知识"（仍有效的通用经验）

> **统计引用次数前，必须先确认地址落在哪个符号范围内。**
> 报告两次统计错误（`svc #0x0` 正则写错、把 libc++ 的 379 个 `abort` 当 kill 链、
> `0x258b8` 落在 `heartbeat` 符号内）根因相同：**没确认符号归属就直接统计**。

## 八、当前强度定位（截至 2026-10-29）

```
第一版（2026-10-19）      静态破解 1.5/10  →  70 分钟产出可用绕过包
```

**第三方对第二轮的最终评价（维护者认可）**：

> 「升级版把定位成本从接近 0 提到约 40 分钟，方向正确。
> 但全部收益来自信息可得性改造，**不是密码学强度提升——强在"藏"，没强在"锁"**。
> 而"藏"可以被耐心磨掉，"锁"不能。」

所以只能从 TEE / JNIEnv 派生里找，且必须接受"离线不可用"或"换机失效"的代价。
