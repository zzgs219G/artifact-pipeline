## 1. 核心结论（一句话）

> **加密链可被完全静态解开，全程不执行 so。**
> 根因：`.ncks` / `.nck` 两个槽段是**明文**，且算法在**公开仓库**里。

【实测】解出的三段明文均已拿到，且 MAC 自检匹配（证明派生链复现正确，不是巧合）。

## 2. 完整解密链（11 步，全部静态）

| 步 | 动作 | 数据来源 | 是否需运行 so |
|---|---|---|---|
| 1 | 读 ELF 段表拿各段 offset/size | `readelf -S`（段表从不被 strip） | 否 |
| 2 | 读 `.ncks[8:24]` = `wrapped_k_stub` | **明文** `0x133fc+8` | 否 |
| 3 | 读 `.ncks[104:112]` = XOR_KEY 碎片 | **明文** | 否 |
| 4 | 按 `NC_XOR_FRAG` 查表拼回 XOR_KEY | 规则在 `nc_guard_boot.c:182` | 否 |
| 5 | `k_stub = wrapped_k_stub ^ XOR_KEY` | 纯异或 | 否 |
| 6 | `crc32(.text)` → 折叠 → `k_stub_eff` | `.text` 明文、无重定位 | 否 |
| 7 | XOR 解 `.ncxh`（16 字节周期） | — | 否 |
| 8 | XOR 解 `.ncxhr` → **master** | — | 否 |
| 9 | 从 APK 提 certDER → `SHA256` | APK 公开可读 | 否 |
| 10 | `k_so = HKDF(master, SHA256(certDER), "nc-so-v1"+pkg)` | 公式在 `nc_guard_key.c:418` | 否 |
| 11 | `RC4(k_so)` 解 `.ncx` / `.ncxr` | 标准 RC4 | 否 |

## 3. 签名校验的逆向结果【实测】

### 3.1 `.ncxr` 明文内容

```
偏移 0x00..0x30   SIG_SALT        = 1c59a5ddb01ce59ef4b891af0bdd79ac
偏移 0x10..0x30   SIG_HASH_STORED = be0e23499f5d36ecd74cbd2836d15b5a
                                     0077f7ffc1ec5bc838ff3f24c1d22c7b
偏移 0x30..0x60   与 [0x00..0x30) 完全相同（重复一份）
```

> **注**：48 字节内容重复了两遍。两份都能通过校验，功能上冗余，体积上多占 48 B。

### 3.2 通过凭据可直接算出【实测】

```
certDER 的 SHA256 (fp) = d82e48da...
t1 = SHA256(fp)        = a2c9ba4e57576720d37a004d550a86b4fc504e9829062a641c29a22182e9d1f5

验证：out[i] = t1[i] ^ SALT[i%16] ^ ((i*0x9E) & 0xFF)
      → be0e2349...2c7b  ✅ 与 SIG_HASH_STORED 逐字节一致
```

**证书是公开的**（APK 里就有），所以 `t1` 对任何人都是可算的。这不是漏洞——正常用户也这么算。真正的防线在 Java 层"测量真实安装包"。

### 3.3 判定核心 `nc_verify_t1` @ `0x4b7d8`【实测】

该函数在 `.ncx` 密文段内（`0x4265c + 0x917c`）。解出后反汇编（r2）：

```asm
0x4b7d8  sub  sp, sp, #0x40
0x4b7dc  stp  x29, x30, [sp, #0x30]
0x4b7e4  mrs  x9, tpidr_el0          ; 栈保护
0x4b7f4  cbz  x0, 0x4b87c            ; t1 == NULL → 返回 0
0x4b7f8  cmp  w1, #0x20              ; len != 32 → 返回 0
0x4b7fc  b.ne 0x4b87c
0x4b808  adr  x10, 0x134cc           ; ← .ncxr 段起始（SIG_SALT）
0x4b80c  mov  w11, #-0x62            ; ← 0xFFFFFF9E，即 (i*0x9E) 的补码乘法
0x4b814  ; 循环 i=0..31:
0x4b81c    and  x13, x8, #0xf        ; i & 15
0x4b820    ldrb w14, [x0, x8]        ; t1[i]
0x4b824    mul  w15, w8, w11         ; i * (-0x62) = (i*0x9E)&0xFF
0x4b828    ldrb w13, [x10, x13]      ; SALT[i&15]
0x4b82c    eor  w13, w14, w13        ; t1[i] ^ SALT[i&15]
0x4b830    eor  w13, w13, w15
0x4b834    strb w13, [x12, x8]       ; out[i]
0x4b840  ; 第二循环：恒定时间比对
0x4b850    adr  x12, 0x134dc         ; ← .ncxr + 0x10（SIG_HASH_STORED）
0x4b868    eor  w13, w14, w13
0x4b86c    orr  w8, w8, w13          ; mismatch |= ...
0x4b874  cmp  w8, #0
0x4b878  cset w8, eq                 ; 返回 (mismatch == 0)
```

`0x4b87c` 是两条 fail 分支的汇聚点（`mov w22, wzr` → `mov w0, w22` → `ret`）。

### 3.4 调用方【实测】

`ncVerify`（`0x20980`，明文 `.text`，152 B）只做转发：

```asm
0x20980  cbz  x2, 0x20a00            ; jbyteArray == NULL → false
0x20994  ldr  x8, [x0]               ; JNIEnv 函数表
0x209a4  ldr  x8, [x8, #0x558]       ; GetArrayLength
0x209ac  cmp  w0, #0x20              ; 长度必须 32
0x209b0  b.ne 0x20a00
0x209c4  ldr  x8, [x8, #0x5c0]       ; GetByteArrayElements
0x209d0  mov  w1, #0x20
0x209d8  bl   0x4b7d8                ; ← 唯一的 nc_verify_t1 调用点
```

全仓只有 `0x209d8` 一处 `bl 0x4b7d8`（手工扫 `.text` 全部 BL 指令确认）。

## 4. patch 攻击（在自建同构 so 上完整跑通）【实测】

### 4.1 攻击原理

`.ncx` 的保护是 **HMAC-SHA256(k_mac, 密文)**，`k_mac` 可由 master 派生。
而 **`k_mac` 不落盘**（`.nck[32:48]` 是诱饵），但派生它的 master 可以静态拿到（§2 步 8）。

于是攻击链：

```
1. 静态解 .ncx 明文
2. patch 目标函数
3. 用 k_so 重新 RC4 加密
4. 用 k_mac 重算 .nck[48:80]
5. 写回 → .text 未动 → CRC 自绑定不受影响 → 完成
```

### 4.2 关键：不要碰 `.text`

CRC 自绑定（`k_stub_eff = k_stub ^ fold(crc32(.text))`）只保护 `.ncxh`，**不保护 `.ncx`**。
所以改 `.ncx` 完全不触发它。**实测：改 `.text` 1 字节 → SIGILL；改 `.ncx` 1 字节 + 重算 MAC → 正常运行。**

### 4.3 实测结果（自建同构 so，无 env_check kill）

| 版本 | `selftest_rc` | 说明 |
|---|---|---|
| 原版 | **59** | 契约值（`ncguard_probe(0) == 59`） |
| patch 后 | **1** | 注入 `mov w0,#1 ; ret` |

补丁字节：`20008052 c0035fd6`（`mov w0,#1` / `ret`），MAC 重算后自检通过。

> **失败记录（供后人避坑）**：第一版 patch 直接 `mov w0,#1 ; ret` 覆盖函数开头，
> **跳过了 `sub sp,sp,#0x40` 的栈帧拆解** → `sp` 错位 → 崩溃。
> 正确做法是保留栈帧：在 `+0x01c` 放 `b +0x0b4`（跳到栈恢复段），把 `+0x0b8` 的
> `mov w0, w8` 改成 `mov w0, #1`。

### 4.4 未完成项（如实）

| 项 | 状态 |
|---|---|
| 在**真实 APK 的 so** 上跑通 patch | ❌ 未完成 |
| 原因 | 环境检测在 Termux 下 `TracerPid` 直接 `hit` → `delayed_kill` 抢在验证前杀掉进程 |
| 性质 | **实验手法受限，不是机制不成立**（patch 落地正确、MAC 验证通过） |

## 6. 已确认的设计缺陷

### 6.1 `have_mac` fail-open【实测·在我们自己的构建上】

`nc_guard_boot.c:453`：

```c
int have_mac = (got >= NC_SLOT_SIZE) && (slot.sh_size >= NC_SLOT_SIZE);
...
if (have_mac) { /* 验 HMAC */ }
```

`sh_size` 被改小 → `have_mac == 0` → **整个 HMAC 校验块跳过** → 直接解密。

四个变体实测（自建同构 so，`exec -a com.xixin.box` 保证包名匹配）：

| 变体 | 改动 | `selftest_rc` | `.ncx` |
|---|---|---|---|
| A | 原样 | **59** | 明文 |
| B | 只把 `.nck` 的 `sh_size` → 0 | **59** | 明文 |
| C | 只篡改 `.ncx` 第 10 字节 | **-11** ✅ | 密文 |
| D | 关 MAC + 篡改同一字节 | **137** | 明文（篡改生效） |

对照 A/C：**HMAC 本身有效**。对照 B/D：**长度一改就整块失效**。

`sh_size` 在 section header table 里，**不在 `crc32(.text)` 覆盖范围，也不在任何 MAC 里** → 改它零成本。

> **这是第三次同类问题**：报错五十二（`lock_head` 段缺失 `return 0`）、
> 报错五十四（`env_mem_readable` 取不到就当通过），都是"取不到数据就当通过"。

### 6.2 `.ncx` 与 `.ncxr` 共用 RC4 keystream【实测】

`so-section-lock.py:703` 每段都从 keystream 偏移 0 起：

```python
segs.append((nm, sc, pl, rc4(k_so, pl)))   # 每段独立调用 → 都从 0 开始
```

实测验证：

```
C_ncx[i] ^ C_ncxr[i] == P_ncx[i] ^ P_ncxr[i]   → True
```

后果：已知 `.ncxr` 明文（96 B 签名表，结构可猜）→ 反推 `.ncx` 前 96 B 明文。
实测交叉验证：**前 96 字节完全一致**。

### 6.3 `manifest_package()` 解析 UTF-8 AXML 错误【实测】

`so-section-lock.py:436-448` 的 UTF-8 分支只读了一段长度。AOSP 规范是**两段**
（UTF-16 长度 + UTF-8 字节长度）。

实测：字符串池被解析成 `'\x0bversionCod'`（应为 `versionCode`），最终
`未找到 <manifest package=...>` → **任何 `--from-apk` 调用都会失败**。

影响：CI 里"从 APK 自动补包名"那条路是死的（当前靠 `--package` 兜底才没暴露）。

## 7. 文档与实现不符（会误导后人）

### 7.1 "静态死锁"不成立

第二版外部复测（见 `外部实测报告结论汇总.md` §六）称：

```
要解 .ncx → 需要 k_so → 需要 master → 恢复代码在 .ncx 内 → 回到起点
```

**这条链是断的。** master 的恢复代码在 `nc_guard_boot.c:893-921` 的
**明文 stub**（`ncg_stub_recover`）里，不在 `.ncx` 内。

原报告作者卡在"CRC32 的输入是什么"，而答案写在 `so-section-lock.py:894-899`
（`.text` 全段、整体无重定位）。**这是分析失败，不是防御生效。**

### 7.2 `NC_STUB_SIZE` 文档漂移

`nc_guard_layout.h:83` 已是 `112`（新增 8 B 碎片区），但同文件 `:62` 标题、
`流程文档.md` 五处（`:887/964/1039/1092`）仍写 **104**。

> 这正是 `nc_guard_boot.c:86-89` 自己批判过的"权威的错图比没有图更坏"。
