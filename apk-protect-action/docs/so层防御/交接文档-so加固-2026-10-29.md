### 逐项说明

**T1：MAC fail-open（真 bug）**

`nc_guard_boot.c` 原代码：
```c
int have_mac = (got >= NC_SLOT_SIZE) && (slot.sh_size >= NC_SLOT_SIZE);
if (have_mac) { /* 验 HMAC */ }
```
把 `.nck` 段表里的 `sh_size` 改小 → `have_mac == 0` → **整个完整性校验被跳过**。
`sh_size` 不在 `crc32(.text)` 覆盖范围，也不在任何 MAC 里 → 改它零成本。

实测四变体（修复前）：
```
A 原样                → selftest 59（正常）
B 只改 sh_size→0      → selftest 59（放行！漏洞）
C 只篡改 .ncx 1 字节   → selftest -11（MAC 有效）
D 关 MAC + 篡改       → selftest 137（篡改生效）
```
修复后 B/D 均变 -11。

**T3：`.ncx` 与 `.ncxr` 共用 RC4 keystream**

`so-section-lock.py:703` 每段独立调 `rc4(k_so, pl)`，都从 keystream 偏移 0 起
→ two-time-pad 误用。实测 `C_ncx[i]^C_ncxr[i] == P_ncx[i]^P_ncxr[i]` 成立，
已知 `.ncxr` 明文（96 字节签名表）即可反推 `.ncx` 前 96 字节。

修复：新增 `so_r` 域（label `nc-so-r-v1`），第 0 段用 `k_so`，第 1 段用 `k_so_r`。

**T5：签名校验主干进 `.ncx`**

`.text` 里原有约 1458 条明文指令完整暴露签名校验流程。
标注 `find_apk_path` / `extract_cert_der` / `derive_expected` / `sig_verify`
（`sig_check.c`）+ `g2_*` 四个函数（`sig_guard2.c`）。

**T4：槽段加密（本轮核心）**

```
boot_key = HKDF-SHA256(
    ikm  = CRC32(.text[0:span])(4B 大端) || 区间首 16B || 区间末 16B,
    salt = NC_BOOT_SALT_INIT,
    info = "nc-boot-v1",
    len  = 16)

加密范围：
  .ncks[8:112)   ← [0:8) magic 豁免（判"未锁"在解密之前）
  .nck[0:96)     ← 其 magic 判定在 boot_key 算出之后
```

## 三、必须知道的 8 个坑（全是实测踩出来的）

### 1. `const volatile` + 初值 `{0}` → `memcpy` 被折成 `memset(0)`

```c
static const volatile unsigned char ncg_stub_slot[NC_STUB_SIZE] = {0};
// memcpy(dst, ncg_stub_slot, 8)  →  -Oz 生成 memset(dst, 0, 8)
// 但 ncg_magic_ok() 里用 volatile 指针逐字节读，读到的是真值
// → 同一块数据，两条路径读出不同结果，极难排查
```
**修法**：一律用 `const volatile unsigned char *src = ncg_stub_slot;` 逐字节拷。

### 2. `.text` 里的函数不能调 `.ncxh` 里的函数

`ncg_rc4` 标了 `NC_SEC_HEAD`（`.ncxh` 段）。stub 阶段 `.ncxh` 还是密文，
调用它 = 用没解开的代码解自己 = SIGILL。

这是本文件开头三条调用纪律之一。**新增 stub 阶段代码时务必检查被调函数在哪个段。**

### 3. `.nck` 在 `ncg_head_unlock` 里 pread 后必须解密

`pread` 拿到的是文件里的密文。且**未锁箱时 `.nck` 是明文**，不能无条件解。
必须先读 `.ncks[0:8)` 的 magic 判断是否已锁。

### 4. `_load_layout_contract()` 的正则必须支持十六进制

原正则 `(\d+)` 不认 `0x1000`，把 `NC_BOOT_BACK` 抽成 0 → `boot_key` 区间长度为 0，
锁箱静默出错。已改为 `(0x[0-9a-fA-F]+|\d+)` + `int(v, 0)`。

### 5. CRC 区间必须自适应，不能写死

原写死 `0x1000 + 0x3000 = 16384`，但 **armeabi-v7a 的 `.text` 只有 12000 字节**
→ CI 报 `boot_key CRC 区间 16384 > .text 段 12000`，锁箱失败。
arm64 的 `.text` 更大所以本地没暴露 —— **典型的"只验证了一个 ABI"**。

**修法**：`span = min(NC_BOOT_SPAN, .text 实际长度)`，两侧同规则。

> ⚠️ 这个错误模式在本轮出现了**两次**（另一次是 T5 漏了 `sig_guard2.c`）。
> **任何改动必须双 ABI 验证，且用 NDK 真实 target clang，不能只用本地 Termux clang。**

### 6. Android linker 强制要求 section header 完整

第三方建议"剥离 section header 1 行搞定"，**在 Android 上不可行**：

```
e_shentsize=0        → DLOPEN_FAIL: unsupported e_shentsize: 0x0
shoff=0, shnum=0     → DLOPEN_FAIL: invalid e_shstrndx
shnum=1, shstrndx=0  → DLOPEN_FAIL: invalid e_shstrndx
```
桌面 Linux 可以，Android bionic 不行。别再试。

### 7. `.ncks` 与 `.rodata`/`.gcc_except_table` 同页

`.ncks` 是 `SHF_ALLOC` 但非 `SHF_WRITE` → 运行期只读。
原地解密需 `mprotect`，实测它们**同属页 0x11000** → 会连带放开邻段权限
（与报错五十同类风险）。

**当前用"解密到调用方栈缓冲"规避**，不碰内存权限。

### 8. 加密和隐藏是矛盾的（数学限制）

密文熵必然≈8，所以**"定位加密段"无法防**：

```
熵 7.996  0x99ac  ← .ncx
熵 7.504  0x0c1c  ← .ncxh
熵 6.517  0x23b1c  ← .text
```
`max(sections, key=entropy)` 一条命令命中。

**我实测过"低熵填充"方案，失败**：每 16 字节密文插 16 字节填充后整体熵降到 6.09，
但攻击者只取奇数块，熵立刻恢复 —— 填充要骗过统计就必须和密文不可区分，
但它又必须能被程序认出才能跳过，**两个要求互斥**。

## 四、已验证有效的 / 明确无效的

### 有效（实测）

| 项 | 效果 |
|---|---|
| CRC 自绑定 | 改 `.text` 1 字节 → SIGILL |
| HMAC 完整性 | 改 `.ncx` 1 字节 → -11 |
| 环境检测 | Termux 下 TracerPid 直接 `hit`，进程被杀 |
| kill 链内联 svc | 无 PLT 软目标 |
| **T4 槽加密** | 逆向脚本 MAC 自检失败 |
| 空 `init_array`（T5 副作用） | 逆向方称"必须动态跑才知道入口" |
| 去明文 xref | 逆向方称"全 `.text` 扫描 0 命中，本次最大障碍" |

### 明确无效（我实测否决，别再做）

| 方案 | 实测结果 |
|---|---|
| 剥离 section header | Android linker 拒载 |
| 段名清空 | 熵值扫描绕过，收益 0 |
| flags 归一化 | 同上 |
| 消除 ADR xref | 攻击者不需要 xref（熵值就够） |
| SHA 常数混淆 | rotate 立即数（2,13,22/6,11,25/7,18,3/17,19,10）本身就是指纹 |
| 低熵填充 | 取奇数块即破解 |
