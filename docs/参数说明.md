## 0. 两层防护的命名（先看这个，不会再混）

| 你看到的词 | 是什么 | 谁控制 | 体积 |
|---|---|---|---|
| **锁箱** | `.ncx` 六段加密：磁盘上是密文，运行期自己解锁。**一直在，不用开** | nox 设施（tools/nox.zip），构建自动 | ~几 KB 槽段 |
| **nox-obf / nox-VMP** | **nox 解密链本身**被 VMP 化 + 混淆（烧进 libnox.a，发版时决定） | nox 发版 tag 的 `-obf` 后缀（CI 自动）；本地直打须设 AMICE_BUNDLE | .a 508KB（VMP 占 95KB 字节码+142KB 解释器） |
| **--vmp（消费方层）** | **签名校验判定逻辑**被虚拟化（sig_check/guard2 的判定点） | `--vmp` 参数（默认不开） | so +200KB~470KB |

**一句话**：锁箱+nox 层 VMP 你天然就有；`--vmp` 加的是"签名校验判定逻辑"的虚拟化。
88.66K 事故（2026-11-24）就是"以为有 nox-VMP 实际发版时丢了"——现在 T34 断言+登记表会拦。

## 3. 产物体积（为什么加固后会变大，以及怎么压回来）

加固 + 去校验组合包的体积有明确的物理下限，不是流水线忘了优化：

| 场景 | 体积 | 为什么 |
|---|---|---|
| 只去校验 | ~62MB | `zip-reuse.py` 让 `origin.apk` 与包体共享字节 |
| 只加固 | ~64MB | 没有 `origin.apk`，本来就不翻倍 |
| **加固 + 去校验** | **~69MB** | `origin.apk`（去校验包，60.95MB）与产物本体（加固包，63.78MB）**内容不同**，必须各存一份。两者相同的 1438 个条目共享字节，其余 20 条（7 个 dex / 2 个 so / Manifest / arsc）另存 |

**为什么不是 119MB**：`apktool b` 用 `java.util.zip` 重写 ZIP，它没有「条目数据指向文件某偏移」这种能力，
所以会把共享布局展开成实体副本。`scripts/repack/partial-reuse.py` 在 zipalign 之后手写 ZIP 补回共享。

> ⚠️ **产物的签名必须用 MT 管理器，不能用 apksigner** —— apksigner 同样重写 ZIP，会把共享布局
> 再展开回 119MB。zipalign 也一样，所以复用必须在 zipalign 之后跑（流水线已保证）。

> ⚠️ **不要用 `zipfile.testzip()` 验收复用包** —— 数据复用本身就是条目重叠，Python 的 zip-bomb
> 防护会报 `origin.apk`，那是预期行为。用 `partial-reuse.py` 自带的 `verify()`。

## 3.1 运行期性能（字符串加密 + so 四项全开）

冷启动首个网络请求：**0.7~0.9 秒**，与原包（不加密）的 ~1 秒持平。
曾出现过 8.5 秒卡顿，根因是缓存哈希函数 `nc_fnv1a` 漏出 `+no_obf` 免混淆白名单
（被混淆 pass 处理后，11.5 万次调用累计 8 秒）。**该问题已修，2026-11-26 真机 5 次复测稳定（0.5~0.7 秒）。**

> ⚠️ 若将来再加 C 侧热路径小函数，**必须同时加进 `scripts/pipelines/protect.sh` 的
> 免混淆白名单**——白名单要按「调用链」列，不能只列入口函数。回归由
> `scripts/string-enc/tests/test-cstrdec.sh` 的白名单成员断言拦。
> 细节见 `scripts/string-enc/README.md`「性能：真机实测」节。
