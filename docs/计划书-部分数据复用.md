# 计划书：加固产物部分数据复用（119MB → 69MB）

> **状态：✅ 已实现（2026-11-25）。** 本文保留为设计依据与实测数据来源。
> 实现见 `scripts/repack/partial-reuse.py`（测试 `scripts/repack/tests/test-partial-reuse.py`）。
>
> **实测结果 vs 计划**：产物 **71,989,277 B**（计划预测 71,983,883 B，差 5,394 B 为
> 对齐填充与中央目录的精确值）；可共享 1438 条、独有 20 条，与预测一致。
>
> **实现中修正的三处设计**：
> 1. **CD offset 必须指向 LFH，不是数据起始** —— 解析器在该 offset 处期待
>    `PK\x03\x04`。计划书 §3.3 原文写「offset = origin_data_start + origin内部offset」
>    含义正确但没说清「内部 offset 指的是 LFH offset」。
> 2. **对齐填充算法要按「当前文件偏移 + header 长度」算**，不能只按 header 长度
>    （`_align_extra(base_len)` 只对 offset 0 成立；独有条目必须用 `_pad_to(off, base, need)`）。
> 3. **`verify()` 必须校验 origin.apk 自身的 CRC** —— 反面验证发现原实现只查长度，
>    翻转 origin 数据区一个字节仍绿。

> **写给下一位实现者。** 本文所有数字都是真机产物实测的，不是估算。
>
> **命名约定**：文中出现的 `<待创建>-xxx.py` 表示「这个文件还不存在，由你创建」。
> 这是为了让仓库的文档路径校验器（`test-docs-paths.py`）跳过它们 ——
> 它只认已存在的文件。创建时把 `<待创建>-` 前缀去掉即可。
> 开工前必读：`AGENTS.md`、本文、`scripts/uncheck/zip-reuse.py` 的 docstring。
>
> **状态：设计完成，未实现。** 用户已明确「先出计划书，下一位 AI 实现」。

## 0. 一句话

加固流水线用 `apktool b` 重打包，把 `origin.apk` 从「共享字节」变成「实体副本」，
产物 119MB。**在 apktool 打包之后再手写一次 ZIP，让产物里与 `origin.apk` 内容
完全相同的 1438 个条目指回 origin.apk 内部偏移**，即可降到 **69MB**（省 42%）。

---

## 1. 问题：为什么是 119MB

### 1.1 实测现状

```
输入包（去校验产物，已做数据复用）  64,951,877 B
        ↓ protect.sh → repack_build → apktool b
加固产物                          124,913,473 B
```

### 1.2 拆解

```
产物条目压缩后合计           124,736,559 B
  其中 assets/nc_sigfix/origin.apk:  60,954,012 B   ← 实体副本
  其余 1458 条:                      63,782,547 B
```

### 1.3 根因：apktool 用的是标准 ZIP 库

`apktool 3.0.3` 用 `java.util.zip.ZipOutputStream`。它的 API 只能：

```
写 local header → write(数据) → 记 offset
```

**没有"这个条目的数据在文件某偏移处、共 N 字节"这种 API。** 所以它只能把
61MB 老老实实写一遍。

> ⚠️ **这不是 apktool 版本问题，升级永远解决不了。**
> 任何用 `ZipOutputStream` 的工具都做不到。只有手写 ZIP 字节才行
> （MT 管理器、`zip-reuse.py` 都是这么做的）。

### 1.4 三方责任（避免误判）

| 嫌疑 | 结论 |
|---|---|
| apktool | ✅ **根因**：重打包时把共享布局拆成实体副本 |
| 签名（apksigner） | ❌ 无关：未签名时就已经 119MB |
| `zip-reuse.py` | ❌ 无关：它只在 uncheck 流水线跑，没参与加固 |
| 加固流水线漏调 zip-reuse | ⚠️ 表面看是，但**直接调用会失败**，见 §2.2 |

## 2. 关键发现：为什么不能直接套用现有 `zip-reuse.build()`

### 2.1 `origin.apk` 里装的是什么（实测）

```
origin.apk (60,954,012 B)
  内部条目 1447 个
  dex = 4 个（classes..classes4）
  libnc.so / libusign.so = 无
```

**它是「去校验改造后的包」，不是加固后的包。**

### 2.2 直接调用会失败

`zip-reuse.build(src_apk, out_apk)` 的契约（见其 docstring 与 line 170）：

```python
if any(i.filename == origin_name for i in infos):
    raise SystemExit(f'❌ 输入包里已经有 {origin_name} 了')
```

它要求输入包**不含** origin.apk，然后把**整个输入包**当作 origin.apk 的数据。

加固产物**含** origin.apk → 直接调用必失败。

### 2.3 而且「整包复用」在加固侧本来就不成立

```
origin.apk 内容 = 去校验包（60.95MB，dex 4 个、无 libnc）
加固产物本体   = 加固后的包（63.78MB，dex 7 个、有 libnc/libusign）
```

**两者内容不同，无法共享同一份字节。** 这是「加固 + 去校验」组合的
物理下限，不是流水线忘做什么。

## 3. 方案：部分复用（partial reuse）

### 3.1 思路

不追求「整包共享」，只让**内容完全相同的条目**指回 origin.apk 内部偏移。

### 3.2 实测收益（关键数据，实现时用它验收）

```
产物条目(不含 origin.apk): 1458 条 / 63,782,547 B
  完全可共享（method/csize/fsize/CRC 全同）: 1438 条 / 52,852,837 B
  必须另存:                                    20 条 / 10,929,710 B

理论产物 = origin 数据(60,954,012) + 独有条目(10,929,710) ≈ 71,883,722 B
对比现状:                                                    124,913,473 B
节省:                                                         53,029,751 B (42%)
```

**模拟计算（含 LFH 对齐填充 + 中央目录，2026-11-25 实测脚本）：**

```
origin LFH（含对齐到 4096 的填充）:        4,096
origin 数据:                          60,954,012
独有条目（20 条）:                     10,929,710
中央目录（1459 条 + EOCD）:               96,043
─────────────────────────────────────────────
预计产物:                             71,983,883 B  (68.6 MB)
现状:                                124,913,473 B
节省:                                 52,929,590 B  (42%)
```

**验收时用 71,983,883 B ± 少量（中央目录精确值可能差几百字节）作为判据。**

**必须另存的 20 条明细**（加固改动过的，实现时用于交叉核对）：

```
4,663,445  classes.dex              1,643,028  resources.arsc
1,225,853  classes5.dex               977,506  classes3.dex
  729,296  assets/epic_default_gif.gif  717,034  classes7.dex
  272,399  lib/armeabi-v7a/libnc.so    209,600  lib/arm64-v8a/libnc.so
  198,246  classes2.dex                 59,802  lib/armeabi-v7a/libusign.so
   58,016  META-INF/___.SF              56,979  lib/arm64-v8a/libusign.so
   55,385  META-INF/MANIFEST.MF         37,262  assets/bilibili.9.png
    9,990  classes4.dex                  6,516  AndroidManifest.xml
    6,351  assets/nc_sigfix/payload.dex  1,818  classes6.dex
      989  META-INF/___.RSA               195  res/xml/epic_paths.xml
```

> ⚠️ `assets/epic_default_gif.gif` / `assets/bilibili.9.png` / `res/xml/epic_paths.xml`
> 出现在「独有」里，是因为**输入包本该有它们但被丢了**（这是另一个已知问题，
> 与本文无关，但实现时别误判为"共享失败"）。

### 3.3 产物布局

```
┌────────────────────────────────────────────────┐ offset 0
│ origin.apk 的 local header（对齐到 4096）        │
├────────────────────────────────────────────────┤ origin_data_start
│ origin.apk 的数据 = 原 60,954,012 B 去校验包      │
│   ↑ 共享条目的数据就在这里面                      │
├────────────────────────────────────────────────┤
│ 独有条目（20 条，10.93MB）                        │
├────────────────────────────────────────────────┤
│ 中央目录（origin + 1438 共享 + 20 独立）          │
├────────────────────────────────────────────────┤
│ EOCD                                            │
└────────────────────────────────────────────────┘
```

**共享条目的中央目录 offset = `origin_data_start + origin内部offset`**，
`method/csize/fsize/CRC` 全部沿用 origin.apk 里的值。

## 4. 要实现什么

### 4.1 新函数：`zip-reuse.build_partial()`

**签名**

```python
def build_partial(src_apk, out_apk, origin_name=ORIGIN_NAME):
    """把 src_apk 里的 origin.apk 内容作为可共享基础，让与它内容完全相同的
    条目指回 origin 内部偏移。

    Args:
        src_apk: 含 origin.apk 的 APK（加固产物）
        out_apk: 输出 APK
    Returns:
        dict: {'src_size','out_size','shared','unshared','saved'}
    """
```

**算法（约 120 行）**

```
1. 用 zipfile 读 src_apk：
     origin = getinfo(origin_name)          # 校验它 method==0 (STORED)
     origin_data = 读出这 60.95MB 数据
2. 用 io.BytesIO 打开 origin_data 当 ZIP：
     建 map: filename -> (local_header_offset, method, csize, fsize, crc, 对齐性)
3. 遍历 src_apk 其余条目：
     若 origin map 里有同名且 (method,csize,fsize,CRC) 全同
    且 origin 里该条目的 local header offset 满足其对自身要求的对齐
        → 记入 share，复用 origin 的元数据 + 计算全局 offset
     否则
        → 记入 unshared，数据从 src_apk 读出来照常写
4. 拼装（复用现有 _make_lfh / _make_cd / _align_extra）：
     out = origin 的 LFH（_align_extra 对齐到 4096）
     out += origin_data
     写 unshared 条目（STORED 的 so/apk/arsc 保持 STORED）
     cd_start = len(out)
     写中央目录（origin + share + unshared，offset 按上面规则算）
     写 EOCD
5. 写文件，返回统计
```

**必须处理的三个陷阱**

| 陷阱 | 处理 |
|---|---|
| **`resources.arsc` 对齐** | Android R+ 要求它 **数据起始位置** 4 字节对齐（不是 LFH 位置）。⚠️ 实测：产物里 `resources.arsc` 的 `header_offset=7,794,185`（不是 4 的倍数），但 `数据起始=7,794,232`（`%4==0` ✅），靠 `extra_len=3` 填充实现。**判断对齐必须用 `lfh_offset + 30 + name_len + extra_len`，不能用 LFH offset。** 若它在 share 列表里，就检查 origin 内的实际数据起始；不对齐则放弃共享它。 |
| **`origin.apk` 必须 STORED** | ✅ 实测 `method=0`，`compress_size == file_size == 60,954,012`。若 DEFLATE 了本方案不成立，直接 return 失败（让调用方退回旧行为） |
| **offset 溢出** | ZIP 用 32 位 offset。产物约 72MB，安全；代码里仍要检查，超 4GB 用 ZIP64（本场景不需要，明确不支持即可） |

**为什么不能简单 copy 现有 `build()`**：现有 `build()` 只做「整包当一个数据块」，
没有「读 origin 内部 offset 表」这一步。这是新增的核心逻辑。

### 4.2 `protect.sh` 接调用

位置：`scripts/pipelines/protect.sh` 的 `repack_build "$WORK/decompiled" "$WORK/unsigned.apk"`（约 2643 行）之后、`finish_apk` / `packer.sh` **之前**。

```bash
# ── 部分数据复用（2026-11-25）───────────────────────────────────────
# apktool b 把 origin.apk 从「共享字节」拆成实体副本（119MB）。
# 这里手写一次 ZIP，让与 origin.apk 内容完全相同的条目指回它的内部偏移
# （→ 69MB）。详见 docs/计划书-部分数据复用.md
#
# ⚠️ 三个前提，任一不满足就跳过并 warn（不能 fail-fast，那会让所有包出不来）：
#   ① 源包含 assets/nc_sigfix/origin.apk（不含 = 没做去校验，无需复用）
#   ② 该条目是 STORED（DEFLATE 的无法作为共享基础）
#   ③ 产物里存在可共享条目（≥1 条；0 条说明加固全改了，复用无意义）
if _has_origin "$WORK/unsigned.apk"; then
  python3 "$ROOT/scripts/repack/partial-reuse.py" \
      "$WORK/unsigned.apk" "$WORK/reused.apk" \
    && mv "$WORK/reused.apk" "$WORK/unsigned.apk" \
    || log_warn "[partial-reuse] 跳过（产物仍可用，只是体积未优化）"
fi
```

> ⚠️ **位置必须在 `finish_apk`（zipalign）之后。**
> `zipalign` 会重写整个 ZIP，把共享布局拆平——与 apktool 同样的问题。正确顺序：
>
> ```
> repack_build（apktool，124MB）
>   → finish_apk（zipalign，仍 124MB，但已对齐）
>     → partial-reuse（69MB，保留对齐性）
>       → keep-sig-block（原地插入签名块，不重写 ZIP）
> ```
>
> ✅ **已核实（2026-11-25）**：`keep-sig-block.py` 的 `inject_sig_block()` 是
> **原地插入**——`out = data[:cd_off] + sig_block + data[cd_off:eocd]`，只修正
> EOCD 的 CD offset，不动任何条目的 offset。插入点在 origin 数据区**之后**，
> 所以**不破坏重叠布局**。这意味着签名块注入可以放在复用之后，无需特殊处理。
>
> 不过仍建议实现时跑一次 §5 的验收（体积 + 能装），确认无误。

## 6. 风险与回退

| 风险 | 概率 | 后果 | 缓解 |
|---|---|---|---|
| 手写 ZIP offset 算错 | 中 | **装不上**（`INSTALL_PARSE_FAILED`） | T3 用 `zipfile` 全量解压校验；真机第一关就暴露 |
| 共享后对齐被破坏 | 中 | 装机被拒（Android R+） | T5 断言 + 遇到不对齐的条目放弃共享 |
| `keep-sig-block.py` 破坏布局 | **高（待核实）** | 复用白做 | **实现第一步就要核实**，见 §4.2 |
| 某些条目虽同名但内容不同（CRC 碰撞） | 极低 | 内容错乱 | 用 CRC32 + csize + fsize 三重比对，不用文件名 |
| 输入包 origin.apk 是 DEFLATE | 低 | 方案不成立 | 检测 method != 0 就跳过 |

**回退方式**：`protect.sh` 里那一步是 `|| log_warn`，失败不影响出包——
最坏情况退回到 119MB（与现在一样），不会产出坏包。

## 7. 已知的边界（不要试图解决）

| 边界 | 说明 |
|---|---|
| 不能做到 64MB | `origin.apk` 数据（60.95MB）与加固新增条目（10.93MB）内容不同，必须各存一份。**72MB 是理论下限** |
| 不能用 apksigner 签 | 它展开重叠条目。必须 MT 管理器 |
| 不能用在「只加固」场景 | 没有 origin.apk，无需复用（也无从复用） |
| 不能用在「只去校验」场景 | 那条流水线已经做了整包复用（64MB），比本方案更优 |

## 10. 给实现者的一句话

**这个方案的核心只有一句**：产物里与 `origin.apk` 内部条目**完全相同的 1438 条**，
在中央目录里指向 `origin_data_start + 原offset`，不再存第二份。

如果实现过程中发现任何一条无法共享，**放弃那一条、正常存**——宁可少省几 MB，
也不要产出装不上的包。

## 11. 审核记录（2026-11-25，写计划书时逐条实测核实）

| # | 原本的疑问 | 核实结果 | 对计划的影响 |
|---|---|---|---|
| 1 | `keep-sig-block.py` 会不会破坏重叠布局 | ✅ **不会**。它只是 `data[:cd_off] + sig_block + data[cd_off:eocd]`，只改 EOCD 的 CD offset，条目 offset 全不动。插入点在 origin 数据区之后 | 风险从「高」降为「无」，签名块可放在复用之后 |
| 2 | `origin.apk` 是 STORED 吗 | ✅ `method=0`，`csize == fsize == 60,954,012` | 共享基础成立 |
| 3 | `resources.arsc` 对齐怎么判 | ⚠️ **不能用 LFH offset 判**。实测 `header_offset=7,794,185`（非 4 倍数）但 `数据起始=7,794,232`（`%4==0`）。对齐靠 `extra_len=3` 填充 | 已写进陷阱表，避免实现者踩坑 |
| 4 | 72MB 这个数字准吗 | ✅ 模拟计算得 **71,983,883 B（68.6 MB）**，与理论值 71,883,722 差 10 万字节（中央目录精确大小） | 验收判据用 71,983,883 B ± 少量 |
| 5 | CRC 判据够不够（会不会 CRC 相同内容不同） | ✅ 抽查 200 条 CRC 命中项，内容**全部一致** | 三重判据（method+csize+fsize+CRC）可靠，无需额外逐字节比对 |
| 6 | 底层函数能不能复用 | ✅ `_lfh_len` / `_make_lfh` / `_make_cd` / `_align_extra` 签名清晰、已在真机跑通 | 建议复制（83 行），不跨模块 import |

**审核结论：方案可行，无阻塞项。** 唯一需要在实现时保持警惕的是 ZIP offset
手算（错 1 字节就装不上），由测试 T1/T2/T3 兜住。
