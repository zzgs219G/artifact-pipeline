## ★ 反检测：必须拆 SupportGuard.checkHookXposed（2026-11-23 新增）

**这是注入任何 hook 框架的前提**，不拆就必闪退（且是无日志的主动退出）。

### 完整链路（1.0.14 与分析报告一致，1.0.17 未变）

```
SupportInitProvider.onCreate()              [classes13] ContentProvider，进程启动即跑
  └→ Handler.postDelayed(SupportInitProvider$1)
       └→ SupportGuard.runAll(ctx)  → int   [classes11] 威胁位掩码
            └→ checkHookXposed()            ← 命中源，or-int 0x4
               └→ SupportLoader.onThreatDetected(mask)
                    └→ SupportBlockActivity.launchBlock()   ← RAIJIN SHIELD 拦截页

**为什么 `logcat -b crash` 什么都看不到**：`System.exit(0)` 是干净退出，
不是异常崩溃，所以没有 FATAL / 异常栈。排障时只能看
`logcat | grep -E "^.*RT: m: 0x"`（`RT` 是 SupportGuard 的 TAG）。

### 补丁（`apply-mods.py` 已内置）

`classes11`，`SupportGuard.checkHookXposed()Z` —— **方法体清空，恒 return 0**：

```smali
.method private static checkHookXposed()Z
    .registers 6          ← ⚠️ 必须保留！删了报
                          #   "A .registers or .locals directive must be present"
    const/4 v0, 0x0
    return v0
.end method
```

### 三个关键决策（都是踩出来的）

**① 为什么只改 checkHookXposed，不改 runAll**
`runAll` 是 14 项的总出口，改它会把调试器/root/模拟器/虚拟空间/抓包检测
一起废掉，动静太大、静态特征也明显。只改 `checkHookXposed` 影响面最小。

**② 为什么整体清空，不是只删命中的那条类名**

> **`0x4` 的类名/包名名单是远程配置下发的。**
> 今天不在名单里的 hook 框架，明天可能被加进去。

这正是"注入了 hook 框架就被检出"的机制来源 —— 不能逐条对抗，必须拆整个方法。

**③ 为什么必须保留 `.registers` 指令**
smali 汇编器对"方法体为空但缺 `.registers`"直接报错：
```
A .registers or .locals directive must be present for a non-abstract/non-final method
```
替换方法体时不能连 `.registers 6` 一起删。

### 与 native 层的关系

我们的 `libusign.so` 用 **shadowhook**（`com.bytedance.shadowhook.*`），

## 0. 给下一任 AI 的最重要提醒（别重蹈覆辙）

### 0.1 不要做的事
1. **不要用 jadx 全量反编译这个 APK**——13 个 dex、7.8 万类，手机（Termux/8GB）堆内存必 OOM
   （jadx 1.5.6 在 UsageInfo 阶段崩）。**只用 `jadx --single-class` 按类反编译**，
   或用 apktool 解 smali + grep。
2. **不要用 apktool 回编**——它会用 dex 035 格式重编，丢接口私有方法语义，
   运行时 `IncompatibleClassChangeError: Found interface ... but class was expected`
   （DrawScope 崩溃，排查了 2 小时的坑）。**必须用 smali 2.5.2 `--api 28` 单独编 dex（039 格式）**，
   然后把新 dex 直接塞回原 APK（zipfile 字节替换）。
3. **不要信 `Download/囧次元.apk` 是官方包**——它是另一个作者改过的（证书 `d82e48da...` ≠
   官方 `de17140c...`）。官方 1.0.17 校验基准：证书 SHA-256 =
   `de17140c22b492a9e38d188c675a185d9d67e1607342f03ed0a181d9f3696e74`
   （从 `META-INF/YZS.RSA` 提取，openssl pkcs7 可验）。
4. **不要试图对比 1.0.14 官方/破解包找改动**——破解包被整体优化重编译，
   寄存器/控制流全变，任何文本 diff 都是 1.4 万+ 文件的噪音。
   唯一有效的对比是**方法级 invoke+const-string 序列哈希**（见 5.3）。
5. **smali 补丁里 invoke-virtual 寄存器顺序**：`{v0, p0}` 和 `{p0, v0}` 完全不同！
   `callVideoAdReward(Z)` 写成 `{v0, p0}` 会导致 VerifyError（v0 被 forName 成 this），
   渠道类加载失败 → 静默回退真实广告路径。V1-V4 版失败就是栽在这里，日志关键词
   `Rejecting re-init on previously-failed class` / `failed to verify`。

### 2.2 广告奖励（免广告直发）——本次最难的部分

**事件流架构（1.0.17）**：
```
渠道 SDK(GDT/CSJ/KS/Sigmob/百度/美数/AdScope/Gromore/章鱼)
  ↓ (各自 RewardAdAdapter / InterstitialAdAdapter.showAd，或 AdapterProxy)
windmill core (assets/windmill/athena/core 的 RewardAdAdapter / InterstitialAdAdapter)
  ↓ callVideoAdShow/PlayComplete/Reward/Closed → IAdBridge
App facade: AdEvent 流 (Shown/PlayStarted/PlayEnded/RewardEarned/Closed...)
  ↓ SdkRenderBridgeKt.reduceAdEvent(event, rewarded, playEnded, ?) → RenderStep
SdkOutcome (Completed/UserClosed/ClosedAfterPlayEnd/...) → AdSessionUseCase.invokePreparedInternal
  ↓ (Completed 才走)
confirmRewardSession({nonce, taskCode}) → 服务器
  ↓
claimReward({nonce, slotCode, taskCode}) → 服务器返回 status=pending s2sVerify=true 时进轮询
  ↓
getRewardStatus 轮询（服务器等广告平台 S2S 回执）→ Recorded/Granted → 发奖
```

**hook 点（4 层全部覆盖，缺一不可）**：
1. **core dex**（assets/windmill/athena/core，解包→patch→重编→回填 zip）：
   - `com.windmill.sdk.core.ads.reward.RewardAdAdapter.showAd(Activity,Map)V`
     → `callVideoAdShow(); callVideoAdPlayComplete(); callVideoAdReward(true); callVideoAdClosed(); return`
   - `com.windmill.sdk.core.ads.interstitial.InterstitialAdAdapter.showAd` 同理（Show+Closed）
   - 这是**统一入口**，覆盖所有 custom 渠道（AdapterProxy 直连路径除外）
2. **主 dex 8 个渠道 RewardAdAdapter.showAd**（adscope/baidu/csj/gdt/gromore/kuaishou/meishu/sigmob）
   → 同样的回调链（双保险）
3. **主 dex 8 个渠道 InterstitialAdAdapter.showAd** → callVideoAdShow + callVideoAdClosed
4. **App 层结算判定**（最关键，V3 起效的点）：
   `shared.presentation.ad.SdkRenderBridgeKt.reduceAdEvent(AdEvent,ZZZ)RenderStep`
   - 原：`Closed → 仅当 rewarded==true && playEnded==true → SdkOutcome.Completed`
   - 改：**Closed → 无条件 Completed**（删掉两个 if-eqz p1/p3）
   - **以及 `Shown` 事件 → 直接 Settle(Completed)**（V4 加的：广告页弹出的瞬间就结算，不用等关闭）

**核心认知（为什么 must 这样）**：
- `RewardEarned(isRewarded=true)` 只有真实看完广告 SDK 才会发 → 不等它，直接在 Shown/Closed 伪造 Completed
- 服务器 `watch_ad_vip` 任务 `s2sVerify=true`：claim 后进 `getRewardStatus` 轮询等平台回执。
  **实测：GDT 原生广告只要真实曝光(onADExposed)就会产生回执**——所以不能拦渲染本身，
  要让广告真实加载+曝光（Native 路径），只是把 App 的结算判定提前。
  **V4/V5 的正确姿势是：不拦 GDT Native 渲染，只把 App 层结算判定改成 Shown 即 Completed。**
- 插屏/开屏走 `InterstitialClosed` 结算（"按关闭结算,不领奖"），它们的 claimReward 是无奖励上报，
  Shown→Completed 让它们也即时结算（副作用：开屏可秒关）

**踩坑记录**：
- 1.0.14 的 hook 点（主 dex `WMCustomRewardAdapter.showCustomAd` 基类）在 1.0.17 **不存在**

## 7. 遗留问题与备注

- **origin.apk**：原 fancy 包里它是 ZIP overlapping entry（199MB 包里不占空间），
  常规工具重建必须实存（官方全量=+197MB → 包 399MB；置空→包 201MB 但**会被判破解**，
  因为 FancyBypass 壳从它提取官方签名喂 PMS hook——V1 置空版失败即此因）。
  399MB 版已验证可用。迷你化思路（未做）：构造只含官方签名块+最小 ZIP 结构的 APK。
- **s2sVerify=true**：`watch_ad_vip` 的奖励依赖 GDT 真实曝光回执，实测曝光后能到账但需
  数秒轮询；**不能**在 Shown 前 claim（服务器 pending 无回执会一直转）。
  V5 的时序：真实曝光发生 → Shown→Completed → confirm → claim → 轮询到回执 → 到账。
- **app 内自动更新会覆盖补丁**：升级后需对官方新包重做全部补丁（本文档流程可复用）
- 1.0.14 破解包（`常用/工作台😡/囧次元/囧次元_1.0.14破解包.apk`）的改动源流是
  论坛帖「动漫共和国1.0.14-教程」（zeroking，33 类改动），`常用/工作台😡/同类壳过.md` 有全文
- 测试签名 keystore：`~/jk_reverse/test.keystore` pass=123456 alias=test
