### 另一种去开屏的思路（1.0.14 用过，1.0.17 未采用）

`逆向分析报告.md`（1.0.14 时代）的做法是改 `SplashViewModelKt.splashAdWaitBudgetMs`
让它返回 0：

```java
// 原：品牌图展示剩余时间 + 上限的 clamp
return brandEnteredAtMs <= 0 ? capMs
     : coerceIn((brandEnteredAtMs + brandDurationMs + capMs) - now, 0L, capMs);
// 改：恒返回 0L
```

→ `withTimeoutOrNull(0)` 立即超时 → `result == null` 走 give-up 分支
→ 取消未展示的广告会话 → 直接进主页。品牌图仍正常显示。

**两种思路对比**：

| | `splashAdWaitBudgetMs` 改 0 | `AdvertisingState.shouldShow` 改 false |
|---|---|---|
| 作用层级 | 开屏专用的等待预算 | 广告会话总闸门（所有 slot） |
| 影响面 | 只影响开屏 | 开屏 / 插屏 / 横幅全受影响 |
| 优点 | 精准、语义清晰、不碰 SDK | 一处覆盖所有非激励广告 |
| 缺点 | 只解决开屏 | 面更大，需确认不会误伤激励 |

当前采用的是 `shouldShow`（因为同时要处理主页插屏）。如果发现开屏仍会弹，
可追加 `splashAdWaitBudgetMs` 作为第二道保险——两者不冲突。

⚠️ 1.0.14 报告里的另一个坑也适用：**不要硬改 suspend 函数的返回值**
（`awaitSplashAdOrGiveUp`），会导致
`ClassCastException: CompletedContinuation cannot be cast to DispatchedContinuation`。
改参数（`splashAdWaitBudgetMs`）而不是改返回值。

**第 4 项是后加的**：只改前三项时开屏仍会弹。`shouldShow` 是广告会话的总闸门，
返回 false 走官方自己的 `warm=skip reason=state_off` 分支——开屏/插屏/横幅
在会话创建前就被跳过，比"拦渲染"干净得多。

**验证方式**：`adb logcat | grep -E "InterstitialEscape|AdPoolTrace"`
—— 启动后应无 `interstitial show` / `splash page_shown` 日志。

## 0. 核心约束（必读）

1. **开屏广告不能直接删除**——不能删除 `SplashScreen`、`SplashFadeGate` 或开屏广告 SDK 调用，否则广告平台回调（加载/展示/关闭/奖励）不会触发，导致回调失败。
2. **正确做法**：保留开屏广告 SDK 的完整回调链路，仅让主页不显示开屏 hold 页面，直接进入主页内容。
3. **主页弹窗广告**——不需要删除插屏广告 SDK，只需阻止 `HomeViewModel.requestHomeInterstitial()` 向 `RewardedAdOverlay` 发起实际请求即可。
4. **smali 编译格式**：必须用 smali 2.5.2 `--api 28`（039 格式），不要用 apktool 回编 dex，否则会 `IncompatibleClassChangeError`。
5. **寄存器顺序敏感**：smali 中 `invoke-virtual {v0, p0}` 和 `{p0, v0}` 完全不同，写错会导致 `VerifyError`。

## 2. 补丁 1：去开屏广告启动图（保留回调）

### 2.1 原理

主页中的 `HomeChromeSplashHold` 组件根据 `isHomeChromeHeldForSplash(completed, heldForSplash)` 的返回值决定是否显示开屏 hold 页面：

- 仅当 `completed == false` 且 `heldForSplash == false` 时返回 `true`（hold 开屏）
- 其他情况返回 `false`（显示主页常规内容）

**修改目标**：让 `isHomeChromeHeldForSplash()` 恒返回 `false`，使主页始终显示常规内容，不显示开屏 hold。

同时辅助修改 `SplashFadeGate.isCompleted()` 恒返回 `true`，让所有依赖开屏完成状态的逻辑都认为开屏已结束。

## 3. 补丁 2：去主页弹窗广告

### 3.1 原理

主页弹窗广告由 `HomeViewModel.requestHomeInterstitial()` 触发。该方法在非 VIP 路径（`getAdSlotVipExemption()` 返回 null 时，即绝大多数用户）会走到 `:cond_6` 标签，调用 `getAdOverlay().request(AdRequest, continuation)` 实际请求插屏广告。

**修改目标**：在 `:cond_6` 处阻止实际请求，直接返回一个成功的 `Either<AdError, AdSuccess>`，使状态机认为插屏请求已完成但不展示广告。

### 3.2 具体 smali 修改

**文件**：`smali_classes10/com/yy/myuko/shared/presentation/screen/main/home/HomeViewModel.smali`  
**方法**：`requestHomeInterstitial(Lcom/yy/myuko/shared/domain/ad/AdRequest;Lkotlin/coroutines/Continuation;)Ljava/lang/Object;`（约第 19925 行）

**关键代码位置**：`:cond_6` 标签（约第 20150 行）

**原代码（cond_6 部分）**：
```smali
    :cond_6
    :goto_2
    invoke-direct {p0}, Lcom/yy/myuko/shared/presentation/screen/main/home/HomeViewModel;->getAdOverlay()Lcom/yy/myuko/shared/presentation/ad/RewardedAdOverlay;
    move-result-object p2
    invoke-static {p1}, Lcom/yy/myuko/shared/presentation/ad/SpillingKt;->nullOutSpilledVariable(Ljava/lang/Object;)Ljava/lang/Object;
    move-result-object v2
    iput-object v2, v0, Lcom/yy/myuko/shared/presentation/screen/main/home/HomeViewModel$requestHomeInterstitial$1;->L$0:Ljava/lang/Object;
    iput v3, v0, Lcom/yy/myuko/shared/presentation/screen/main/home/HomeViewModel$requestHomeInterstitial$1;->label:I
    invoke-virtual {p2, p1, v0}, Lcom/yy/myuko/shared/presentation/ad/RewardedAdOverlay;->request(Lcom/yy/myuko/shared/domain/ad/AdRequest;Lkotlin/coroutines/Continuation;)Ljava/lang/Object;
    move-result-object p1
    if-ne p1, v1, :cond_7
    :goto_3
    return-object v1
    :cond_7
    return-object p1
```

**新代码**：
```smali
    :cond_6
    :goto_2
    # 跳过实际广告请求，直接返回成功 Either
    # 注意：requestHomeInterstitial 返回 arrow/core/Either<AdError, AdSuccess>
    # AdSuccess 是接口，需先确认其子类（如 AdSuccess$Recorded、AdSuccess$Rewarded）是否有 INSTANCE 单例字段
    # 建议先用 jadx --single-class 查看：
    #   jadx --single-class com.yy.myuko.shared.domain.ad.AdSuccess\$Recorded classes10.dex
    #
    # 示例（若 AdSuccess$Recorded 有 INSTANCE）：
    # sget-object p1, Lcom/yy/myuko/shared/domain/ad/AdSuccess$Recorded;->INSTANCE:Lcom/yy/myuko/shared/domain/ad/AdSuccess$Recorded;
    # invoke-static {p1}, Larrow/core/EitherKt;->right(Ljava/lang/Object;)Larrow/core/Either;
    # return-object p1
    #
    # 占位：若未确定 AdSuccess 实现，可暂时返回 v1 (COROUTINE_SUSPENDED)，但会导致状态卡住，不推荐生产使用
    return-object v1
```

> ⚠️ 注意：补丁 2 需要确认 `AdSuccess` 子类是否有 `INSTANCE` 字段，建议另一 AI 先用 `jadx --single-class` 查看相关类，再决定 `EitherKt.right()` 的参数。

### 3.3 备选方案：修改 `RewardedAdOverlay.request()`

如果上述方案难以确定 `AdSuccess` 实现，可改为修改 `RewardedAdOverlay.request()` 方法，让它直接返回成功而不实际显示广告。

**需要先定位文件**：`RewardedAdOverlay` 可能在 `smali_classes6/7/8` 中，需用 `find` 定位：


**修改思路**：在 `request()` 方法开头直接 `return-object` 一个成功的 `Either`，不调用广告 SDK。

## 5. 注意事项

0. ⚠️ **反检测（必须同时做）**：`SupportGuard.checkHookXposed()` 方法体清空
   （classes11）。这份检测的类名名单是**远程配置下发**的，注入任何 hook 框架
   都会被检出 → RAIJIN SHIELD 拦截页 → System.exit(0)。
   `apply-mods.py` 已内置此补丁。
1. **smali 编译格式**：必须用 smali 2.5.2 `--api 28`（039 格式），不要用 apktool 回编 dex，
   否则会 `IncompatibleClassChangeError`（已踩，见 `docs/签名校验接手文档.md`）。
2. **补丁顺序**：先改 `isHomeChromeHeldForSplash` / `isCompleted` / `shouldShow`，
   再改 `requestHomeInterstitial`。
3. **不要签名的时机**（2026-11-23 修正）：
   - 业务补丁阶段**绝不能签名** —— 后续去校验要从包里提原始证书
     （`META-INF/*.RSA`），一旦重签，提出来就是新证书，origin.apk 的证明力就没了。
   - 完整顺序：
     ```
     官方/裁剪包 → apply-mods.py（本文件的补丁）→ uncheck.sh（签名校验绕过）
       → MT 管理器签名 → 装机
     ```
4. **签名工具必须是 MT 管理器**：`apksigner` 会重写 ZIP 把数据复用结构展开
   （122MB → 244MB）。MT 实测保持复用（128MB）。
5. **工作目录**：`~/jk_reverse/refix/r3/` 是已打全部业务补丁的 smali 树；
   用 `apply-mods.py` 可一键套用到任意同版本 APK（只重编受影响的 5 个 dex，
   其余 8 个逐字节不变）。
