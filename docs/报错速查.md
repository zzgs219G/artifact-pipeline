## 回编/格式保真类

| 报错现象 | 根因 | 修法 |
|---|---|---|
| 报错八:注入后 APK 膨胀 380KB~1.8MB | apktool 回编重建 debug_info,按方法数线性放大 | 解包加 `--no-debug-info`(已修);排"包变大"先对比 dex map 区块 |
| 报错十八:Compose 首帧 `IncompatibleClassChangeError` | apktool 回编一律写 035 头,原包 038 的接口方法按旧规则校验 → ICCE | `patch-dex-version.py` save/restore 双模式(已修);教训:**"两包内容一致却一崩一不崩"先 diff 字节级元数据** |
| 报错五十九:回编报 `Could not smali folder: <任意 smali 目录>` → `ExceptionWithContext: Exception occurred while writing code_item for method <任意类>` → `Error while writing instruction at code offset 0x2/<其他>` → **`Unsigned short value out of range: 65536`**(`InstructionWriter.write(SourceFile:398)`) | **dex 的 method_ids 超 65536**(16 位索引)。真实大型包经 R8/d8 编译后 classes.dex 几乎必然贴顶(实测囤次元包 65519/65536,**余量仅 17**;15 个 dex 里 6 个余量 < 500),而 `inject-javacheck.py` / `encrypt-strings.py` 曾把注入类**硬编码写进 `smali/`**,实测 Guard+NcLink+Guard$Hb 占 25 个方法 → 直接溢出。**报错类名毫无诊断价值**:谁最后被写谁中枪,同包三次分别炸在 `com/beizi/ad/e$a->values()`、`androidx/media3/.../Tracks$Group-><init>`、`androidx/camera/.../ExifData$WhiteBalanceMode->values()`,全部是**我们没碰过的第三方类** | `scripts/repack/dex-capacity.py`:注入前读 dex header 的 `method_ids_size`(偏移 0x58,只读 112 字节,15 个 dex 共 20.6ms),余量 < 需求(注入量+2000 工程余量)就**新建 `smali_classes{N+1}/`**(n+1,只增不改,不碰任何已有 dex 也不捡现成的空 dex);两处注入点按同一标记文件共用同一个自建 dex。已修(报错五十九)。**排查要点**:① 见到 `65536` 先算目标 dex 的方法数,**不要看报错类名**;② 只查方法数就够——字符串索引超限**不致命**(dexlib2 自动升 `const-string/jumbo`,原包本身已有 2982 条 jumbo);③ 本地复现:往 `smali/` 塞 20 个方法 → 逐字复现同一栈;塞 17 个(65519+17=65536,正好到上限)→ 编译成功,可用来二值确认 |

| 报错六十:回编 `Could not smali file: <smali 路径>` → `<路径>[行,4] Invalid register: vNNN.
