# 发布与验证流程（SOP）

> **这份文档解决什么问题**：每一任新接手的 AI/人都要重新摸索一遍
> 「改完代码之后该做什么」，而且经常做错 —— 实测踩过的错误包括：
>
> · 改完 nox 源码不打 tag、不重新打包 → 用户手机跑的仍是旧版
> · 打了 tag 但改名不带 `-obf` → 产出的 `.a` 里没有 VMP，so 凭空小 379KB
> · 换了分发包但没删解压产物 → `ensure_nox` 靠文件存在判断，静默用旧版
> · 走了本地编译 / 本地构建 → 环境不同，结论不成立
> · 漏更新 `工具包版本.md` → 版本表与实物脱节，事后无法追溯
>
> **照本文档的顺序做，不要自创流程。**

---

## 0. 一句话总览

```
改代码 → 跑测试 → 打 tag → 云端 CI 打包 → 下载分发包 → 替换消费方
   → 同步版本表 → 跑云端构建 → 真机验证（有 adb 时）→ 报告产物路径
```

**唯一的构建入口是云端网关**（`scripts/trigger_build.py`）。
不做本地构建 —— 本地没有 NDK/Amice bundle，编出来的东西与线上不一致。

---

## 1. 判断你要发的是哪一层

这个项目有三个仓库，改动落在哪一层决定了要走哪套流程：

| 你改了什么 | 要做什么 | 目标 tag 仓库 |
|---|---|---|
| `nox/scripts/so-guard/*.c`（锁箱设施、自检报告） | 发 nox 分发包 | `../nox` |
| Amice 的 Rust pass（`防御仓库/amice`） | 发 Amice bundle | `防御仓库/amice` |
| `artifact-pipeline/scripts/**`（流水线本体） | 只推 main，构建用最新代码 | 不需要 tag |
| `configs/v1/config-schema.json`（模块勾选项） | 只推 main | 不需要 tag |

**只有被「打包成分发包」的仓库才需要 tag。** 流水线脚本是 checkout 最新
代码跑的，推上去就生效。

## 2. nox 变更的完整流程（最常走的一条）

### 2.1 改完先跑测试

```bash
cd ../nox
bash test.sh          # 必须 0 失败才能继续
```

测试里包含 V7（`.ncxr` 与 `.bss` 同页）、V12（自检报告）、V15（版本文档与
tag 一致）等关键断言。**测试红了不要打 tag** —— CI 也会红，白跑一轮。

### 2.2 更新版本记录

`docs/版本记录.md` 顶部的「当前版本」必须与即将打的 tag 完全一致，
否则 CI 的 V15 断言会失败：

```markdown
| **版本** | `v0.9.45-xxx-obf` |
```

### 2.3 打 tag —— **名字必须带 `-obf`**

```bash
cd ../nox
git add -A && git commit -m "feat(...): ..."
git tag -a v0.9.45-xxx-obf -m "说明"
git push origin main
git push origin v0.9.45-xxx-obf
```

**为什么必须带 `-obf`**：`.github/workflows/release.yml:181` 的判定是

```bash
if [[ "$REF" == *-obf* ]]; then ON=true; fi
```

不带 `-obf` 的 tag 走**普通编译**，产出的 `libnox.a` 里**没有 VMP**
（`nc_guard_crypto.o` 的 VM 子段数 = 0）。后果：消费方链接后第一套
VMP 三个段（`.ncr`/`.ncq`/`.ncs`）完全消失，so 从 747KB 掉到 368KB
—— 是防护缺失，不是瘦身。**这个坑实测踩过一次，花了 40 分钟才发现。**

### 2.4 等 CI 出包并验证 VMP 在包里

```bash
gh run list --workflow=release.yml --limit 1
# 等 completed/success，然后：
cd /tmp && rm -rf vx && mkdir vx && cd vx
gh release download <tag> --repo zzgs219G/nox -p 'nox-<tag>.zip' --clobber
sha256sum nox-<tag>.zip        # 记下来，后面要填进版本表
unzip -q nox-<tag>.zip
ar x nox/so-guard/lib/arm64-v8a/libnox.a nc_guard_crypto.o
readelf -S -W nc_guard_crypto.o | grep -cE '\.ncr|L\.L__'
# ↑ 必须 > 0（正常值 ~209）。等于 0 = 打 tag 时漏了 -obf，重打
```

### 2.5 替换消费方的分发包

```bash
cd ../artifact-pipeline
cp /tmp/vx/nox-<tag>.zip tools/nox.zip
rm -rf tools/nox                    # ⚠️ 必须删！
unzip -q tools/nox.zip -d tools/
unzip -p tools/nox.zip nox/VERSION  # 确认版本号对得上
```

**为什么必须删 `tools/nox/`**：`common.sh` 的 `ensure_nox` 靠
「文件是否存在」判断要不要解压。旧产物留着 → 静默用旧版 → 后续所有
构建都基于旧代码，而日志看起来完全正常。

### 2.6 同步版本表（漏了会静默漂移）

`tools/工具包版本.md` 有三处要改：

1. `nox.zip` 那行的版本号、sha256、字节数
2. 文末汇总行 `作者:当前 ... / nox vX.Y.Z`
3. 正文里出现的路径引用（如 `ncguard_log.md`）

改完验证：

```bash
python3 scripts/actions/tests/test-toolkit-version.py    # 7 项必须全过
```

### 2.7 跑云端构建

```bash
RELAY_TOKEN=<token> python3 scripts/trigger_build.py scripts/样本.apk \
    --sigcheck --vmp --sign
```

**这是唯一的构建入口。** 不要用 `gh workflow run`（需要先手动传 R2），
更不要本地 `ndk-build`（本地没有 Amice bundle，产物不同）。

### 2.8 有 adb 时真机验证

```bash
adb devices                          # 确认设备在线
# 装机后启动 App，然后：
adb shell "cat /storage/emulated/0/Android/data/com.xixin.box/files/ncguard_log.md"
```

**看三件事**：

1. 有没有 `[NCG-TRACE]` 行、最后一行是哪一步（闪退定位）
2. 段表里 `.ncx` 的「熵(文件)」是否 ≈8.0、「熵(内存)」是否 ≈6.5
   （两者都对 = 锁箱生效）
3. VMP 列 ✅ 的段有哪些

进程存活检查：

```bash
adb shell pidof com.xixin.box     # 有输出 = 没闪退
```

### 2.9 报告产物路径

**必须给出完整路径**，不要只说「构建成功」：

```
/sdcard/Download/样本_signed_HH_MM_SS.apk（N 字节）
```

## 3. Amice 变更的流程

### 3.1 编译验证只能用云端

本地没有 Rust 工具链。**不要**为了验证语法去跑全平台构建 ——
`build-android-ndk.yml` 会同时编译 r27d/r28c/r29/r30 × LLVM 18/19/21，
一次几十分钟。

```bash
# 只跑需要的那个组合
gh workflow run build-android-ndk.yml --ref master
```

改的是 pass 逻辑时，本地可用 `-fsyntax-only` 做不了（Rust），
直接看 CI 的 verify job。

### 3.2 发 bundle

```bash
cd 防御仓库/amice
git tag -a vX.Y.Z-<说明> -m "..."
git push origin master && git push origin vX.Y.Z-<说明>
```

release.yml 的矩阵已裁剪为**只有 LLVM 21 + NDK r29 + ubuntu**（约 8 分钟），
不会跑全平台。

### 3.3 替换消费方的 bundle URL

`protect-modules.yml` 有 **6 处**引用（3 个 cache key + 3 个 URL）：

```bash
cd ../artifact-pipeline
grep -n 'amice-r29-v' .github/workflows/protect-modules.yml
sed -i 's/v旧版本/v新版本/g' .github/workflows/protect-modules.yml
```

**漏改的后果**：CI 从缓存拿到旧 bundle，新写的 pass 逻辑完全不生效，
但构建全绿 —— 又是一次「看起来成功」。

## 4. 最容易犯的六个错

| # | 错误 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 改完源码不打 tag | 用户跑的是旧版，日志/产物都对不上 | 见 §2.3 |
| 2 | tag 不带 `-obf` | 分发包里没有 VMP，so 小 379KB | tag 名必须含 `-obf` |
| 3 | 不删 `tools/nox/` | 静默用旧解压产物 | `rm -rf tools/nox` 再解压 |
| 4 | 不更新版本表 | 版本表与实物脱节，无法追溯 | 跑 `test-toolkit-version.py` |
| 5 | 本地编译/构建 | 环境不同，结论不成立 | 一律走 `trigger_build.py` |
| 6 | 只发 main 不打 tag（该打的没打） | 分发链路断在中间 | 按 §1 判断改的是哪一层 |

## 5. 验证清单（发版前逐条打勾）

```
□ nox test.sh 0 失败
□ docs/版本记录.md 的「当前版本」== 即将打的 tag
□ tag 名含 -obf
□ CI Release 成功
□ 分发包里 nc_guard_crypto.o 的 VM 子段数 > 0
□ 已删 tools/nox/ 并重新解压
□ tools/工具包版本.md 三处已同步
□ test-toolkit-version.py 7/7
□ 云端构建成功
□ （有 adb）真机不闪退 + ncguard_log.md 内容正常
□ 报告产物完整路径
```

## 6. 为什么这些步骤不能省

这个项目的核心风险是**静默失败**：

- 混淆空转（pass 装了但函数全被跳过）→ 构建绿、产物正常、只是没保护
- 分发包没换 → 用户看到的是旧代码的行为，却以为在测新版
- VMP 跳过 → 日志不说，得反汇编才发现

所以每一步的验证都必须是**在产物上验**，不能只看日志有没有打印。
`docs/踩坑记录` 里记的绝大多数问题，本质都是「以为生效了，其实没有」。
