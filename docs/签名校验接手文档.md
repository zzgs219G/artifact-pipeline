## 1. 漏洞在哪：两条未覆盖的路径

### 1.1 路径 A：App 自读 APK 文件

App 不调 PackageManager，直接：

```java
// 读自己 APK 里的 META-INF/*.RSA（v1 签名证书）
ZipFile zf = new ZipFile(getPackageResourcePath());
// 或读 v2/v3 签名块（APK Signing Block，二进制块，在 ZIP central directory 之前）
```

**本模块为什么没覆盖**：Java 层 hook 的是 PackageManager 的数据返回，
App 走 `java.util.zip.ZipFile` 直接读文件，完全不经过 PMS。

**典型样本（囧次元，1.0.17）**：
| 类 / 库 | 行为 |
|---|---|
| `com.yy.myuko.shared.data.security.integrity.NativeApkSignatureProbe` | quickjs 脚本调 `q7.a()` 读签名 |
| `libSecureFuck.so`（`com.ty.core.SecureFuck` / `NativeLib`） | `ApkSigner::parseAndGetFirstCertSHA1` / `verifyCurrentApk` 直接解析 APK 签名块 |
| `assets/libliteso.so`（XOR 加密的 native 库，`SecureNativeAssets` 加载） | 疑似独立的完整性校验器 |
| `libzqguard.so`（朱雀） | 反调试 + 可能含签名校验 |
| `com.yy.myuko.feature.deviceinfo.AndroidDeviceProvider` | `getAppSignatureSha256()` → 设备指纹 `asig` 字段上报服务器 |

### 1.2 路径 B：native 层直接 syscall

更极端的情况：native 代码绕开 libc，直接 `svc #0` 发 `openat`。
PLT/GOT hook 完全无效。本模块和下面的补丁方案**都不覆盖**这条（见 §5 边界）。

## 2. 补法：文件系统重定向（已在别的项目验证过）

### 2.1 原理

App 要读自己的 APK，最终一定落到一次文件 open。
**把 `open(base.apk)` 重定向到 `open(origin.apk)`**，它读到的就是原签名 APK
的签名块 —— 真实、完整、任何解析方式都成立（v1 RSA 文件、v2/v3 Signing Block 都在）。

这是 MT 管理器 / ApkSignatureKillerEx 的核心手法，也是 FancyBypass 壳做的事。

### 2.2 组件清单

| 组件 | 位置（建议） | 说明 |
|---|---|---|
| `libusign.so`（arm64/armv7） | `payload/lib/` | XHook 实现的 libc `open/open64/openat/openat64` PLT hook。**已编好，见 §3** |
| `origin.apk` | `assets/nc_sigfix/origin.apk` | 原签名 APK **全量副本**，重定向目标 |
| Java 侧调用 | `SigFixImpl.install()` 尾部 | `System.load(绝对路径)` + `hookApkPath(baseApk, originApk)` |

### 2.3 native 侧接口

```c
// payload/c/usign_hook.c
JNIEXPORT jboolean JNICALL
Java_com_nc_uncheck_SigFix_nativeHookApkPath(JNIEnv *env, jclass clazz,
                                             jstring apkPath, jstring repPath);
```

行为：用 shadowhook 挂 11 个**路径类** libc 函数（`open/open64/__open_2/openat/
openat64/fopen/fopen64/access/faccessat/stat/lstat`），路径与 `apkPath` 完全
相等时改为 `repPath`。成功返回 `JNI_TRUE`（至少 3 个关键函数挂上）。

### 2.4 ⚠️ 三个必须踩准的技术点

#### ① `System.loadLibrary` 在 BootClassLoader 域会失败

`SigFixImpl` 是被 `new DexFile(path)` 加载到 **BootClassLoader 域**的（这是本模块
绕 hidden API 的核心设计，见 `payload/build.sh` 头部注释）。
`System.loadLibrary("usign")` 依赖**调用类的 ClassLoader** 去找 `nativeLibraryDir`，
BootClassLoader 域找不到，静默失败。

**正确做法**（二选一）：
```java
// 方案 1（推荐）：用绝对路径 load，不依赖 ClassLoader
String libDir = ctx.getApplicationInfo().nativeLibraryDir;
System.load(new File(libDir, "libusign.so").getAbsolutePath());

// 方案 2：把 loadLibrary 放到 app 域的 SigFix / SigFixApp 里，
//         再通过反射把 hook 入口交给 SigFixImpl
```

#### ② `origin.apk` 释放时机 & 路径

必须在 `open` hook 生效**之前**把 `origin.apk` 从 assets 拷到可读路径。
`SigFixImpl` 有 `ctx.getCodeCacheDir()` 可用（`attachBaseContext` 之后 Context 已就绪）。

**踩过的坑**（来自 `ApkForge/docs/去签名校验.md §5`）：dex 文件写盘后必须
`setReadOnly()`，否则 `SecurityException: Writable dex file is not allowed`。
`origin.apk` 是普通文件不受此限，但为一致性建议同样处理。

#### ③ hook 必须**早于**目标 App 的任何校验

`SigFixImpl.install()` 目前在 `SigFixApp.attachBaseContext` 里被调用，
早于原 Application 初始化 —— 这个时机对 open hook 是够的。
**但如果目标 App 有 ContentProvider 在 `install()` 之前读 APK**（极罕见，
ContentProvider.onCreate 早于 Application.attachBaseContext），仍然会漏。
遇到这类包只能改挂载点（`android:appComponentFactory`，见 §5）。

### 2.5 ⚠️ shadowhook 必须打的补丁（Android 16 上必需）

`third_party/shadowhook/shadowhook.c` 的 `shadowhook_init()` 里，原代码：

```c
if (__predict_false(0 != sh_linker_init())) GOTO_END(SHADOWHOOK_ERRNO_INIT_LINKER);
```

**已改为降级警告**：

```c
if (0 != sh_linker_init()) {
  SH_LOG_WARN("linker mod init failed, auto-hook-on-dlopen disabled (harmless)");
}
```

理由：`sh_linker_init()` 的唯一作用是 hook linker 的 `soinfo::call_constructors()`，
**仅服务「自动 hook 后续新加载的 so」这一附加特性**。它取不到 linker 私有符号
（`__dl__ZN6soinfo17call_constructorsEv`，符号名随 Android 版本变）时，
原实现会让**整个 init 失败**（errno 12 `Init linker mod failed`）→ 所有 hook 全部失效。

本项目不需要该特性：目标 so（`libSecureFuck.so` / `libliteso.so`）在
Application 初始化前就已加载完毕，`shadowhook_hook_sym_name` 直接就能 hook 到。

**实测环境**：HyperOS V816 / Android 16。不打此补丁必然 errno 12。
`build-native.sh` 里有自检：`grep -q 'PATCHED（USign）'`，漏了会警告。

### 2.6 ⚠️ 静态链接 + --exclude-libs 会让符号自检误报

shadowhook 用 `-Wl,--exclude-libs,ALL` 静态链入 `libusign.so`（避免额外投放
`libshadowhook.so`、避免目标 App 自带同名库冲突）。

**副作用**：shadowhook 的符号会从 `.dynsym`（动态导出）里消失，只剩 `.symtab`（本地）。
所以自检**不能用** `nm -D`（只查动态符号）判断"shadowhook 是否链进去了"，
必须用 `nm`（不加 `-D`）：

```bash
nm libusign_arm64.so | grep -q shadowhook_hook_sym_name   # ✅ 正确
nm -D libusign_arm64.so | grep -q shadowhook_hook_sym_name # ❌ 必然找不到，误报
```

正确的符号面应该是：`.dynsym` 只有 `Java_com_nc_uncheck_SigFix_nativeHookApkPath`，
`.symtab` 里有完整的 shadowhook 内部符号。


### 2.7 已改的 Python 侧（`run.py`）

`run.py` 的改动：

1. 投放 `lib/{arm64-v8a,armeabi-v7a}/libusign.so`（STORED）
2. **origin.apk 不再作为普通条目投放** —— 由 `zip-reuse.py` 做数据复用，
   与整包共享字节（见 §6 待办 2）
3. 组装流程改为：先产出「不含 origin.apk 的中间包」→ 对其 zipalign →
   再 `zip-reuse.build()` 注入 origin.apk → **跳过后续 zipalign**
4. `rebuild_apk()`：`.apk` / `.so` 结尾的新增条目用 `ZIP_STORED`

**Java 侧已完成**：`SigFix.java` 里 `installNativeRedirect()` 在 `boot()` 开头调用，
JNI 入口 `nativeHookApkPath(String,String)Z` 与 C 侧符号名一致。

## 4. 囧次元样本的完整检测面（实测清单）

如果目标是囧次元这类「多层防护」的 App，native 重定向只是其中一环。完整清单：

| 层 | 位置 | 覆盖手段 |
|---|---|---|
| Java 签名比对 | `AndroidRiskEnvProbe.isSigningCertMismatch`（硬编码官方指纹 `de17140c...`） | 恒 return false，或本模块 CREATOR hook |
| 设备指纹上报 | `DeviceProvider.getAppSignatureSha256()` → 字段 `asig`；`getAppSignatureCertDer()` → `acert` | 需要 Java 层伪造（CREATOR hook 覆盖 `getPackageInfo`，但**已验证不够**，因为字段内容来自 `Signature.toByteArray()` 的直接调用，见下） |
| quickjs 风控脚本 | `Hx` 类 k0~k4 桥函数 | 同上 |
| attest 上报 | `AndroidIntegrityInspector` → `SecurityAttestApi` | 同上 |
| **native 解析 APK** | `libSecureFuck.so` / `assets/libliteso.so` | **本补丁（IO 重定向）** |
| **native 探针 → 业务层判决** | `NativeApkSignatureProbe`（quickjs 调 `q7.a()`）→ `nativeSigStatus` → **签到/任务/领奖 API 逐请求判破解** | **apply-mods H 组**（探针脚本常量直改，恒返回官方指纹；重打包下 q7.a() 自校验必然 false，且判定逻辑在混淆 so 内无法干预——改结论出口是唯一可行点）⚠️ 必须与 uncheck 配套：只堵探针不堵 Java 线 = 两条签名线口径矛盾照样判破解（真机实证） |
| **硬件证明** | `AndroidHardwareAttestation`（STRONGBOX，证书链由系统 keystore2 进程从真实安装签名组装） | **apply-mods F 组**（isSupported 恒 false，不发起；证书链本身在系统进程+TEE 内，App 内任何 hook 无法影响——结构性无解，只能不参与） |
| **libc 完整性** | native CRC 校验 libc .text（inline hook 改写 open/fopen 必触发）→ `detail.libcCrc` | **apply-mods G 组**（libcCrc 键永不放入 detail；官方包此键不存在） |
| 服务器裁决 | `SecurityAttestVerdict.action` + `officialUrl` → 播诱饵视频 | ⚠️ **observe ≠ 全放行**：安全层 verdict 只是判决之一，业务 API 另有独立判决链（nativeSigStatus），必须全链对齐官方形态 |

**关键提醒**：囧次元实测发现，即使 CREATOR hook 生效，
`DeviceProvider_androidKt.resolveAppSignatureSha256()` 内部走的是
`PackageManager.getPackageInfo().signingInfo.getApkContentsSigners()[0].toByteArray()`。
CREATOR hook 改了 `signatures` 和 `apkContentsSigners` 的**数组元素**，
理论上覆盖到了。但**实测 atteset 仍被判破解** —— 说明要么某个调用点绕过了 CREATOR
（如直接读 `/proc/self/maps` 找 APK 路径再自己解析），要么 native 层在更早的时机
（ContentProvider / JNI_OnLoad）已完成校验并缓存结果。

> 这一条是**未验证的推断**，下一个接手的人如果走这条路，需要先做 §3③ 的红绿测试
> 确认 native 重定向真的生效，再判断剩余失败属于哪一层。不要假设"加了 so 就完事"。

## 5. 已知边界（写在界面上给用户看的）

| 路径 | 本补丁覆盖 |
|---|---|
| `getPackageInfo().signatures` | ✅ (已有) |
| `signingInfo.apkContentsSigners` / `signingCertificateHistory` | ✅ (已有) |
| `checkSignatures()` / `getPackageArchiveInfo(自身)` | ✅ (已有) |
| App 自读 APK（`ZipFile` / `File` / `mmap`） | ✅ (本补丁) |
| native `open/open64/openat/openat64` | ✅ (本补丁) |
| native **裸 `svc #0`** 直接 syscall | ❌ 需 SVC patch / seccomp（工程量大，暂不做） |
| native **硬编码证书哈希**（如 `memcmp(cert, "\x12\x34...")`） | ❌ 补丁无效，需逆向该 so 逐个 patch |
| `libc` 之外的 IO（如 `std::ifstream` 内部走 `open` → ✅；但若 statically linked libc++ 则漏） | ⚠️ 视情况 |
| 服务器端校验（Play Integrity / 自有 attest） | ❌ 结构性无解 |

末尾 `and-int 0x86` 只认 0x2/0x4/0x80。

**⚠️ 0x4 的类名/包名名单是远程配置下发的**（远程配置里下发一个 JSON 数组，
`checkHookXposed` 遍历 `Class.forName`）。不能"只删命中的那条"，
必须拆掉整个检测方法。

我们已把 `checkHookXposed` 方法体清空：
```smali
.method private static checkHookXposed()Z
    .registers 6     ← ⚠️ 必须保留，删了报
                     #   "A .registers or .locals directive must be present"
    const/4 v0, 0x0
    return v0
.end method
```

**⚠️ 为什么不改 runAll**：runAll 是 14 项检测总出口，改它会把
调试器/root/模拟器/虚拟空间/抓包检测一起废掉，影响面太大。
只改 checkHookXposed 影响面最小、语义最精确。

**⚠️ shadowhook 不在名单里**：
`com.bytedance.shadowhook.*` 不在 checkHookXposed 的 8 个类名里，
也不在 checkHookStack 的 6 个特征串里。当前不触发。
但名单是远程配置下发的，未来可能加。

## 7. 附：本次会话中被验证无效的方案（别重复）

| 方案 | 结果 | 原因 |
|---|---|---|
| 纯 smali 层伪造 `Signature.toByteArray()` 返回值（SigSpoof 类，11 处插桩） | ❌ 被判破解 | 覆盖了 Java 层所有已知调用点，但 native 读 APK 文件不受影响 |
| 只改 `AndroidRiskEnvProbe.isSigningCertMismatch` 恒 false | ❌ | 只是本地比对，服务器 attest 走另外的路径 |
| 本模块 Java 三层 hook（CREATOR + PMS 代理 + signingInfo） | ❌ 单独用 | 同上，native 层未覆盖 |
| 以上 + native IO 重定向 | ✅ **有效** | 2026-11-23 真机验证：囧次元 1.0.17 播放正常 |
| FancyBypass 壳（NP 自研去签名校验） | ✅ 有效 | 它同时做了 PMS hook + IO 重定向（`origin.apk` + Pine hook），与本补丁思路一致 |
| **只挂 open/open64/openat/openat64 的 PLT hook（初版 XHook）** | ❌ | 目标 so 导入的是 `__open_2`/`fopen`，**根本没有 openat**。必须逐个核对 `readelf -r \| grep JUMP_SLOT` |
| **shadowhook 未打 linker mod 补丁** | ❌ | Android 16 上 `sh_linker_init()` 失败 → errno 12 → 所有 hook 失效。见 §2.5 |
| **误判「fopen 内部直调 open，所以 PLT hook 无效」** | 推理错误 | `fopen@LIBC` 在目标 so 的 PLT 跳转槽上，PLT hook 本来就能拦。这个误判导致在 XHook / shadowhook 之间反复横跳 |
| **origin.apk 最小化（只留签名块）** | ❌ 真机崩溃 | IO 重定向会连 ART 的 dex 懒加载一起劫持。见 §6 待办 2 |
| **对数据复用包做 zipalign** | ❌ 体积失效 | zipalign 重写 ZIP，把重叠字节展开成两份（127.96MB → 255.6MB）。先对齐再复用 |
| **用 Python zipfile 读复用包** | 报 BadZipFile | zipfile 有 zip-bomb 防护，拒绝重叠条目。手工按 offset 解析即可 |
| `open64` / `fopen64` 报 `Duplicate shared hook` | 正常 | 它们与 `open`/`fopen` 是同一符号别名，不影响 |
| **用 apksigner 签数据复用包** | ❌ 体积失效 | apksigner 重写 ZIP、展开重叠条目（122MB → 244MB）。**必须用 MT 管理器签名** |
