# 去签名校验（V2）—— 接手文档

> 写给下一个接手「去签名校验」的 AI。
> 本文只讲**当前怎么做的、为什么这么做、踩过哪些坑、还缺什么**。
> 机制细节看 `scripts/uncheck/README.md`；AXML 改写细节见该 README 的 AXML 章节。
>
> 写作时间：2026-11-23｜**2026-11-23 重构：剥离特定包定制，回归通用能力**

---

## 0. 一句话结论

**本模块是通用去签名校验工具，不针对任何特定 App 做定制。**

覆盖两条读取路径：

1. **通过 PackageManager 问签名** → Java 层三层 hook（CREATOR / PMS 代理 / signingInfo）
2. **App / native 自己读 APK 文件** → native 层 IO 重定向（shadowhook inline hook，把 `base.apk` 重定向到 `origin.apk`）

产物未签名，由使用者自行签名（**数据复用包必须用 MT 管理器签名**，见 §6）。

**不在本模块范围内**：广告绕过 / 任务自动化 / 弹窗去除 / 反检测 / native 探针伪造等
业务补丁。那些是针对具体 App 的定制工作，不属于去签名校验的通用能力。

## 0.1 已落地的东西（接手先看这里）

| 组件 | 路径 | 说明 |
|---|---|---|
| native hook 源码 | `scripts/uncheck/payload/c/usign_hook.c` | shadowhook inline hook，重定向 13 个路径类 libc 函数 |
| native 编译脚本 | `scripts/uncheck/payload/c/build-native.sh` | NDK 交叉编译 → `payload/lib/libusign_{arm64,armv7}.so` |
| shadowhook 源码 | `scripts/uncheck/payload/third_party/shadowhook/` | 字节跳动 android-inline-hook，**已打一处补丁**（见 §2.5） |
| 编译产物 | `scripts/uncheck/payload/lib/libusign_{arm64,armv7}.so` | 各约 130KB，shadowhook 静态链入 |
| Java 侧集成 | `payload/src/com/nc/uncheck/SigFix.java` | `installNativeRedirect()` + `nativeHookApkPath()` JNI 声明 |
| Java 载荷 | `payload/src/com/nc/uncheck/{SigFix,SigFixImpl,SigFixApp}.java` | 引导器 / 实现类 / Application 代理 |
| 注入器投放 | `scripts/uncheck/run.py` | 投放 so 到 `lib/{abi}/`；origin.apk 由 zip-reuse 复用打包 |
| 构建入口 | `payload/build.sh` | 已接入 native 编译（无 NDK 时自动跳过并警告） |
| 数据复用打包 | `scripts/uncheck/zip-reuse.py` | 让 origin.apk 与整包共享字节（体积不翻倍） |

**★ 签名工具必须用 MT 管理器**：apksigner 会重写 ZIP 把重叠条目展开，
122MB 撑回 244MB。MT 实测保持复用（128MB）。见 §6 待办。

**真机日志判据**（`adb logcat | grep USign`）：
```
USign: hookApkPath: apk=/data/app/.../base.apk
USign: hookApkPath: rep=/data/user/0/.../code_cache/sigfix-origin.apk
USign: shadowhook init ok (vshadowhook version 2.0.1)
USign: hooked: open / __open_2 / fopen / access / stat ...
USign: hook 汇总: 5/5 关键函数挂上
USign: native hook install OK
```
看到 `install OK` 才算 native 层真的生效。**注意**：`open64` / `fopen64` 会报
`hook fail (16 Duplicate shared hook)` —— 它们与 `open` / `fopen` 是同一符号别名，
已挂上，**不是失败**。

## 0.2 2026-11-24 大更新：加固侧已能检测本工具

**本节是最新状态，与下文 §1~§7 的历史记录冲突时以本节为准。**

### 发生了什么

加固侧 `sig_check.c` 升级为「**6 路取证书 + 交叉比对**」后，
本工具的重定向会被识破：

```
【数据】多路证书采集表头
| open      size=5077060    fp=d82e48da…  <== 不一致     ← 本工具的诱饵
| openat    size=10189766   fp=93622a73…                 ← 真实 APK
| openat64  size=10189766   fp=93622a73…
| syscall   size=10189766   fp=93622a73…
| svc       size=10189766   fp=93622a73…
| sysfd     size=10189766   fp=93622a73…
ok=6/6 mismatch=1
【失败】多路证书指纹不一致(疑似 APK 读取被劫持) → fail-closed
```

### 关键判据不是证书，是**文件大小**

日志里 `open` 那路 `size=5077060`（= `origin.apk`），其余 5 路
`size=10189766`（= 真实 `base.apk`）。**体积差异是最直白的破绽**——
即便诱饵包用同样的官方证书签，大小也对不上。

### 本工具已做的补强（`usign_hook.c`）

hook 从 11 个扩到 **17 个**：补了 `openat` / `openat64` / **`__openat_2`** /
`openat2` / `readlinkat` / `statx`。

> ⚠️ **`__openat_2` 是重点**：C 里写 `openat(AT_FDCWD, ...)` 会被
> `_FORTIFY_SOURCE` 编成 `__openat_2`，只挂 `openat` 等于没挂。
> 这是从加固侧 `libnc.so` 的导入表实测到的。

补强后：**6 路中拦住 3 路**（open / openat / openat64）。

### 拦不住的 3 路（技术边界，不是没做）

| 路线 | 为什么拦不住 |
|---|---|
| 内联 `svc #0` | 指令在调用方函数体内，无符号、无独立函数，inline hook 无从下手 |
| `syscall()` 的 inline 展开 | 同上 |
| `/proc/self/fd/N` 复用系统已开 fd | 压根不发起 open |

要破这 3 路只能改加密段 `.ncx` 里的指令 —— 针对性逆向，不再是通用工具。

### 所以本工具的现状（如实）

| 场景 | 结果 |
|---|---|
| 目标 App 只用 `PackageManager` 查签名 | ✅ 有效（Java 层 hook） |
| 目标 App 自读 APK，**无**多路交叉校验 | ✅ 有效（重定向成功） |
| 目标是**我们自己的加固包**（多路校验） | ❌ 被检测并 fail-closed |
| 目标是第三方 App，但其自研校验搞了多路 | ⚠️ 未实测，原理上同我们自己的 |

**结论：本工具的能力没有变弱，是加固侧多了一道检测。**

### 中间包（调试用）

要验证「加固有效但去校验被拦」，需要一个**只加固、未去校验**的包：
用 `trigger_build.py <原包> --sigcheck --no-sign` 产出，或从加固流水线
的 `protected_unsigned.apk` 取，再用 `熠小夕.keystore` 签。

## 1. 漏洞在哪：两条未覆盖的路径

### 1.1 路径 A：App 自读 APK 文件

App 不调 PackageManager，直接：

```java
// 读自己 APK 里的 META-INF/*.RSA（v1 签名证书）
ZipFile zf = new ZipFile(getPackageResourcePath());
// 或读 v2/v3 签名块（APK Signing Block，二进制块，在 ZIP central directory 之前）
```

**本模块为什么需要 native 层**：Java 层 hook 的是 PackageManager 的数据返回，
App 走 `java.util.zip.ZipFile` 直接读文件，完全不经过 PMS。

### 1.2 路径 B：native 层直接 syscall

更极端的情况：native 代码绕开 libc，直接 `svc #0` 发 `openat`。
PLT/GOT hook 完全无效。本模块和下面的补丁方案**都不覆盖**这条（见 §5 边界）。

## 2. 补法：文件系统重定向

### 2.1 原理

App 要读自己的 APK，最终一定落到一次文件 open。
**把 `open(base.apk)` 重定向到 `open(origin.apk)`**，它读到的就是原签名 APK
的签名块 —— 真实、完整、任何解析方式都成立（v1 RSA 文件、v2/v3 Signing Block 都在）。

这是 MT 管理器 / ApkSignatureKillerEx 的核心手法，也是 FancyBypass 壳做的事。

### 2.2 组件清单

| 组件 | 位置 | 说明 |
|---|---|---|
| `libusign.so`（arm64/armv7） | `payload/lib/` | shadowhook inline hook 的 libc 路径类函数 |
| `origin.apk` | `assets/nc_sigfix/origin.apk` | 原签名 APK **全量副本**，重定向目标 |
| Java 侧调用 | `SigFix.installNativeRedirect()` | `System.load(绝对路径)` + `nativeHookApkPath(baseApk, originApk)` |

### 2.3 native 侧接口

```c
// payload/c/usign_hook.c
JNIEXPORT jboolean JNICALL
Java_com_nc_uncheck_SigFix_nativeHookApkPath(JNIEnv *env, jclass clazz,
                                             jstring apkPath, jstring repPath);
```

行为：用 shadowhook 挂 13 个**路径类** libc 函数（`open/open64/__open_2/openat/
openat64/fopen/fopen64/access/faccessat/stat/lstat/readlink/opendir`），路径与
`apkPath` 完全相等时改为 `repPath`。成功返回 `JNI_TRUE`（至少 3 个关键函数挂上）。

**为什么覆盖全集而不是按目标裁剪**：不同目标 so 的导入表各不相同
（`readelf -r | grep JUMP_SLOT`），有的用 `__open_2`/`fopen`、有的用 `open`、
有的根本没有 `openat`。挂全集靠 `is_target_apk` 精确匹配路径，不匹配立即透传，
开销可忽略。逐包核对导入表只在**排查某条路径为何没拦住**时才需要。

### 2.4 ⚠️ 三个必须踩准的技术点

#### ① `System.loadLibrary` 在 BootClassLoader 域会失败

`SigFixImpl` 是被 `new DexFile(path)` 加载到 **BootClassLoader 域**的（这是本模块
绕 hidden API 的核心设计，见 `payload/build.sh` 头部注释）。
`System.loadLibrary("usign")` 依赖**调用类的 ClassLoader** 去找 `nativeLibraryDir`，
BootClassLoader 域找不到，静默失败。

**正确做法**（二选一）：
```java
// 方案 1（推荐）：用绝对路径 load，不依赖 ClassLoader
String libDir = ctx.getApplicationInfo().nativeLibraryDir;
System.load(new File(libDir, "libusign.so").getAbsolutePath());

// 方案 2：把 loadLibrary 放到 app 域的 SigFix / SigFixApp 里，
//         再通过反射把 hook 入口交给 SigFixImpl
```

#### ② `origin.apk` 释放时机 & 路径

必须在 `open` hook 生效**之前**把 `origin.apk` 从 assets 拷到可读路径。
`SigFix` 有 `ctx.getCodeCacheDir()` 可用（`attachBaseContext` 之后 Context 已就绪）。

**踩过的坑**：dex 文件写盘后必须 `setReadOnly()`，否则
`SecurityException: Writable dex file is not allowed`。
`origin.apk` 是普通文件不受此限，但为一致性建议同样处理。

#### ③ hook 必须**早于**目标 App 的任何校验

`SigFix.install()` 在 `SigFixApp.attachBaseContext` 里被调用，
早于原 Application 初始化 —— 这个时机对 open hook 是够的。
**但如果目标 App 有 ContentProvider 在 `install()` 之前读 APK**（极罕见，
ContentProvider.onCreate 早于 Application.attachBaseContext），仍然会漏。
遇到这类包只能改挂载点（`android:appComponentFactory`，见 §5）。

### 2.5 ⚠️ shadowhook 必须打的补丁（Android 16 上必需）

`third_party/shadowhook/shadowhook.c` 的 `shadowhook_init()` 里，原代码：

```c
if (__predict_false(0 != sh_linker_init())) GOTO_END(SHADOWHOOK_ERRNO_INIT_LINKER);
```

**已改为降级警告**：

```c
if (0 != sh_linker_init()) {
  SH_LOG_WARN("linker mod init failed, auto-hook-on-dlopen disabled (harmless)");
}
```

理由：`sh_linker_init()` 的唯一作用是 hook linker 的 `soinfo::call_constructors()`，
**仅服务「自动 hook 后续新加载的 so」这一附加特性**。它取不到 linker 私有符号
（`__dl__ZN6soinfo17call_constructorsEv`，符号名随 Android 版本变）时，
原实现会让**整个 init 失败**（errno 12 `Init linker mod failed`）→ 所有 hook 全部失效。

本项目不需要该特性：目标 so 在 Application 初始化前就已加载完毕，
`shadowhook_hook_sym_name` 直接就能 hook 到。

**实测环境**：HyperOS V816 / Android 16。不打此补丁必然 errno 12。
`build-native.sh` 里有自检：`grep -q 'PATCHED（USign）'`，漏了会警告。

### 2.6 ⚠️ 静态链接 + --exclude-libs 会让符号自检误报

shadowhook 用 `-Wl,--exclude-libs,ALL` 静态链入 `libusign.so`（避免额外投放
`libshadowhook.so`、避免目标 App 自带同名库冲突）。

**副作用**：shadowhook 的符号会从 `.dynsym`（动态导出）里消失，只剩 `.symtab`（本地）。
所以自检**不能用** `nm -D`（只查动态符号）判断"shadowhook 是否链进去了"，
必须用 `nm`（不加 `-D`）：

```bash
nm libusign_arm64.so | grep -q shadowhook_hook_sym_name   # ✅ 正确
nm -D libusign_arm64.so | grep -q shadowhook_hook_sym_name # ❌ 必然找不到，误报
```

正确的符号面应该是：`.dynsym` 只有 `Java_com_nc_uncheck_SigFix_nativeHookApkPath`，
`.symtab` 里有完整的 shadowhook 内部符号。

### 2.7 Python 侧（`run.py`）

`run.py` 的流程：

1. 投放 `lib/{arm64-v8a,armeabi-v7a}/libusign.so`（STORED）
2. **origin.apk 不作为普通条目投放** —— 由 `zip-reuse.py` 做数据复用，
   与整包共享字节（见 §6 待办）
3. 组装流程：先产出「不含 origin.apk 的中间包」→ 对其 zipalign →
   再 `zip-reuse.build()` 注入 origin.apk → **跳过后续 zipalign**
4. `rebuild_apk()`：`.apk` / `.so` 结尾的新增条目用 `ZIP_STORED`

**Java 侧**：`SigFix.java` 里 `installNativeRedirect()` 在 `boot()` 开头调用，
JNI 入口 `nativeHookApkPath(String,String)Z` 与 C 侧符号名一致。

## 3. 补完之后必须验证的四层

```
① Java 层是否生效        adb logcat | grep SigFixImpl
   ✓ PackageInfo.CREATOR 替换成功
   ✓ ActivityThread.sPackageManager 替换成功

② native 层是否加载      adb logcat | grep USign
   必须看到 "hook 汇总: 5/5 关键函数挂上" + "native hook install OK"
   （open64/fopen64 报 Duplicate shared hook 属正常，见 §0.1）

③ 红绿测试（最关键）     造一个自读 APK 的探针
   在 demo App 里写：
     new ZipFile(getPackageResourcePath()) → 读 META-INF/*.RSA → 算 SHA-256
   对比：装原签名包 vs 装 usign 处理过的包，哈希必须相同
   ⚠️ 这一项仍然没做（见 §6 待办）

④ 真实目标           目标 App 是否仍检测到重签名
```

**只看 ①② 不够**（它们只证明 hook 装上了，不证明拦住了）。③ 是唯一能独立
证明"native 重定向真的生效"的测试，目前缺失 —— 见 §6。

## 4. 通用检测面清单

不同 App 的签名校验实现差异很大，以下是**按读取途径**分类的通用清单
（不含任何特定 App 的类名/字段名）：

| 读取途径 | 覆盖手段 | 是否本模块覆盖 |
|---|---|---|
| Java `getPackageInfo().signatures` | CREATOR hook | ✅ |
| Java `signingInfo.getApkContentsSigners()` | CREATOR hook + signingInfo patch | ✅ |
| Java `getSigningCertificateHistory()` | 同上（pastSigningCertificates 也要改） | ✅ |
| `checkSignatures()` / `getPackageArchiveInfo(自身)` | PMS 代理 | ✅ |
| App 自读 APK（`ZipFile` / `FileInputStream` / mmap） | native IO 重定向 | ✅ |
| native so 读 APK（`open`/`fopen`/`__open_2`/`access`/`stat`） | native IO 重定向 | ✅ |
| native 裸 `svc #0` 直接 syscall | seccomp / SVC patch | ❌ 工程量太大，暂不做 |
| native 硬编码证书哈希（`memcmp` 常量） | 逆向该 so 逐个 patch | ❌ 结构性需逆向 |
| 硬件证明（STRONGBOX Key Attestation） | — | ❌ 证书链由系统 keystore2 进程组装，App 内 hook 无法伪造 |
| 上报服务端裁决 / Play Integrity | — | ❌ 结构性无解 |
| 服务器业务层判决（如签到/领奖 API） | — | ❌ 不属于去签名校验；需按目标包单独处理 |

后几类是**结构性无解或超出范围**，不是「还没做」。工具不会假装能处理它们。

> ⚠️ **平台层与业务层是两层独立判决**：即使安全层 verdict 放行，
> 业务 API 仍可能按自己的规则判「破解版」。后者属于目标 App 的业务逻辑，
> 不在通用去签名校验的能力边界内。

## 5. 已知边界

| 路径 | 本模块覆盖 |
|---|---|
| `getPackageInfo().signatures` | ✅ |
| `signingInfo.apkContentsSigners` / `signingCertificateHistory` | ✅ |
| `checkSignatures()` / `getPackageArchiveInfo(自身)` | ✅ |
| App 自读 APK（`ZipFile` / `File` / `mmap`） | ✅ |
| native `open/open64/openat/openat64/fopen/access/stat/lstat/readlink/opendir` | ✅ |
| native **裸 `svc #0`** 直接 syscall | ❌ 需 SVC patch / seccomp（工程量大，暂不做） |
| native **硬编码证书哈希**（如 `memcmp(cert, "\x12\x34...")`） | ❌ 补丁无效，需逆向该 so 逐个 patch |
| `libc` 之外的 IO（如 `std::ifstream` 内部走 `open` → ✅；但若 statically linked libc++ 则漏） | ⚠️ 视情况 |
| 服务器端校验（Play Integrity / 自有 attest） | ❌ 结构性无解 |

## 7. 附：被验证无效的方案（别重复）

| 方案 | 结果 | 原因 |
|---|---|---|
| 纯 smali 层伪造 `Signature.toByteArray()` 返回值 | ❌ 被判破解 | 覆盖了 Java 层所有已知调用点，但 native 读 APK 文件不受影响 |
| 只改本地签名比对（如某 `isSigningCertMismatch` 恒 false） | ❌ | 只是本地比对，服务器 attest 走另外的路径 |
| 本模块 Java 三层 hook（CREATOR + PMS 代理 + signingInfo） | ❌ 单独用 | 同上，native 层未覆盖 |
| 以上 + native IO 重定向 | ✅ **有效** | Java + native 全链覆盖 |
| FancyBypass 壳（NP 自研去签名校验） | ✅ 有效 | 它同时做了 PMS hook + IO 重定向（`origin.apk` + Pine hook），与本补丁思路一致 |
| **只挂 open/open64/openat/openat64 的 PLT hook（初版 XHook）** | ❌ | 目标 so 导入的是 `__open_2`/`fopen`，**根本没有 openat**。必须逐个核对 `readelf -r \| grep JUMP_SLOT` |
| **shadowhook 未打 linker mod 补丁** | ❌ | Android 16 上 `sh_linker_init()` 失败 → errno 12 → 所有 hook 失效。见 §2.5 |
| **误判「fopen 内部直调 open，所以 PLT hook 无效」** | 推理错误 | `fopen@LIBC` 在目标 so 的 PLT 跳转槽上，PLT hook 本来就能拦。这个误判导致在 XHook / shadowhook 之间反复横跳 |
| **origin.apk 最小化（只留签名块）** | ❌ 真机崩溃 | IO 重定向会连 ART 的 dex 懒加载一起劫持。见 §6 待办 2 |
| **对数据复用包做 zipalign** | ❌ 体积失效 | zipalign 重写 ZIP，把重叠字节展开成两份（127.96MB → 255.6MB）。先对齐再复用 |
