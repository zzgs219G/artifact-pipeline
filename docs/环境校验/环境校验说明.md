# 环境校验（envcheck）— 完整说明

> **这份文档回答三个问题**：它检测什么、它怎么检测、它到底挡得住什么。
>
> 代码：`scripts/guard/src/env_check.c`（1573 行）
> 开关：`--envcheck`
> 建立日期：2026-11-08（真机验证后重写）

---

## 0. 一句话

**在 App 运行期持续检查「有没有人对我的进程动手脚」，发现就杀。**

不检测「有没有人读过我的文件」—— 那件事纯客户端做不到，见 §6。

## 1. 13 个探针，分两类

### 1.1 一览表

| # | 探针 | 抓什么 | 构造期 | watchdog |
|---|---|---|---|---|
| 1 | `frida_port_probe` | 本机 27042/27043 有监听 | ✅ | ✅ |
| 2 | `frida_maps_probe` | `/proc/self/maps` 里的 Frida 特征串 | ✅ | ✅ |
| 3 | `frida_tcp_table_probe` | `/proc/net/tcp` 的 LISTEN 解析 | ✅ | ✅ |
| 4 | `frida_thread_probe` | `/proc/self/task/*/comm` 线程名 | ✅ | ✅ |
| 5 | `frida_unix_probe` | `/proc/net/unix` 里的 frida/linjector | ✅ | ✅ |
| 6 | `xposed_maps_probe` | maps 里的 Xposed/LSPosed/Riru | ✅ | ✅ |
| 7 | `xposed_file_probe` | LSPosed/zygisk/riru 的文件路径 | ✅ | ✅ |
| 8 | `tracer_probe` | `/proc/self/status` 的 `TracerPid` | ✅ | ✅ |
| 9 | **`tracer_all_threads_probe`** | **全线程 `task/<tid>/status` 的 TracerPid** | ✅ | ✅ |
| 10 | **`stat_state_probe`** | **`/proc/self/stat` 的 state 字段（T/t）** | ✅ | ✅ |
| 11 | `libc_hook_probe` | 8 个 libc 符号序言被改（≥2 才判） | ❌ | ✅ |
| 12 | `libc_text_crc_probe` | libc `.text` 内存 vs 磁盘 CRC | ✅ | 每 5 轮 |
| 13 | `self_text_crc_probe` | 本 so `.text` 内存 vs 磁盘 CRC | ✅ | 每 5 轮 |

**加粗的 9、10 是 2026-11-08 新增**（对比 sentry / XopProtector / NativeShield 后确认的缺口）。

`libc_hook_probe` 只在 watchdog 跑：它读代码段字节，重操作，且单次结果意义有限。

### 1.2 两个执行时机

```
constructor(50) ncg_boot_init     ← nox 解锁
      ↓
env_check_entry()  (constructor)
      ├→ ncguard_unlock()
      ├→ anti_debug_preempt()     PTRACE_TRACEME + PR_SET_DUMPABLE(0)
      ├→ env_check_run()          12 个探针各跑一次
      └→ env_watchdog_start()     常驻线程，每 5s 一轮
```

**为什么两个时机都要**：
- 构造期：App 一启动就查，攻击者没时间准备
- watchdog：补「启动后才挂载 Frida」的窗口

## 2. 段归属：13 个探针全在 `.ncx` 密文段

```c
__attribute__((section(NC_SEC_CODE), retain))
static int frida_port_probe(void) { ... }
```

`NC_SEC_CODE` = `.ncx`，**未解锁时是密文**。

| 好处 | 说明 |
|---|---|
| 静态不可见 | `strings` / `objdump` 扫不到探针逻辑 |
| 自动被 CRC 覆盖 | `ncguard_code_check` 每 25s 校验 `.ncx` 明文，探针被 patch → CRC 变 → 自杀 |

**调用方（`env_check_entry` / `env_watchdog` / `env_fail`）留在 `.text` 明文** ——
它们是 `ncguard_unlock()` 的使用者，标进 `.ncx` 就是「开锁器锁进箱子」= 死锁。

⚠️ **`env_delayed_kill`（处置函数）也在 `.ncx`**，理由是同样的「藏起来」：
静态视角看不到有这个东西存在。

## 3. 字符串密文化（LSGS）

所有特征串走 `/*LSGS:NAME|明文*/` 标记 → 构建期加密 → 运行期 `lsg_s()` 解码。

```c
/*LSGS:PATH_STATUS|/proc/self/status*/
/*LSGS:THR_FRIDA|frida*/
```

**实测验证**（`test-lsgs-strings.sh`，12 项全绿）：

```
✅ 密文表 volatile 在位（防 -O2 SIMD 明文折叠）
✅ lsg_decode noinline 在位（防内联折叠）
✅ 26 条 LSGS 逐字节对拍正确
✅ 明文零泄漏（26 个特征串在 so 里全部零命中）
```

⚠️ **踩过的坑**：初版 `-O2` 把 `lsg_decode` 对常量 id 的 XOR 循环向量化，
前 8 字节明文以 SIMD 向量常量落进 `.rodata`，`strings` 仍可扫出。
修法 = 密文表 `volatile` + `lsg_decode` `noinline`。

## 4. 处置：检出后怎么死

```
env_fail()
  └→ pthread_create(env_delayed_kill)

env_delayed_kill()          ← 在 .ncx 密文段
  ├→ 延时 1~3s（随机）
  ├→ 延时堆破坏 8~23 轮（malloc/free + 随机 usleep）
  ├→ safe_syscall(__NR_tgkill, pid, tid, SIGABRT)
  └→ 兜底：env_raw_die() —— 内联 svc 直投，不经 PLT
```

**为什么这么设计**：

| 手段 | 目的 |
|---|---|
| 延时 1~3s | 攻击者不知道是哪一步触发的 |
| 堆破坏 | dump 到的内存不可用 |
| 内联 `svc` | `abort@plt` / `syscall@plt` 改 4 字节即废，svc 没有 PLT 桩 |
| 起线程 | kill 逻辑不在主线程栈上，难回溯 |

⚠️ **`abort@plt` 仍存在 376 处**（dex2c 产物 + libc++ 的），但**不在我们的 kill 链上**。
真机验证：崩溃信号是 `SIGABRT (SI_TKILL)` —— `tgkill` 发的，不是 `abort()`。

## 6. 它挡不住什么（重要，别高估）

| 攻击方式 | 能挡吗 | 为什么 |
|---|---|---|
| `strings` 扫特征串 | ✅ | LSGS 密文化 |
| Frida 默认注入 | ✅ | 端口/maps/线程名/unix socket 四路 |
| 调试器 attach | ✅ | TracerPid + 全线程 + stat state |
| Xposed/LSPosed | ✅ | maps + 文件痕迹 |
| libc inline hook | ✅ | 序言打分 + `.text` CRC |
| **离线分析（Unicorn / IDA）** | ❌ | **进程没启动，探针没机会跑** |
| **Java/ART 层 hook** | ❌ | **完全无覆盖** |
| **`Base64.decode` 等系统 API hook** | ❌ | 同上 |
| **改 so 文件后重打包** | ⚠️ | 靠签名校验 + 证书绑定，不靠探针 |

### 6.1 为什么离线分析挡不住

```
Unicorn 流程：
  从 APK 抠出 libnc.so  →  离线加载到模拟器  →  模拟 ARM64 执行
  ↑ 全程 App 没启动，探针一行没跑
```

**这是设计边界，不是缺陷。** 文档从 2026-10 就写明：

> 防的是 `strings` 一眼可见与静态特征扫描，**不是有心人的定向逆向**。

### 6.2 Java/ART 层是真实缺口

`AGENTS.md` 已登记：

> **挡不住**：PLT/GOT hook（不改 `.ncx` 字节）、**ART 层 hook**、
> 以及把本校验函数自身 patch 成恒真。

**具体到字符串加密**：

| hook 点 | 现状 |
|---|---|
| Java `StrDec.dn` | ✅ 挡住（勾 `--dex2c-stub` 后已 native 化，dex 里无实现） |
| `nm -D` 找符号 | ✅ 挡住（动态注册，不在 `.dynsym`） |
| 扫 `.text` 找 native 函数 | ❌ 挡不住 |
| **`android.util.Base64.decode`** | ❌ **挡不住，最省力的一条路** |

## 7. 单独勾 `--envcheck` 时的行为

### 7.1 已知的两个 bug（2026-11-08 修复）

#### Bug 1：so 编了但没人加载

**症状**：构建全绿、`libnc.so` 在包里、系统 logcat 都能看到
`nativeLibs1/1:: [..., libnc.so]`，但过滤 `nc:` **完全为空**。

**根因**：`protect.sh` 的 `loadLibrary` 插桩只有两个分支：

```bash
if   WANT_TRANSPILE  -> mark-native.py
elif WANT_SIGCHECK   -> inject-loadlib.py
fi
```

`--envcheck` 单独勾选时两个都不进 → 没有任何 Java 代码调
`System.loadLibrary("nc")` → constructor 从不执行。

**修法**：条件加 `|| $WANT_ENVCHECK -eq 1`。

#### Bug 2：装上去必 SIGSEGV

**症状**：

```
F libc: Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x0
F DEBUG: backtrace:
F DEBUG:   #00 pc 0000000000000000  <unknown>
F DEBUG:   #01 pc 000000000002d484  libnc.so
```

反汇编 `0x2d484`：`bl <nc_heartbeat_arm_constructor@plt>`

**根因**：`nc_heartbeat_arm_constructor` 由 `nc_link.c` 提供，
只勾 envcheck 时不在工程里。`env_check.c` 声明为 `weak`，
但 **`weak` 只保证编译通过，不保证运行安全**：

| 写法 | 符号缺失时 |
|---|---|
| `if (fn) fn();` | ✅ 取地址得 NULL，跳过 |
| `fn();` 裸调用 | ❌ PLT 桩指向地址 0 → SIGSEGV |

**修法**：两处补 NULL 检查。

### 7.2 依赖关系

```
--envcheck 单独勾选
  ├→ 需要 nox 设施（解锁 .ncx）          ✅ 自动带上
  ├→ 需要 nc_link.c？                     ❌ 不需要（weak，缺失即跳过）
  ├→ 需要 sig_check.c？                   ❌ 不需要
  └→ 生成 .ncxr 段？                      ❌ 不生成（那是签名表）
```

**实测产物**（只勾 envcheck，arm64）：

```
.nc x    5,356 B   熵 7.962   ← 12 个探针
.nc xh   3,104 B   熵 7.940   ← 开锁程序
.ncks      112 B
.nck        96 B
无 .ncxr
libnc.so  365,888 B
```

⚠️ **365 KB 里只有 5 KB 是探针**，剩下 330 KB 是 nox 的解锁设施 + VMP 解释器
（`nc_guard_crypto.o` 406 KB，被 VMP 虚拟化后膨胀）。

## 8. 验证方法（无 root 环境）

| 探针 | 怎么触发 | 难度 |
|---|---|---|
| `frida_port_probe` | Termux 监听 27042 | ⭐ 已实测 |
| `frida_tcp_table_probe` | 同上（同时命中 `/proc/net/tcp`） | ⭐ |
| `stat_state_probe` | 需进程被 stop，较难 | ⭐⭐⭐ |
| `tracer_probe` | 需调试器 attach，无 root 做不到 | ⭐⭐⭐⭐ |
| `xposed_file_probe` | 需 `/data/adb/`，无 root 做不到 | ⭐⭐⭐⭐⭐ |
| `libc_hook_probe` | 需真 inline hook | ⭐⭐⭐⭐⭐ |

**没有 root 时，`frida_port_probe` 是唯一低成本入口** —— 而它恰好也是最有效的
（Frida 默认就开 27042）。

## 9. 维护纪律

1. **新增探针必须标 `__attribute__((section(NC_SEC_CODE), retain))`**
2. **属性与函数之间不能夹 `#define`** —— 属性会落到 `#define` 上，肉眼读错
   （`libc_hook_probe` 曾这样，预处理后确认才发现没事）
3. **新增特征串必须走 `/*LSGS:NAME|...*/`**，否则 `strings` 能扫到
4. **注释里禁止书写 LSGS 标记的字面形态** —— 嵌套注释会提前终结注释块，编译炸
5. **改动后必须跑**：
   - `test-lsgs-strings.sh`（特征串密文化）
   - `test-mem-readable.sh`（跨映射判定）
   - `test-javacheck.sh`（心跳语义）
6. **不要写死探针数量** —— 文案写「全部探测干净」而不是「六项探测干净」
   （后者已漂移过一次）
7. **weak 符号调用必须判空** —— 见 §7.1 Bug 2
