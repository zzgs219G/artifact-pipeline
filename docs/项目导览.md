## 一句话介绍

给 APK 做加固的 GitHub Actions 项目：你给它一个 APK 和几个勾选，它在云端把 APK
解包 → 加固（签名校验 / 核心逻辑转 C / 字符串加密 / 防对比混淆）→ 回编 → 吐回
一个未签名 APK，你拿回去自己重签即可。

## 全景图（数据怎么流）

```
你的 APK
   │
   ▼
.github/workflows/protect-modules.yml   ← 唯一入口：网页上勾选 + 填 APK 链接
   │
   ▼
scripts/pipelines/protect.sh            ← 唯一总控：固定顺序执行，勾几个跑几个
   │
   ├─ STEP1  提证书指纹 ────────────────► guard/hash/make-sig-hash.sh
   ├─ STEP2  核心方法转 C（dex2c）───► tools/Dex2C/ 里的 dcc.py（唯一引擎）
   ├─ STEP3  把 C 代码组装成 NDK 工程
   ├─ STEP4  编译出 libnc.so
   │
   ├─ STEP5  解包 APK 成 smali，然后按顺序做三件事：
   │     ① repack/mark-native.py        把转 C 的方法改成 native 壳
   │     ② string-enc/encrypt-strings.py 字符串加密
   │     ③ anti-diff/anti-diff.py       防对比混淆（最后做，盖全包噪声）
   │
   └─ STEP6  回编 APK（lib/lib-repack.sh）→ 产出 unsigned.apk（此时尚未对齐）
             │
             ├─ 不勾加壳：zipalign(unsigned.apk) → 最终产物
             │
             ├─ 勾加壳：zipalign(unsigned.apk) → aligned.apk → packer/packer.sh
             │            → packer 产物**就是**最终产物（不再二次 zipalign）
             │
             └─ libnc.so 里装着：签名校验 + 环境检测（App 运行时自检，不对就闪退）
```

**执行顺序是写死的**：`sigcheck → dex2c → stringenc → anti-diff → envcheck → packer`。
你勾选的顺序和数量只决定"哪些步骤跑"，不决定先后。加壳(packer)永远排最后；
环境检测(envcheck)实际在 NDK 组装阶段并进 `libnc.so`，排在列表末位只是展示顺序。

### nox 上游仓库是什么（2026-11-05 补：此前 4 份主文档都只写"zip 的来源"）

`tools/nox.zip` 不是"某个第三方库"，而是**我们自己的另一个仓库**：
`zzgs219G/nox`，与本仓库**同级**（`../nox`）。它是 so 段加密设施的**唯一源码真相源**。

> 📖 **完整说明见 [`docs/上游仓库-nox.md`](./上游仓库-nox.md)**（结构 / CLI / 自测 /
> 两种分发形态 / 加密契约 / 改法与发版流程）。
> 下面只留最需要知道的几条。

```
../nox/                          ← 源码真相源（开发机常态，两仓库并列）
  nox                            CLI：protect / build / test 三个子命令
  test.sh                        自测 18 项，零参数即可跑（用包内 fixture）
  AGENTS.md                      上游自己的硬约束（冻结契约/加密纪律/发版纪律）
  scripts/so-guard/*.c/*.h/*.py  设施本体
  scripts/make-zip-lib.sh        打静态库形态（生产用，需 ANDROID_NDK_HOME）
  scripts/make-zip-src.sh        打源码形态（给要改代码的人）

tools/nox.zip → tools/nox/       ← 生产分发形态（静态库，无 .c）
```

**四条必须知道的**：

1. **改设施 = 去 `../nox` 改**。本仓库没有 `nc_guard_*.c`，找也找不到。
   改完跑 `../nox/test.sh`（18 项）→ `make-zip-lib.sh` → 换 zip + **删
   `tools/nox/`**（不删会静默用旧解压产物）。
2. **回归测试只认源码**（`ensure_nox_src` 读 `../nox/scripts/so-guard`）。
   只克隆本仓库的人**跑不了 `test-so-lock.sh`**，必须先 clone nox ——
   这是刻意取舍，2026-11 删掉了 `nox-src.zip` 兜底。
3. **加密契约在 `nc_guard_layout.h`**，本仓库的 `nc_link.c` / `env_check.c` /
   `sig_check.c` 都 include 它。改它必然波及本仓库。
4. **生产包是静态库形态**：`.a` 里有 5 个成员（含 `nc_guard_jni.o`），
   链接**必须** `-Wl,--whole-archive`，否则加密段 5 个塌成 1 个。

<!-- 下面是 2026-10-30 独立化时写的原说明，保留作为背景 -->

`scripts/so-guard/` 已整体迁到**上游仓库 `zzgs219G/nox`**，本仓库不再保存源码副本：

```
../nox/scripts/so-guard/        ← 源码唯一真相源（开发机常态，两仓库并列）
```

  24 处副本之间互相矛盾）
- 回归测试 `test-so-lock.sh` 需要源码形态，会读 `../nox/scripts/so-guard`，
  **没有该仓库会直接 exit 1**（2026-11 删掉了 `nox-src.zip` 兜底）

### protect.sh 调用了谁（总控的"手臂"）

> 顺序与代码对齐（2026-11-05 按 `protect.sh` 逐 STEP 复核）。注意 STEP 编号与
> 代码里的 `log_step N 6` 一致，**envcheck 不占独立 STEP**——它在 STEP3
> 组装 NDK 工程时并入 `libnc.so`。

| protect.sh 的步骤 | 调用 | 干什么 |
|---|---|---|
| source | `lib/common.sh` `lib-repack.sh` `lib-ndk.sh` | 三个公共库全部吃进总控 |
| 入口 | `require_file` / `repack_require_tools` / `ensure_nox` | 环境假设开工前 fail-fast；nox 解压一次，22 处引用共用 |
| STEP2 前置轮（仅 `--dex2c-stub`） | `string-enc/encrypt-strings.py` + `repack_unpack/build` | 桩必须先进 APK 才能被 dex2c 转译（联动手术） |
| STEP1 | `guard/hash/make-sig-hash.sh` | → 内部再调 `extract-cert-fp.py`，产 `sig_hash.h` + `sig_guard2.h` |
| STEP2 | `tools/Dex2C/dcc.py`（`--no-build --project-archive --dynamic-register`） | filter 由 `filter/` 下两个脚本提前生成 |
| STEP3 | `guard/log/make-sig-log.py` | 扫 `sig_check.c`/`env_check.c`/`sig_guard2.c` 的注释生成密文头文件 |
| STEP3 | `lib-ndk.sh: ndk_write_mk` | 唯一 mk 模板；静态库形态时写 `--whole-archive` 段 |
| STEP3 编译前 | `$GUARD_SRC/so_section_mark.py --rule dex2c-jni`（上游 nox，随 `--dex2c`） | 把 dex2c 转译出的 JNI 函数打进 `.ncx`，引擎零侵入；带"静默失防"守卫 |
| STEP4 | `ndk-build`（`lib-ndk.sh: ndk_build`） | 编 `libnc.so`（纯 stringenc 组合整体跳过 STEP3/4） |
| STEP5 解包后 | `encrypt-strings.py remove-stub`（仅 LINK_STUB + packer） | 桩已转译进 so，从业务 dex 摘除（同时剔 `compiled_methods.txt` 的桩条目） |
| STEP5 | `$GUARD_SRC/so-section-lock.py` ×3（有一 so 就跑） | ① 一级锁箱 `.ncx,.ncxr` ② 二级锁箱 `--lock-head` ③ `--strip-meta` |
| STEP5 | `repack/mark-native.py` **或** `inject/inject-loadlib.py` | 二选一：勾了 dex2c 用前者，只勾 sigcheck 用后者 |
| STEP5 | `guard/javalink/inject-javacheck.py`（随 `--sigcheck`） | Java 层判决式签名联动：测量杀在 Java、比对在 so 的 `nc_link.c`，so 缺失即 fail-closed |
| STEP5 | `string-enc/encrypt-strings.py` | 规则文件直接透传；联动路径下跳过（避免二次加密）。**C 桩路径**额外传 `--stub-impl native --seed-hex --stub-name`（三者必须与 STEP3 预算的一致） |
| STEP3 前 | 生成桩种子 + `encrypt-strings.py emit-stub-decl` | **C 桩专用**：C 侧注册需要真实桩类名，而桩在 STEP5 才注入 → 必须提前预算 |
| STEP3 | 生成 `nc_strdec_cfg.h` + `nc_strdec_bind.c` | **C 桩专用**：桩类名/密钥/短名绑定都是构建期生成 |
| STEP5 | `anti-diff/anti-diff.py --enable-f` | 无参数依赖，最后做（等前面改动落定） |
| STEP5 回编前 | `patch-extractnativelibs.py` / `patch-debuggable.py` | 有 so 才改 extractNativeLibs；debuggable=false 所有组合都做 |
| 回编 | `lib-repack.sh: repack_build` | → 内部调 `patch-dex-version.py restore` |
| 收尾 | `finish_apk`（zipalign）或 `packer/packer.sh` | 勾加壳时 packer 产物**直接**是最终产物，不再二次 zipalign |

### Python 脚本之间的隐藏依赖（容易漏改的地方！）

| 脚本 | 暗中引用 | 引用什么 |
|---|---|---|
| `encrypt-strings.py` | `filter/rules-to-filter.py` | 借用它的规则解析函数 |
| `encrypt-strings.py` | `inject/inject-loadlib.py` | 借用它的多 dex 目录正则 |
| `anti-diff.py` | `inject/inject-loadlib.py` | 同一正则（报错七的教训：正则只准有一份） |
| `encrypt-strings.py` | `repack/dex-capacity.py` | `_load_module('dex_capacity', ...)` 动态加载，决定注入落哪个 dex |
| `guard/javalink/inject-javacheck.py` | `repack/dex-capacity.py` | `_load_dex_capacity()` 同上，**两处共用同一个 `dex-capacity.json` 标记** |

> **改 `inject-loadlib.py` 里那个目录正则时，三个脚本同时受影响。**
> 这是历史上真实炸过的地方（报错七）。
>
> **改 `dex-capacity.py` 时两个注入器同时受影响**（报错五十九新增）：
> `inject-javacheck.py` 与 `encrypt-strings.py` 必须落到**同一个**新建
> `smali_classes{N+1}/`，各建一个 = 两个 dex 各浪费一份开销。

### lib-repack.sh 内部的固定动作

解包时自动带 `--no-debug-info`（dex 瘦身约 1.8MB）、自动 save dex 版本头；
回编时自动 restore 版本头、调 `patch-dex-version.py`。这些你不用记，
但**别往解包/回编命令里手动加参数**，公共库已经统一了。

### androguard 的解压逻辑有 5 份——这是设计，不是重复代码，别去"清理"

> ⚠️ 2026-11 更正：本节原文讲的是 `tools/dcc.zip` 的 4 份解压逻辑。
> **dcc 引擎已在 2026-12 下线、`dcc.zip` 已于 2026-10-21 删除**，
> 但"多运行时各写一份解压兜底"的结构没变——只是供应源换成了 `dex2c.zip`
> （androguard 现由它携带）。

解压 `tools/dex2c.zip`（取里面的 androguard）的逻辑存在 5 份：

| 位置 | 运行时 | 用途 |
|---|---|---|
| `lib/common.sh` 的 `ensure_dex2c` | bash | 主流水线（`protect.sh`）用 |
| `inject/inject-loadlib.py` 的 `_ensure_dcc_dir` | python | 该脚本单独运行时的自救兜底 |
| `filter/make-filter-from-apk.py` 的 `_ensure_dcc_dir` | python | 同上 |
| `guard/javalink/inject-javacheck.py` 的 `_ensure_dcc_dir` | python | 同上 |
| `repack/patch-dex-version.py` 内联 | python | 同上 |

历史结论（报错六时期）：bash 和 python 是两种运行时，python 无法直接复用
bash 函数，硬合并要引入跨语言子进程调用/状态文件，报错六已证明
"跨语言依赖执行顺序"会炸。各份都幂等（目录在就跳过）且解压后校验
`Dex2C/dcc.py` 或 `androguard/core/bytecodes/apk.py` 存在，
唯一真源 `dex2c.zip` 只有一份，谁先需要谁解压。

**改动时五份的目标解压路径必须保持一致**（都是 `<仓库根>/tools/Dex2C/`），
改任何一份先 grep 其余四份。
