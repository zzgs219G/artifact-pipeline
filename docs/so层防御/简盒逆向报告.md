## 第 1 课 先画地形图，不是先看代码

拿到 APK 先别急着反编译。先回答四个问题：**是什么、多大、有没有壳、代码在哪儿执行**。

第一件事是 `unzip -l target.apk`——不解压，只看目录结构。**文件清单本身就是情报**。

### 1.1 身份信息

```bash
aapt dump badging target.apk
```

```
package: name='com.xixin.box' versionCode='212' versionName='2.1.2'
sdkVersion:'26'  targetSdkVersion:'37'  compileSdkVersion='37'
```

权限清单里有几条特别扎眼：

```
MANAGE_EXTERNAL_STORAGE                     全盘文件读写
QUERY_ALL_PACKAGES                          枚举所有已安装应用
REQUEST_INSTALL_PACKAGES                    请求装包
UPDATE_PACKAGES_WITHOUT_USER_ACTION         静默更新
ENFORCE_UPDATE_OWNERSHIP
moe.shizuku.manager.permission.API_V23      Shizuku 提权框架
```

**结论**：这是一个"应用盒子/软件库"类 App，权限要得很凶（全盘存储 + 静默装包 + Shizuku）。
**推断**：核心逻辑大概率在**装包与下发流程**，而不是普通 UI。逆向重心应放在下载/校验/安装链路。

### 1.2 代码分布

```
classes.dex                       7.4 MB   ← 只有一个 dex，未做多 dex 拆分
lib/arm64-v8a/libnc.so           629 KB    ← 可疑，最大的自定义 so
lib/arm64-v8a/libxcrash.so        76 KB    ← 崩溃捕获
lib/arm64-v8a/libxcrash_dumper.so 114 KB   ← 崩溃捕获（子进程）
lib/arm64-v8a/libandroidx.graphics.path.so ← 官方库，无关
```

**判断**：`libnc.so` 名字里 `nc` 毫无语义，体积是 dex 的 1/12、远超普通辅助库 → 几乎必然是 **native 保护壳 / 虚拟化引擎**。
`xcrash` 的存在佐证这一点：壳需要抓崩溃日志做自身诊断（它把自己的崩溃也归到应用崩溃里）。

### 1.3 段表——马脚在这里

```bash
readelf -SW libnc.so
```

```
[11] .ncxr       0x37f14  0x60     AR     ← 自定义段
[12] .ncks       0x37f74  0x70     AR     ← 自定义段
[13] .nck        0x37fe4  0x60     AR     ← 自定义段
[15] .text       0x425c0  0x4ee3c  AXR    ← 正常代码
[16] .ncx        0x913fc  0x1ac0   AXR    ← 自定义段，可执行！
[17] .ncxh       0x92ebc  0xc20    AXR    ← 自定义段，可执行！
[18] .plt        0x93ae0  0x560    AX
[27] .ncxhr      0x9a170  0x20     WAR    ← 自定义段
```

三个观察：

**① 非标准段名。** `.ncxr / .ncks / .nck / .ncx / .ncxh / .ncxhr` 全是壳作者自建的，统一前缀 `nc` + 后缀。后缀含义可推测：

| 段 | 属性 | 推测含义 |
|---|---|---|
| `.ncxr` | R | x-region，待重定位/解密的数据区 |
| `.ncks` | R | 96 字节，key/salt 区 |
| `.nck` | R | 96 字节，key 区 |
| `.ncx` | **RX** | 隐藏代码区 |
| `.ncxh` | **RX** | 隐藏代码区（h = hidden/handler） |
| `.ncxhr` | RW | 隐藏代码的可写上下文 |

**② 地址连续。** `.ncx` 起始 `0x913fc` **正好等于 `.text` 末尾**（`0x425c0 + 0x4ee3c = 0x913fc`）。
说明 linker 把它当作连续代码接在后面，**可以直接 `bl` 过去**，肉眼看却是"另一个段"。

**③ 可执行属性。** `.ncx / .ncxh` 带 `X`——`mmap` 时可执行，里面装的是真代码，静态看是加密的。

### 1.4 符号表——最重要的一击

```bash
readelf -sW --dyn-syms libnc.so
```

87 个动态符号，**只有 1 个自定义导出函数**：

```
Num:   Value   Size Type  Bind   Vis     Ndx Name
 86: 0x042b50   388 FUNC  GLOBAL DEFAULT  17  JNI_OnLoad
```

其余 86 个全是 libc 导入符号。

**教学点**：如果 Java 层的 `native` 方法靠默认的 `Java_com_xixin_box_Xxx_yyy` 命名约定导出，`dynsym` 里会有一排 `Java_*` 符号。现在一个都没有 → 这个 so 用的是 **`RegisterNatives` 动态注册**。

方法名到函数指针的映射被藏在**运行时的数据结构**里，静态看不见。这是保护第一层：**剥离导出符号，破坏"按名字找函数"这条常规路径**。

### 1.5 导入符号也在说话

```
mprotect  getauxval  dl_iterate_phdr  dladdr  syscall
pthread_rwlock_*  pthread_key_*  pthread_create  pthread_attr_*
syslog  openlog  closelog
__system_property_get  access  fopen  fgets  readdir  strstr  opendir
```

逐组翻译：

| 符号组合 | 用途 |
|---|---|
| `mprotect` + `getauxval` + `dl_iterate_phdr` | **自解密 + 遍历自身映射做完整性校验** |
| `syslog` / `openlog` / `closelog` | 不走 Android logcat，写 `/dev/log` 绕开常规抓日志 |
| `fopen` `fgets` `readdir` `opendir` `strstr` | **扫描文件/目录，搜索特征串**（root / frida / magisk 痕迹） |
| `syscall` 直调 | 绕 libc hook（反 frida 常用手法） |
| `pthread_create` + `nanosleep`/`sleep` | 后台线程 + 定时循环 → **心跳/巡检** |

> 注意：**没有 `ptrace` 的 PLT 导入**。如果它要反调试，只能走 `syscall(SYS_ptrace, ...)`——这正是 `syscall` 导入的可疑之处。

### 第 1 课小结

| 层 | 机制 | 证据 |
|---|---|---|
| 符号 | 只导出 `JNI_OnLoad`，JNI 动态注册 | dynsym 仅 1 个 FUNC |
| 布局 | 自定义段藏代码 | `.ncx` / `.ncxh` 可执行段 |
| 加密 | 运行时自解密 | `mprotect` + `.ncxr` relocator 段 |
| 完整性 | 遍历自身 phdr 校验 | `dl_iterate_phdr` + `getauxval` |
| 反调试 | 扫描进程/文件、直调 syscall | `readdir` / `strstr` / `syscall` |
| 日志 | 绕过 logcat | `syslog` / `openlog` |

## 第 2 课 init_array 是壳的开机自启清单

`.init_array` 段在 ELF 里是**构造函数数组**——linker 加载 so 时、`JNI_OnLoad` 之前，会按顺序把里面每个地址当函数调用一遍。

**壳作者最爱的挂载点就在这里**：解密、反调试、装 hook，全塞这一步。

### 2.1 陷阱：段看着是空的

```bash
readelf -x .init_array libnc.so
```

```
0x00098b88 00000000 00000000 00000000 00000000 ................
0x00098b98 00000000 00000000 00000000 00000000 ................
0x00098ba8 00000000 00000000 00000000 00000000 ................
```

**全是 0。为什么？**

因为这些地址不是编译期常量，是**重定位项 `R_AARCH64_RELATIVE` 在加载时才填进去的**。原文件里的 0 只是占位。

> ⚠️ **这是逆向静态 so 时最常见的坑**：`"段是空的"` 往往是幻觉。必须去 `.rela.dyn` 里查谁往这个偏移写值。

### 2.2 从重定位表还原真相

```bash
readelf -rW libnc.so | grep -E "98b8|98b9|98ba|98bb"
```

```
0000000000098b80  R_AARCH64_RELATIVE  0x425c0    ← .fini_array
0000000000098b88  R_AARCH64_RELATIVE  0x4c20c    ← init[0]
0000000000098b90  R_AARCH64_RELATIVE  0x8cc64    ← init[1]
0000000000098b98  R_AARCH64_RELATIVE  0x8d298    ← init[2]
0000000000098ba0  R_AARCH64_RELATIVE  0x43820    ← init[3]
0000000000098ba8  R_AARCH64_RELATIVE  0x4aa18    ← init[4]
0000000000098bb0  R_AARCH64_RELATIVE  0x4b388    ← init[5]
```

**6 个构造函数。** 这个数量本身就异常——正常 C++ so 通常 1~2 个（`__cxa_atexit` 相关）。6 个说明壳把初始化流程拆得很细，每步干一件事。

### 2.3 旁证：dispatch 表的雏形

`.data.rel.ro`（`0x95000`）开头是一张指针表，混合了 `.rodata` 偏移和 `.text` 地址：

```
0000000000095000  R_AARCH64_RELATIVE  0x95000   ← 指向自己
0000000000095008  R_AARCH64_RELATIVE  0xd165    ← .rodata 中间
0000000000095010  R_AARCH64_RELATIVE  0xbe4c
0000000000095018  R_AARCH64_RELATIVE  0x43a04   ← .text
0000000000095020  R_AARCH64_RELATIVE  0xb990
0000000000095028  R_AARCH64_RELATIVE  0xb103
0000000000095030  R_AARCH64_RELATIVE  0x44490   ← .text
0000000000095038  R_AARCH64_RELATIVE  0xc2ae
```

"字符串和函数指针交替排列"是**解释器 dispatch 表**的经典形态：每项 = {名字/日志串, handler 函数}。

另：1580 条 `.rela.dyn` 里绝大多数 `addend` 落在 `0xb000 ~ 0xd900`——那正是 `.rodata` 靠前的部分。说明 `.rodata` 前段被当**数据表数组**使用。

## 第 3 课 读 JNI_OnLoad，认壳的总控函数

### 3.1 怎么"读"而不是逐条念汇编

只看骨架：

```asm
0x42b50  sub  sp, sp, 0x60            ; 建栈帧
0x42b64  mrs  x21, tpidr_el0          ; 取 TLS 基址
0x42b70  ldr  x8, [x21, 0x28]         ; TLS+0x28 → stack canary
0x42b80  stur x8, [x29, -8]           ; 存 canary（标准的 -fstack-protector）
0x42b84  ldr  x8, [x0]                ; x0 = JavaVM*，读出 vtable
0x42b88  ldr  x8, [x8, 0x30]          ; vtable[6] = GetEnv
0x42b8c  blr  x8                      ; (*vm)->GetEnv(vm, &env, 6)
0x42b90  cbnz w0, 0x42c9c             ; 失败 → 返回 -1
```

**教学点：认出 C++ 虚表调用。**
`x0` 是 `JavaVM*`，`ldr [x0]` → vtable，`[vtable + 0x30]` → **`GetEnv`**。
`JNIInvokeInterface` 里 `GetEnv` 是第 7 个槽位，8 字节对齐 = `0x30`。汇编里所有 `ldr x8,[x0]; ldr x8,[x8,OFF]; blr x8` 都是这种"对象 → 虚表 → 槽位 → 调用"。

### 3.2 JNIEnv vtable 被替换了

```
0x42bac  add  x1, sp, 0x10
0x42bb8  ldr  x22, [x8]        ; x8 = .got[?]，读出某个 vtable 指针
0x42bc4  bl   0x438e8          ; stub: str x8,[sp,0x10]; b 0x42cd4
0x42bd8  adr  x8, .rodata+0x392 (=0xb392)
0x42be0  bl   0x438e8
0x42bf4  adr  x8, .rodata+0x875 (=0xc875)
0x42c10  adr  x8, .rodata+0x397 (=0xb397)
0x42c2c  adr  x8, .rodata+0xc6fc
0x42c48  adr  x8, .rodata+0x3f
0x42c8c  str  x22, [x0]        ; ★ 把 vtable 指针写回某个对象
0x42c94  bl   0x43948          ; ★★ 真正的业务初始化
```

被读的 `.got` 槽位（重定位后）：

```
0x98dc8  → 0x4a088     .text
0x98dd0  → 0x4a120     .text
0x98dd8  → 0x6f00c     .text 深处
0x98de0  → 0x37f74     ★ .ncks 段首
0x98de8  → 0x9ae18     .ncxhr
0x98d88  → 0x9a2a8     .bss
0x98d90  → 0x9a2a0     .bss
```

**这就是壳的标准签名：JNIEnv vtable 替换。**

`JNI_OnLoad` 一进来先做一件事——自己造一个**假的 `JNIEnv` 函数表**，把 `env->FindClass`、`env->GetMethodID`、`env->GetFieldID`、`env->CallXxxMethod`、`env->RegisterNatives` 等槽位换成壳自己的版本，再把 `env` 指向这张假表。

**为什么这么干？**
JNI 的函数表是**一张纯指针数组**，Java/NDK 代码只能靠 `env->Xxx()` 的宏偏移去调（`(*env)->Xxx(env, ...)`）。壳一旦把 `env` 指向自己的表，就获得了对**所有** JNI 调用的完全监控权：
- 看谁调用了什么
- 篡改参数/返回值
- 在调用前后插桩（比如隐藏某些类、拦截某些反射）

比 hook `libart` 简单得多，也隐蔽得多。

> `.got` 里 `0x37f74` = `.ncks` 段**起始地址**。`JNI_OnLoad` 把 `.ncks` 装进 GOT，说明后面会拿它当结构体/表解析。

### 3.3 组件劫持：attachBaseContext

`JNI_OnLoad` 最后调用的 `0x43948`，里面出现**明文**字符串：

```asm
0x43964  adr  x1, str.com_xixin_box_MainActivity   ; 0xb975
0x4397c  blr  x8                                   ; 调 FindClass
0x43980  cbz  x0, 0x439d4
0x4398c  adr  x1, reloc.fixup.attachBaseContext    ; 0x95008 → "attachBaseContext"
0x43994  mov  w2, 0x60                             ; 0x60 = 96 = sizeof(JNINativeMethod)? 不是
0x439b0  ldr  x8, [x8, 0x6b8]
0x439b4  blr  x8
0x439c4  ldr  x8, [x8, 0xb8]
0x439c8  blr  x8                                   ; 反射调用
0x439d4  adrp x0, 0xc000; add x0, x0, 0x282        ; "Class not found: com/xixin/box/MainActivity"
```

**`com.xixin.box.MainActivity` + `attachBaseContext` 同时出现** → 壳在做 **Activity/Application 劫持**：反射拿到组件实例，替换 `attachBaseContext`，把真正的 App 塞进自己的容器里跑。

**好消息**：`.rodata` **没有加密**（能读出明文类名）。说明加密区是**局部的**——只有特定的指针表区间被加密。

## 第 4 课 先挖字符串，别一条条跟指令

`adrp x4, 0xb000; add x4, x4, 0xe69` → 字符串 `0xbe69`。这种 `adrp+add` 是 `.rodata` 取址的标准姿势。**与其一条条跟，不如一次性把 `.rodata` 整个倒出来。**

```python
import re
data = open('libnc.so','rb').read()
base = 0xaea0                       # .rodata 地址 = 文件偏移
rod  = data[base:base+0x2d074]      # .rodata 大小
for m in re.finditer(rb'[\x20-\x7e]{5,}', rod):
    print(f"{base+m.start():#07x}  {m.group().decode()}")
```

651 条字符串，其中 `.rodata` 前段（`0xb000~0xd950`）是金矿。

## 第 5 课 定位 shell 与 App 的「契约」：NcLink

`strings` 里 `nc: ok` 和 `com/nc/link/NcLink` 是钥匙。jadx 单类反编译：

```bash
java -Xmx2500m -cp ~/逆向工具/jadx/lib/jadx-1.5.6-all.jar jadx.cli.JadxCLI \
  --single-class 'com.nc.link.NcLink' --comments-level debug -d jadx x/classes.dex
```

```java
// jadx/sources/com/nc/link/NcLink.java
package com.nc.link;

public final class NcLink {
    public static void ensureLoaded() { System.loadLibrary("nc"); }

    public static native void    heartbeat();
    public static native boolean ncVerify(byte[] bArr);
    public static native int     selftest();
}
```

**这三个方法把整张图补全了。**

### ① `System.loadLibrary("nc")`
壳就是 `libnc.so`，不是"某个混淆库附带的 so"，是独立命名的保护库。

### ② `static native` 但 `dynsym` 里没有 `Java_*` 符号
复习第 1 课：这证明它用 **`RegisterNatives`** 注册。
也就是说 `libnc.so` 里有一张 `{类名, 方法名, 签名, 函数指针}` 表，把这三个方法挂上去。这张表在哪？**答案在第 7 课**（被 XOR 加密了）。

### ③ `ncVerify(byte[]) → boolean` —— 最关键的一条

配合 so 里那句 `der_len=%zu`：

- `der_len` = **DER 编码长度**
- APK 签名证书（`META-INF/CERT.RSA` 或 v2/v3 签名块）就是 DER / PKCS#7 格式
- 所以 `bArr` **极可能就是签名证书的 DER 原始字节**
- 返回 boolean = 校验通过/失败

**为什么这一点很重要？**

如果 App 只简单比对 `getPackageInfo().signatures[0].hashCode()`，你改 dex 就能过。但这里把**原始 DER 字节**丢进 native：
- 校验逻辑不在 dex 里 → **改 Java 无效**（可以直接把 `ncVerify` 调用删掉，但那样 `Invalid access!` 会触发）
- native 里可以做 DER 解析、取公钥、验签、比对指纹，甚至解密内嵌的一段加密数据 —— **这些静态看不见**
- 配合 `Invalid access!`，校验失败很可能直接 `abort`/`_exit`，**连异常都抓不到**

### ④ `heartbeat()` / `selftest()` —— 主动防御接口

- `heartbeat()`：通常被杀出的 `pthread_create` 线程周期性调用（`pthread_create` + `sleep`/`nanosleep` 导入符号对上了），形成**心跳**。一旦 App 停止调用（比如被脱壳工具暂停、或被替换掉），壳就知道自己被动过了。
- `selftest()`：自检，多半是查 so 自身完整性 + 查调试器/注入。

```
0x00095010  0x000000000000b990  0x000000000000b103
0x00095018  0x0000000000044490  0x000000000000c2ae   ← .text
...
```

### 6.2 看出结构：`(length, pointer)` 成对

关键在验算：

```
0xd55b - 0xd520 = 0x3b   ← 而 length 字段恰好是 0x3b
0xd57f - 0xd55b = 0x24   ← 而 length 字段恰好是 0x24

```

**完美对齐。** 这是**不带 `\0` 结尾的、长度前缀的字符串表**（length-prefixed string table）。

**壳为什么要这么设计？**
`strings` 命令靠找 `\0` 分隔的可打印序列。长度前缀表**没有分隔符**，天然对抗 `strings`。
（但对付长度前缀表最简单的办法就是——**把 length 字段也当数据读出来**，见下）

## 第 7 课 破掉第一层加密：单字节 XOR

### 7.1 思路：先猜"密码学最弱的一环"

看到"加密字符串"，新手容易直接上 angr / 动态调试。**先做最便宜的事**：单字节 XOR 爆破。

理由：字符串混淆的成本和收益必须平衡。壳作者通常只用最轻量的手法——因为完整 AES 解密要带密钥管理、要防密钥泄漏，成本高。**单字节 XOR + 长度前缀 + 无 `\0`** 三件套，足以秒掉 99% 的 `strings` 分析。

```python
data = open('libnc.so','rb').read()
blob = data[0xd4a0:0xda00]          # 密文区

for k in range(0x20, 0x7f):         # 暴力所有可打印 key
    dec = bytes(b ^ k for b in blob[:80])
    printable = sum(1 for c in dec if 32 <= c < 127 or c == 0)
    if printable > 70:              # 大部分是可打印/终止符 → 命中
        print(f"XOR {k:#04x}: {dec}")
```

### 7.2 结果

```
XOR 0x5a: b'ZZncVerify\x00([B)Z\x00heartbeat\x00()V\x00selftest\x00()I\x00ZZZZ...'
```

**一击命中。** XOR key = **`0x5A`**。

### 7.3 逐字节验证（别只看"看起来对"）

```
密文 0xd4b0:  5a 32 3f 3b 28 2e 38 3f 3b 2e 5a 72 73 0c 5a 29 ...
XOR  0x5a:    00 68 65 61 72 74 62 65 61 74 00 28 29 56 00 73 ...
明文:         .  h  e  a  r  t  b  e  a  t  .  (  )  V  .  s  ...
                  └────── "heartbeat" ──────┘    │  │  │
                                                  │  │  └─ "selftest" 开头
                                                  │  └──── 签名 "()V"
                                                  └─────── 分隔符
```

### 7.4 反推出两个格式规则

**规则 1：明文 `0x00`（字符串终止/分隔）← 密文 `0x5A`**
所以密文里那些 `Z`（`0x5A`）字符**不是字母，是分隔符**。
这也解释了为什么 `strings` 把这堆东西当乱码吐出来——`Z` 在中间被当成普通字符了。

**规则 2：明文 `0x5A`（'Z'）← 密文 `0x00`**
所以解出来的开头 `ZZ` 是**真实存在的 `0x5A 0x5A` 明文**，不是幻觉。

### 7.5 解出的内容 = JNI 注册表

```
ncVerify   ([B)Z
heartbeat  ()V
selftest   ()I
```

**这和第 5 课从 `NcLink.java` 读到的方法名/签名完全一致**，互相印证：

| 方法 | 签名 | 与第 5 课对照 |
|---|---|---|
| `ncVerify` | `([B)Z` | `native boolean ncVerify(byte[])` ✓ |
| `heartbeat` | `()V` | `native void heartbeat()` ✓ |
| `selftest` | `()I` | `native int selftest()` ✓ |

> 这也是个**方法论**：不同来源的信息能互相印证时，你才敢下结论。单看密文解出来一堆字，你只知道"好像对"；和 jadx 的 Java 声明对上，才是**确认**。

### 7.6 密文区里还藏着什么

解完前 60 字节后，后面是别的东西：

```
... 5a 5a 5a 5a │ 15 46 d0 29 8f 7c b3 51 6d 9e 35 c8 fb 02 b7 6a 43 │ 00*16 │
```

以及再往后（`0xd5xx` 起）有一段**很可疑的常量**：

```
67e6096a 85ae67bb 72f36e3c 3af54fa5 9cb0a4d7 ...
```

按小端读出来是：

```
6a09e667  bb67ae85  3c6ef372  a54ff53a  510e527f  9b05688c  1f83d9ab  5be0cd19
```

**这就是 SHA-256 的初始向量（IV）。**

```
6a09e667 bb67ae85 3c6ef372 a54ff53a 510e527f 9b05688c 1f83d9ab 5be0cd19
```

> 教学点：**认识密码学常量**是逆向的重要基本功。看到这 8 个 32 位字就等于看到 "SHA-256 实现"。同理：
> - `67452301 EFCDAB89 98BADCFE 10325476` → MD5 IV
> - `6a09e667...` → SHA-256 IV
> - `428a2f98...` → SHA-256 轮常量 K
> - `cbf43926` → CRC32 多项式
>
> 这意味着：**校验逻辑用的是 SHA-256**（而不是简单的字节比对），并且**算法是内嵌实现的**（不是调 libcrypto），所以既查不到 `SHA256_Init` 之类导入符号，也没法 hook 系统库。

### 7.7 第 7 课小结

| 项 | 结论 |
|---|---|
| 加密算法 | **单字节 XOR，key = `0x5A`** |
| 分隔符 | 密文 `0x5A` = 明文 `0x00` |
| 表结构 | `(uint64 length, ptr)` 成对，长度前缀 |
| 解出内容 | JNI 注册表：`ncVerify ([B)Z` / `heartbeat ()V` / `selftest ()I` |
| 额外发现 | 密文区混有 **SHA-256 IV**，说明内嵌了 SHA-256 实现 |
| 防护强度 | **弱**——字符串混淆只是入门门槛 |

## 第 8 课 XOR 扫描的误报陷阱

破掉 `0x5A` 之后，最自然的想法是"把整个 `.rodata` 都用 `0x5A` 解一遍，反调试黑名单不就全出来了"。

**我这么做了，然后得到了假结果。** 这个坑必须讲清楚。

### 8.1 错误做法

```python
dec = bytes(b ^ 0x5A for b in rodata)
re.finditer(rb'[\x20-\x7e]{4,}', dec)     # 找可打印串
```

结果出来 6203 条"解出的字符串"，看起来收获巨大。但交叉验证时发现：

```
0xb1d7  raw: 6661696c65643a202573206572726e6f3d256428257329 00
       = "failed: %s errno=%d(%s)"     ← 这根本不是密文！是明文
```

明文 `'a' ^ 0x5A = ';'`，仍然是可打印 ASCII。**所以 XOR 任何明文 ASCII 段都会得到"看起来像字符串"的垃圾。**

### 8.2 为什么滑窗法也救不了

我改用滑窗打分（64 字节窗口内 ≥92% 可打印率即判为密文区），结果得到 300+ 个"密文区"——因为明文段本身就 100% 可打印。**滑窗法在这里完全失效。**

### 8.3 正确做法

**① 用结构，不要用内容。**
真正的密文区位置是由**代码里的引用**决定的。看 `0x4a1f8`：

```asm
adr x1, 0xd4a2      ; 密文起始
mov w2, 9           ; 长度
bl  0x4a34c         ; XOR 解密
```

`0xd4a2` 和长度 `9` 都是**硬编码在指令里**的。所以：
- 与其扫数据找密文，不如**扫代码找 `bl <decrypt>` 调用点**
- 每个调用点给出 `(地址, 长度)` 二元组，**这就是密文区清单**

**② 密文区只有一小块。**
全文件用 0x5A 解，真正有意义的只有：
```
0xd4a2  "ncVerify"
0xd4ab  "([B)Z"
0xd4b1  "heartbeat"
0xd4bb  "()V"
0xd4bf  "selftest"
0xd4c8  "()I"
```
共 6 条，54 字节。**其余全是噪音。**

### 8.4 已知明文攻击也失败了

我还试了正向思路——搜 `frida`/`magisk`/`ptrace` 在**任意单字节密钥**下的密文：

```python
for t in [b'frida', b'magisk', b'ptrace', ...]:
    for k in range(1, 256):
        data.find(bytes(c ^ k for c in t))
```

2917 个命中，**全部是误报**。原因：

- `frida`（5 字节）→ 2917/2917 是误报
- `su`（2 字节）→ `'su' ^ 1 = "rt"`，满文件都是 `rt`（`start`/`return`/`assert`……）

**教训**：短模式串 + 小密钥空间的搜索**信噪比极低**，永远要通过上下文（是否在密文区、是否被解引用）二次验证。

### 8.5 本课结论

> **反调试特征串不在 so 的静态数据里。**

它们要么①运行时逐字符拼接（`mov w8, 'f'; strb w8, [buf]`），要么②来自 Java 层传参，要么③根本不存在于这份样本（壳的这部分功能被裁剪了——记得 `RegisterNatives` 里的 `cbz x26` 可裁剪逻辑吗）。

**这也是逆向中要有心理准备的事：不是每个假设都会被证实。** 我花了大约 4 次尝试在这条路上，最后只能标记为"未发现"，而不是硬编一个答案。

## 第 9 课 从 dex 找到校验主控 NativeGuard

`.rodata` 挖完了，回头做**交叉验证**——`NcLink` 到底被谁调用？

```bash
grep -rn "ncVerify\|NcLink\|selftest\|heartbeat" jadx_all/sources
```

```
jadx_all/sources/com/xixin/box/NativeGuard.java:12,22,23,26,31
```

**只有 `NativeGuard` 一个文件**。这就是整个防护体系在 Java 侧的唯一入口。

```java
// jadx_all/sources/com/xixin/box/NativeGuard.java
package com.xixin.box;

public final class NativeGuard {
    private static boolean hbStarted;

    public final class Hb extends Thread {
        @Override public void run() {
            while (true) {
                try {
                    com.nc.link.NcLink.heartbeat();
                    Thread.sleep(5000L);          // ★ 每 5 秒一次心跳
                } catch (Throwable unused) { }
            }
        }
    }

    public static void c(android.content.Context context) {
        try {
            com.nc.link.NcLink.ensureLoaded();
            if (com.nc.link.NcLink.selftest() != 59) {          // ★ 魔数 59
                Log.w("ncguard", "selftest rc!=59");
            }
            com.nc.link.NcLink.heartbeat();
            startHeartbeat();

            MessageDigest md = MessageDigest.getInstance("SHA-256");
            PackageManager pm = context.getPackageManager();
            String pkg = context.getPackageName();

            byte[] sig = (Build.VERSION.SDK_INT >= 28
                    ? pm.getPackageInfo(pkg, 0x8000000).signingInfo.getApkContentsSigners()
                    : pm.getPackageInfo(pkg, 0x40).signatures)[0].toByteArray();

            if (com.nc.link.NcLink.ncVerify(md.digest(md.digest(sig)))) {
                return;                                          // ★ 校验通过
            }
            android.os.Process.killProcess(android.os.Process.myPid());   // ★ 失败自杀
        } catch (UnsatisfiedLinkError unused) {
            android.os.Process.killProcess(android.os.Process.myPid());   // ★ so 加载失败也自杀
        } catch (Throwable unused2) { }
    }

    public static void startHeartbeat() {
        if (hbStarted) return;
        hbStarted = true;
        Hb hb = new Hb();
        hb.setDaemon(true);
        hb.start();
    }
}
```

### 逐个讲清楚

**① 校验数据 = `SHA256(SHA256(证书 DER))`**

```
sig = 签名证书的 DER 字节
       ↓ MessageDigest.digest(sig)            → 32 字节
       ↓ MessageDigest.digest(前一步结果)      → 32 字节
       ↓ ncVerify(32 字节)
```

**双重 SHA-256**。这是壳作者的一个小心思：即使你 dump 出传给 `ncVerify` 的 32 字节，你也只拿到 `SHA256(SHA256(DER))`，不直接等于任何标准的指纹格式，多一层推理成本。

而 `ncVerify` 里 `cmp w0, 0x20`（长度必须 32）——**完美对应**。

**② 56 = 0x38，59 = 0x3B**

```java
if (NcLink.selftest() != 59)
```

`59` 这个魔数在 native 里一定有对应的返回值。**改 dex 把这行删掉是无效的**，因为 `selftest` 的返回值可能还被 native 内部其他地方用（比如写进 `crash_info`）。

**③ `catch (UnsatisfiedLinkError) → killProcess`**

这是最恶心的设计，第 10 课会讲为什么（`RegisterNatives` 的可裁剪注册）。

**④ `catch (Throwable unused2) { }` 空吞异常**

注意：`ncVerify` 返回 `false` 走 `killProcess`；但如果 native 里 `abort()`/`brk`，那连这个 catch 都拦不住。

**⑤ `0x8000000` = `PackageManager.GET_SIGNING_CERTIFICATES`**

```
SDK >= 28 : pm.getPackageInfo(pkg, 0x8000000).signingInfo.getApkContentsSigners()
SDK <  28 : pm.getPackageInfo(pkg, 0x40 /*GET_SIGNATURES*/).signatures
```

**这是 Android 9+ 的正确写法**——`getApkContentsSigners()` 返回的是**当前安装的签名者**，而不是历史签名者。壳作者很专业。

### 本课结论

**Java 侧完全透明，一行没混淆。** `NativeGuard` / `NcLink` / `hbStarted` / `startHeartbeat` 全是语义化命名。

> 这本身就是情报：**壳作者对 native 层有足够信心，认为不需要混淆 Java 侧**。所以攻击面必然在 native。

## 第 10 课 读懂 RegisterNatives 现场

要在 native 里找 `ncVerify` 的实体，得先找 `RegisterNatives`。因为 `FindClass` 的类名 `com/nc/link/NcLink` 是明文的，直接搜它的引用：

```bash
grep -nE "com_nc_link_NcLink" dis.txt
```

### 10.1 完整现场（0x4a1a8 ~ 0x4a2e4）

```asm
0x4a1a8  sub sp, sp, 0xe0             ; 栈上开 3 个 JNINativeMethod (3*24=72)
0x4a1aac  stp x29, x30, [sp, 0x90]    ; 序言
...
0x4a1d0  cbz x0, 0x4a2bc              ; env == NULL → 返回 -1
0x4a1d4  ldr x8, [x0]                 ; env->functions
0x4a1dc  adr x1, "com/nc/link/NcLink" ; 0xb805  ← 明文类名
0x4a1e4  ldr x8, [x8, 0x30]           ; FindClass (槽位 6)
0x4a1e8  blr x8
0x4a1ec  cbz x0, 0x4a2b8              ; 类找不到 → ExceptionClear + 返回 -1
0x4a1f0  mov x20, x0                  ; clazz

; ─────── methods[0] = {"ncVerify", "([B)Z", ptr} ───────
0x4a1f8  adr x1, 0xd4a2               ; ★ 密文起始（跳过了前 2 字节 "ZZ"）
0x4a1fc  sub x0, x29, 0x28            ; 目标栈缓冲
0x4a200  mov w2, 9                    ; 长度 9
0x4a208  bl  0x4a34c                  ; ★ XOR 0x5A 解密
0x4a210  adr x1, 0xd4ab               ; "([B)Z"
0x4a218  mov w2, 6
0x4a220  bl  0x4a34c
0x4a234  ldr x8, [0x980dc8]           ; ★ ncVerify 函数指针（从 GOT 读！）
0x4a244  str x8, [sp, 0x10]           ; methods[0].fnPtr

; ─────── methods[1] = {"heartbeat", "()V", ptr} ───────
0x4a230  adr x1, 0xd4b1  ; len 0xa
0x4a26c  ldr x8, [0x980dd0]           ; ★ heartbeat 指针

; ─────── methods[2] = {"selftest", "()I", ptr} ───────
0x4a270  ldr x26, [0x980dd8]          ; ★ selftest 指针
0x4a27c  cbz x26, 0x4a2c4             ; ★★★ 指针为 NULL 就跳走
0x4a284  adr x1, 0xd4bf  ; "selftest" len 9
0x4a298  adr x1, 0xd4c8  ; "()I"      len 4
0x4a2a8  mov w3, 3                    ; nMethods = 3
0x4a2b4  b   0x4a2c8

0x4a2c4  mov w3, 2                    ; ★ nMethods = 2  ← 只注册两个！

0x4a2c8  ldr x8, [x19]
0x4a2cc  mov x2, sp                   ; methods 数组
0x4a2d0  mov x0, x19                  ; env
0x4a2d4  mov x1, x20                  ; clazz
0x4a2d8  ldr x8, [x8, 0x6b8]          ; RegisterNatives (槽位 215)
0x4a2dc  blr x8
0x4a2e0  cbz w0, 0x4a2f0              ; 成功 → w21 = 0
0x4a2e4  bl  0x4a388                  ; 失败 → ExceptionClear
0x4a2e8  mov w21, -3
```

### 10.2 四个关键机制

**① 字符串永不驻留内存**

`0x4a34c` 这个解密函数调用了 5 次，每次都把密文解到**栈上临时缓冲**，用完立刻 `memset(0)` 清零（`0x4a36c`）。做完这次 `RegisterNatives` 后，栈帧销毁，**内存里再也找不到 "ncVerify" 这个字符串**。

> 这是专门对抗 **memory scan / string dump** 的。你用 Frida `Memory.scan("ncVerify")` 是扫不到的。

**② 函数指针走 GOT，不是内联**

```
[0x980dc8] → 0x4a088   ncVerify
[0x980dd0] → 0x4a120   heartbeat
[0x980dd8] → 0x6f00c   selftest
```

`.got` 在 `.data` 段（可写）。**为什么要绕这一层？**
- 运行时可以把任意槽位改成 0 或换成别的函数
- 这样 `RegisterNatives` 注册的内容是**动态决定的**，静态看不出全貌
- 也让"直接 patch 0x4a088"这种改法可能被绕过（走的可能是另一份代码）

**③ `cbz x26, 0x4a2c4` —— 可裁剪注册**

如果 `selftest` 指针为 NULL，`nMethods` 从 3 变成 2，**`selftest` 就不注册**。

后果：Java 调 `NcLink.selftest()` 会抛 `UnsatisfiedLinkError`，而 `NativeGuard.c()` 的 `catch (UnsatisfiedLinkError)` 分支是 **`Process.killProcess(myPid())`**。

> **置空 = 自杀式陷阱。**
> 反过来，如果你想 patch 掉 `selftest` 的返回值，**不能靠置空指针**，那会直接自杀。必须改返回值。

**④ JNI 槽位偏移速查**

从这段代码可以直接建立一张表（`env->functions` 索引 × 8 = 偏移）：

| 偏移 | 槽位 | 函数 |
|---|---|---|
| `0x30` | 6 | `FindClass` |
| `0x558` | 171 | `GetArrayLength` |
| `0x5c0` | 184 | `GetByteArrayElements` |
| `0x600` | 192 | `ReleaseByteArrayElements` |
| `0x6b8` | 215 | `RegisterNatives` |
| `0x88` | 17 | `ExceptionClear` |
| `0x6b8` | 215 | `RegisterNatives` |

> **逆向技巧**：有了这张表，后面读任何 JNI 代码都不用查头文件。建议逆向 native 时先把这张表建好。

```asm
0x4a0ac    ldr  x8, [x8, 0x558]             ; GetArrayLength
```

### 11.2 **`0x91400` 不在 `.text` 里！**

这是整条线索的爆点。

```
.text   0x425c0 ~ 0x913fc     ← 普通代码
.ncx    0x913fc ~ 0x92ebc     ← 自定义段，RX
```

`0x91400` 落在 **`.ncx` 段内 4 字节处**。

也就是说：
> **`ncVerify` 本身是明文（能读、能改），但它唯一做的事就是把 32 字节交给加密段里的代码判断。真正的算法在 `.ncx` 里。**

这也解释了为什么壳这么"大方"地不混淆 `ncVerify`——**反正它只是个转发器**。

### 11.3 顺手确认 XOR 函数和 anti-forensics

## 第 12 课 找到加密段执行器：解释器真身

### 12.1 `.ncx` 是被 `b`（无条件跳转）进入的

```bash
grep -E "0x9(1[3-9a-f]|2[0-9a-e])[0-9a-f]{2}" dis.txt
```

```
0x4a0e0  bl 0x91400      ← ncVerify 进入
0x4aa18  b  0x92184      ← init_array[4] 直接跳进 .ncx
0x4b388  b  0x92cb4      ← init_array[5] 直接跳进 .ncxh
0x4c380  bl 0x92e0c      ← init_array[0] 里的反调试循环
0x6f03c  b  0x92ea4
0x8d37c  bl 0x91360
```

注意 `b` 是**无条件跳转**，不是 `bl`（不返回）。

**这就是"代码分段加密 + 执行流接力"**：`.text` 把控制权交给 `.ncx`，永不返回。

关键线索：
```
init_array[4] = 0x4aa18 : b 0x92184
init_array[4]+4 = 0x4aa1c : sub sp, sp, 0x150   ← 一个完整函数
```

**`0x4aa18` 是一条 1 条指令的跳板**，真实函数体在 `0x4aa1c`。它先把控制流丢进 `.ncx`（`0x92184`），而 `0x92184` 里解完密再跳回来继续。

### 12.2 `.ncx` 起始处的"明文残片"

`0x913fc` 处的前 12 字节是**合法 aarch64**：

```
0x913fc: 1f 04 01 fd  →  sub  sp, sp, 0x40
0x91400: 00 00 80 d2  →  mov  x0, 0
0x91404: c0 03 5f d6  →  ret          ← 只返回 0
```

> ⚠️ **等等——这段是假的。**
> 如果 `0x91400` 真是 `mov x0,#0; ret`，那 `ncVerify` 永远返回 **false**，App 一启动就自杀。
>
> 所以这几条"合法指令"是**刻意构造的诱饵**：如果你把 `0x913fc` 当代码起点直接反汇编，会得到一段"看起来正常但语义荒谬"的代码。
> **真正的 `0x91400` 函数体是加密的**，由初始化流程解密后才变成有效代码。

（这也是为什么 jadx/r2 在 `0x91400` 附近的自动分析会给出一堆 `tbz x2, 0x21` 之类无意义指令——它解不出来。）

`.ncx` 实际内容：
```
0x913fc: f0 87 ac be ff bf 8d 75 d7 35 ef ea 91 92 5c 67 ...
```
从第 4 字节起就是随机字节。

### 12.3 `init_array[0]` 是全部防御的总闸

`0x4c080`（`init_array[0]` 的实体）：

```asm
0x4c094  ldrb w8, [0x9a734]        ; 已初始化标志
0x4c09c  tbz  w8, 0, 0x4c0a8       ; 已初始化 → 直接跳过
0x4c0a0  mov  w19, wzr ; b 0x4c174 ; 返回 0

0x4c0a8  bl   0x4c38c              ; ★ dladdr(self) 拿自身路径
0x4c0c4  add  x0, sp, 0x20
0x4c0c8  sub  x2, x29, 0x70
0x4c0d0  strb wzr, [sp, 0x21f]
0x4c0d8  bl   0x4baac              ; ★ 解析 ELF/找符号表
0x4c0e0  bl   0x6ec30              ; 取字段 A
0x4c0ec  bl   0x6ec30              ; 取字段 B
0x4c0f4  mov  w8, 0x3fffffe
0x4c0fc  cmp  w9, w8 ; b.hi 0x4c138 ; 范围检查
0x4c110  bl   0x6ec30              ; 取字段 C
0x4c11c  adr  x8, .ncks            ; 0x37f74
0x4c124  add  x8, x8, w19, uxtw    ; .ncks + A
0x4c128  sub  x0, x8, w0, uxtw     ; (.ncks + A) - C
0x4c12c  bl   0x4c034              ; ★ CRC32(区间, B)
0x4c134  str  w0, [0x9a740]        ; 存到全局

0x4c138  bl   0x4ba84              ; 收尾
0x4c13c  bl   0x4c38c              ; 再取自身路径
0x4c154  bl   0x4c3a4              ; strncpy(path, ..., 0x1ff)
0x4c164  bl   0x6eb90              ; ★ 打开并解析 APK

0x4c168  bl   0x933a0              ; ★★ 进入 .ncxh 反调试检测
0x4c170  cbz  w0, 0x4c18c          ; 通过 → 继续
0x4c174  ret                      ; 失败 → 返回（上层会处理）

0x4c1a4  strb w8, [0x9a738]        ; 标志位
0x4c1b0  bl   pthread_attr_init
0x4c1c4  adr  x2, 0x4c354          ; ★ 线程入口
0x4c1d4  bl   pthread_create       ; ★ 创建反调试线程
0x4c1f4  adr  x9, .ncxhr           ; 0x9a170
0x4c1f8  cmp  x8, 0x20
0x4c200  strb wzr, [x9, x8]        ; 清零 .ncxhr (32 字节)
```

**这个函数干了 6 件事**：
1. `dladdr` 拿自身路径（`/proc/self/root.../libnc.so`）
2. 解析自己的 ELF（`0x4baac`）
3. 用 `.ncks` + 三个字段算 CRC32 存全局
4. 重新取路径 → 打开 APK（`0x6eb90`）
5. 调 `0x933a0`（在 `.ncxh` 里）做反调试检测
6. `pthread_create` 起反调试线程，然后清零 `.ncxhr`

**`0x4c20c` 还在后面 `b 0x4c080`** —— 所以 `init_array[0]` 是个环形跳板，实际执行两遍（第二遍命中已初始化标志提前返回）。

## 第 13 课 破解流密码：黄金分割常数

### 13.1 找到算法

`0x4c834` 被三处调用：
```
0x4c900  bl 0x4c834    ← 0x4c8d8 里（读 LEB128 变长整数，两次）
0x4d160  bl 0x4c834    ← ★ 解释器主循环
```

### 13.2 算法全文

```asm
0x4c834  stp xzr, xzr, [sp, -0x10]!
0x4c838  mov  x8, 0x7c15
0x4c840  movk x8, 0x7f4a, lsl 16
0x4c844  movk x8, 0x79b9, lsl 32
0x4c848  movk x8, 0x9e37, lsl 48
         → x8 = 0x9e3779b97f4a7c15   ← ★ 64 位黄金分割常数 (2^64 / φ)

0x4c83c  mov  w9, 0xd              → w9 = 13
0x4c84c  ldr  x10, [x3]           → i = *ctx   (当前偏移)
0x4c850  cmp  x10, x1             → 与长度比较
0x4c854  b.hs 0x4c8cc             → 越界则退出

loop:
0x4c858  mul  w11, w10, w9        ; tmp   = i * 13          (32 位，自动取低位)
0x4c85c  mneg w12, w10, w9        ; tmp2  = -(i * 13)
0x4c864  lsl  x11, x2, x11        ; x11   = K << (i*13 % 64)
0x4c868  lsr  x12, x2, x12        ; x12   = K >> (-(i*13) % 64)
0x4c86c  orr  x11, x11, x12       ; x11   = ROL64(K, i*13)     ★ 旋转

0x4c860  mul  x13, x10, x8        ; x13   = i * GOLDEN
0x4c870  eor  x11, x11, x13       ; x11  ^= i * GOLDEN

0x4c874  ldrb w13, [x0, x10]      ; c     = buf[i]
0x4c878  eor  x11, x11, x10, ror 47   ; ^= (i ror 47)
0x4c87c  eor  x11, x11, x10, lsr 7    ; ^= (i >> 7)

0x4c880  add  x10, x10, 1
0x4c884  str  x10, [x3]           ; 回写 i

; ── 把 64 位密钥流折叠成 8 位 ──
0x4c888  lsr  x12, x11, 0x20
0x4c88c  eor  w12, w11, w12       ; w12 = lo32 ^ hi32
0x4c890  eor  w12, w12, w11, lsr 16
0x4c894  eor  w11, w12, w11, lsr 8 ; w11 = 折叠后 8 位
0x4c898  eor  w12, w13, w11       ; x = c ^ keybit

; ── 一个 byte 的位操作（反转/旋转）──
0x4c89c  sub  w11, w12, w11
0x4c8a0  and  w12, w11, 0xf8
0x4c8a4  lsr  w12, w12, 2
0x4c8a8  orr  w12, w12, w11, lsl 6
0x4c8ac  bfxil w12, w11, 2, 1
...
0x4c8c8  tbnz w12, 7, 0x4c84c     ; 若高位为 1 则跳回（变长编码！）
```

### 13.3 拆解结论

**密钥流生成**（这是核心，可独立复现）：

```
KS[i] = ROL64(K, (i*13) mod 64)
      ^ (i * 0x9e3779b97f4a7c15) mod 2^64
      ^ (i ror 47)
      ^ (i >> 7)

keybyte[i] = fold64_to_8(KS[i])      ; lo32^hi32, 再 ^(>>16), 再 ^(>>8)
```

**性质**：
| 性质 | 说明 |
|---|---|
| 类型 | **纯流密码**（密钥流只依赖 `i` 和种子 `K`，与明文无关） |
| 加解密 | **同一函数**（XOR 的自反性） |
| 种子 | 64 位 `K`，来自 `x2`（参数） |
| 常量 | `0x9e3779b97f4a7c15` = 黄金分割比例常数 |
| 明文相关 | 无（`ldrb w13, [x0, x10]` 只影响最后的组合，不影响密钥流） |

**为什么用黄金分割常数？**
这是 **splitmix64 / Fibonacci hashing** 的经典手法。它保证 `i * GOLDEN mod 2^64` 在 `i` 递增时均匀分布，避免低位相关性。作者显然懂 PRNG 设计。

**但这仍然不是"军用级"加密**：
- 没有 S 盒
- 没有多轮混合
- 密钥流是可预测的（知道 `K` 就全解）
- 而 `K` 是编译期常量，**就在 so 文件里**

### 13.4 后面的变长编码混淆

`0x4c898` 之后的代码把 1 个字节做了位重组，然后用 `tbnz w12, 7` 决定是否继续循环——这是 **LEB128 风格的变长解码**，`0x4c8d8` 就是它的外层封装（读 7 位、累积到 64 位）。

> 所以 `.ncx` 里存的不是裸字节码，而是 **"加密 + 变长编码"两层**。

### 13.5 这下能确认解释器了

`0x4d160` 处的调用点就是解释器主循环：

```asm
0x4d12c  adr  x24, 0xef08           ; ★ 跳转表基址
0x4d140  ldr  x8, [x19, 0xe8]       ; 读 PC
0x4d144  cmp  x8, x21
0x4d148  str  x8, [x19, 0xe0]
0x4d14c  b.hs 0x50738               ; PC 越界 → 结束
0x4d150  add  x0, x20, x27          ; code + base
0x4d154  orr  x2, x25, x28          ; ★ 密钥 K（拼出来的）
0x4d158  add  x3, x19, 0xe0         ; ctx
0x4d160  bl   0x4c834               ; ★ 解出 1 个操作码
0x4d164  sub  x8, x0, 1
0x4d168  cmp  x8, 0x9cd             ; 操作码范围 1 ~ 0x9ce (2509 个)
0x4d16c  b.hi 0x50738               ; 越界 → 结束
0x4d170  adr  x9, 0x4d134           ; 跳转表基准
0x4d174  ldrh w10, [x24, x8, lsl 1] ; ★ 16 位偏移
0x4d178  add  x9, x9, x10, lsl 2    ; base + off*4
0x4d17c  br   x9                    ; ★★ 二次间接跳转 → handler
```

**这就是第 12 课推测的"2509 个操作码的虚拟机"实锤**。跳转表在 `.rodata` 的 `0xef08`（`0x9ce * 2 = 0x139c` 字节）。

我解出前 24 个操作码的 handler 地址验证了一下：

```
opcode 0x001 → 0x4ed30      opcode 0x00d → 0x4d134  (= 0x4d134 即"空操作/loop")
opcode 0x002 → 0x4d2d0      opcode 0x011 → 0x4d180  (PC += 0x20)
opcode 0x003 → 0x4faf8      opcode 0x016 → 0x4d180
opcode 0x007 → 0x4d2a0      opcode 0x00c → 0x4d2a0  (PC += 0x8)
opcode 0x009 → 0x4d364
```

可以看到 handler 结构高度重复（`PC += N; b loop`）——**这是字节码解释器的典型特征**：每个操作码对应"推进 PC + 执行语义"。

### 13.6 本课结论

| 项 | 结论 |
|---|---|
| 加密段 | `.ncx`(0x1ac0) + `.ncxh`(0xc20) + `.ncxr` |
| 加密算法 | **自研流密码**，密钥流用黄金分割常数混合 |
| 增强层 | 加密后再套一层 **LEB128 变长编码** |
| 执行方式 | **2509 操作码的字节码解释器**，跳转表在 `0xef08` |
| 解释器位置 | `0x4d134` 起，主循环在 `0x4d140` ~ `0x4d17c` |
| 破解路径 | 拿到 64 位种子 `K` → 解密 → 得字节码 → 反汇编字节码 |

**保护强度重新评估**：这是**商业级代码虚拟化（VMP）**，不是简单加密。2509 个操作码说明它的字节码 ISA 相当完整（能跑 Compose 主题框架）。

## 第 14 课 反调试三件套

`0x4c354` 是 `pthread_create` 的线程入口：

```asm
0x4c354  sub  sp, sp, 0x30
0x4c360  adrp x8, 0xd000
0x4c364  ldr  q0, [x8, 0x4e0]        ; ★ 从 .rodata 加载 16 字节 = timespec
0x4c368  str  q0, [sp]               ; 存到栈
0x4c370  add  x0, sp, 0x10
0x4c374  mov  x1, xzr
0x4c37c  bl   nanosleep              ; ★ 睡！

loop:
0x4c380  bl   0x92e0c                ; ★ 调 .ncxh 里的检测函数
0x4c384  cbnz w0, 0x4c36c            ; 返回非 0 → 继续睡+检测（无限循环）
0x4c388  brk  1                      ; ★★★ 返回 0 → brk #1 → SIGTRAP → 崩溃
```

### 14.1 睡眠时长

我直接读了 `0xd4e0` 处的 16 字节：

```
1900000000000000  0000000000000000
→ timespec { tv_sec = 25, tv_nsec = 0 }
```

**25 秒**。

所以逻辑是：**每 25 秒检测一次，检测通过（返回非 0）就继续，检测失败（返回 0）就 `brk #1` 自杀。**

> 这和 Java 层的 5 秒心跳（`Thread.sleep(5000)`）是**两套独立机制**：
> - **Java 心跳**（5 秒）：`heartbeat()`，防的是 App 逻辑被替换
> - **native 反调试**（25 秒）：`0x92e0c`，防的是调试器/注入

### 14.2 `brk #1` 而不是 `abort()`

```asm
0x4c388  brk 1
```

**为什么用 `brk` 而不是 `abort()`？**

| | `abort()` | `brk #1` |
|---|---|---|
| 依赖 | libc，可被 hook | 单条指令，无法 hook |
| 信号 | SIGABRT | **SIGTRAP** |
| 混淆效果 | 崩溃日志里明确写 `abort` | 看起来像**硬件断点触发**，误导分析者 |
| 调试器 | 能拦 | **调试器会认为是你自己下的断点** |

这是**反调试的心理战**：如果你挂着 gdb/lldb，看到 SIGTRAP 第一反应是"我自己设的断点？"，而不是"程序在自杀"。

### 14.3 反调试线程的自我保护

```asm
0x4c18c  adrp x9, 0x9a000
0x4c190  add  x9, x9, 0x734       ; 标志区
0x4c194  mov  w8, 1
0x4c198  ldrb w10, [x9, 4]        ; 读 flags[4]
0x4c19c  strb w8, [x9]            ; flags[0] = 1
0x4c1a0  tbnz w10, 0, 0x4c1e0     ; 已启动 → 跳过
0x4c1a8  strb w8, [x9, 4]         ; flags[4] = 1
0x4c1b0  bl   pthread_attr_init
0x4c1bc  bl   pthread_attr_setdetachstate(attr, 1)   ; PTHREAD_CREATE_DETACHED
0x4c1c4  adr  x2, 0x4c354
0x4c1d4  bl   pthread_create
0x4c1dc  bl   pthread_attr_destroy
0x4c1f4  adr  x9, .ncxhr          ; 0x9a170
0x4c1f8  cmp  x8, 0x20
0x4c200  strb wzr, [x9, x8]       ; 清零 .ncxhr 32 字节
```

三个细节：
- **`PTHREAD_CREATE_DETACHED`**：线程不可 `join`，也不留句柄。你想暂停它就得扫描所有线程。
- **双重标志位**（`flags[0]` 和 `flags[4]`）：防止线程被 kill 后重复启动，也防止只改一处就绕过。
- **清零 `.ncxhr`**：这是 `.ncxhr` 段（32 字节）的用途——**存敏感状态，用完即清**。

### 14.4 三件套总览

| # | 机制 | 位置 | 周期 | 失败后果 |
|---|---|---|---|---|
| 1 | Java 心跳 | `NativeGuard.Hb` | 5 秒 | 无（仅维持） |
| 2 | native 反调试 | `0x4c354` 线程 | 25 秒 | **`brk #1` → SIGTRAP** |
| 3 | 启动自检 | `init_array[0]` | 1 次 | CRC32 不匹配 → 后续走错分支 |

## 第 15 课 `.ncks` 的真实用途：CRC32 校验锚点

### 15.1 它不是密钥，是锚点

之前我猜 `.ncks` 是 3 个 SHA-256 摘要。**错了**。真实用途在 `0x4c11c`：

```asm
0x4c11c  adr  x8, .ncks          ; 0x37f74 ← .ncks 段的地址
0x4c120  mov  w1, w20            ; 长度 B（来自 ELF 某个字段）
0x4c124  add  x8, x8, w19, uxtw  ; .ncks + A
0x4c128  sub  x0, x8, w0, uxtw   ; (.ncks + A) - C   ★ 三个整数算地址
0x4c12c  bl   0x4c034            ; CRC32(那个地址, 长度 B)
0x4c134  str  w0, [0x9a740]      ; 存全局
```

**`.ncks` 的地址被当作"基址锚点"**，用三个整数 `A/B/C` 算出一个区间，然后对它算 CRC32。

- `ks` = **K**nown **S**ignature 或 check**S**um，不是 key
- 三个整数来自 **ELF 自身解析结果**（`0x4baac` 解析后再由 `0x6ec30` 三次取值）
- 这解释了第 1 课看到的 `dl_iterate_phdr` / `getauxval`：**壳在读自己的 ELF 头，算运行时自校验**

> 这是**自校验（self-integrity check）**：如果你改了 so 里任何字节，CRC32 就变，`0x9a740` 的值就错，后面所有依赖它的解密都会得到垃圾。

### 15.2 我尝试暴力解 A/B/C —— 失败了

思路：把 `.ncks`/`.nck`/`.ncxr` 里所有 u32/u64 当候选，暴力 `A×B×C` 三元组，看哪个能算出等于某个已知常量。

```python
cands = {全部 u32/u64}     # 141 个
targets = {全部 u32 常量}  # 72 个
for A in cands:
  for C in cands:
    for B in cands:
      if crc32(file[ncks+A-C : ...+B]) in targets: ...
```

**结果：0 个匹配。**

### 15.3 为什么失败 + 下一步

失败原因是我的假设太窄：
1. **A/B/C 不一定来自那 96 字节**——它们更可能是 `0x4baac` 解析 ELF 得到的**段偏移/大小**（比如 `.text` 的 offset/size）
2. 我假设了 `crc32 结果 == 某个 .ncks 里的常量`，但实际上结果存在 `0x9a740`，**可能根本不和任何常量比较**（只是被后续解密当作密钥材料用）

**正确的下一步**（记录下来，供继续）：
- 读 `0x4baac` 和 `0x6ec30`，搞清 A/B/C 到底取自 ELF 哪个字段
- 然后直接算出目标区间，验证 CRC32
- 或者走**动态路线**：在 `0x4c12c` 下断点，直接读寄存器 `x0`/`w1`

**这也是逆向的常态**：一条路走死了，就把死因记下来，换条路。



## 第 16 课 密钥派生被拆成 13 份副本

### 16.1 发现

在 `0x4ca94`（解释器主函数）里，看到大量 `mov/movk` 拼常量的序列。把这些常量的**高 16 位**提出来搜：

```bash
for p in 0x9e37 0xbf58 0x94d0; do grep -c "$p" dis.txt; done
```

```
0x9e37 : 33 次    ← 0x9e3779b97f4a7c15 的低半部分
0xbf58 : 13 次    ← 0xbf58476d1ce4e5b9
0x94d0 : 13 次    ← 0x94d049bb133111eb
```

**这三个都是 splitmix64 的官方常量：**

```
GOLDEN = 0x9E3779B97F4A7C15
MUL1   = 0xBF58476D1CE4E5B9
MUL2   = 0x94D049BB133111EB
```

而 `0xbf58` / `0x94d0` 各出现 **13 次，每次地址不同**：

```
0x4cc00 / 0x50b38 / 0x54a48 / 0x577c0 / 0x58a98 / 0x5c3ec
0x5f154 / 0x605dc / 0x63ff0 / 0x66cc8 / ...
```

### 16.2 这是「KDF 复印件」

**同一段密钥派生逻辑被手工复制粘贴了 13 份**，插在解释器不同位置。

**技术目的：**
1. **消灭函数边界** —— 没有 `bl <kdf>`，就没有"KDF 函数"这个东西可分析
2. **消灭符号** —— 反汇编器不会给它起名，静态搜 `sub sp` 找不到
3. **增加工作量** —— 每份嵌在不同上下文，寄存器分配不同，不能批量处理
4. **抗 hook** —— hook 住第 1 份，还有 12 份

> 这是**对抗「函数级逆向」**的标准手法。正常流程是"找关键函数 → 读懂 → 打补丁"，现在这个流程被彻底破坏。

### 16.3 解出的一层结构

以 `0x4cb18` 那段为例：

```asm
0x4cae0  mov  x8, 0x7538
0x4cae4  movk x8, 0xbc2f, lsl 16
0x4caf8  movk x8, 0x3573, lsl 32
0x4cb04  movk x8, 0x0ab3, lsl 48
         → x8 = 0x0ab33573bc2f7538
0x4cb18  eor  x8, x8, x0, ror 38      ; ★ 旋转异或，把输入混进来

0x4cb00  x9  = 0xf1de83e19937733d
0x4cb0c  x10 = 0x8d0622192e06eab8
0x4cb2c  madd x10, x8, x9, x10        ; ★ 乘加
0x4cb54  cmp  x10, 0xb                ; ★ 约束到 [0, 11]
0x4cb64  b.hi 0x50738                 ; 越界 → 失败退出
```

关键点：
- `eor x8, x8, x0, ror 38` —— **旋转异或**，把输入折进常量
- `madd x10, x8, x9, x10` —— 乘加混合
- 结果被约束在 `[0, 11]` 区间，说明这层是**索引/选择器**（12 路）

### 16.4 后续是展开的 splitmix64

```asm
0x4cbf8  movk x8, 0x9e37, lsl 48      ; x8 = GOLDEN
0x4cc04  add  x14, x14, x8            ; + GOLDEN
0x4cc0c  add  x0,  x0,  x8            ; + GOLDEN
0x4cc10  eor  x1,  x14, x14, lsr 30   ; ^ (x >> 30)
0x4cc84  mul  x1,  x1,  x11           ; * MUL2
0x4cc90  eor  x17, x17, x17, lsr 27   ; ^ (x >> 27)
0x4cc94  mul  x3,  x3,  x11
```

对照 splitmix64 标准实现：

```c
uint64_t next() {
    uint64_t z = (s += 0x9E3779B97F4A7C15);    // add GOLDEN
    z = (z ^ (z >> 30)) * 0xBF58476D1CE4E5B9;  // eor>>30, mul MUL1
    z = (z ^ (z >> 27)) * 0x94D049BB133111EB;  // eor>>27, mul MUL2
    return z ^ (z >> 31);                       // eor>>31
}
```

**结构完全对应** —— 只是被展开成内联指令。你没法 `bl splitmix` 去 hook。

### 16.5 种子链的疑点

`0x4cb18` 用的 `x0` 已经是"上一层输出"。函数入口：

```asm
0x4ca94  sub  sp, sp, 0x610
0x4caac  mov  x26, x1              ; 参数 1
0x4cab0  str  xzr, [x19, 0xe8]     ; 清零 PC
```

如果这是 JNI 入口，`x0` 是 `JNIEnv*`；但这里被当整数参与运算——**疑似拿运行时指针当种子**。

> 这有个矛盾点：如果用 `JNIEnv*` 当种子，每次运行地址不同，App 就无法解密自己的字节码。
> **所以后面一定存在"消掉运行时随机性"的操作**（比如只取低几位、或用它和另一个运行时值做 XOR 相互抵消）。
> 这也是下一步必须精确复原 KDF 的原因。

### 16.6 重要修正：字节码在 `.rodata`，不在 `.ncx`

第 13 课我推测代码在 `.ncx`。**这里修正**——`0x4d064` 给出了硬证据：

```asm
0x4d064  adr  x20, 0x1da70          ; ★ 解释器基址
0x4d150  add  x0, x20, x27          ; code + offset
```

`0x1da70` 在 **`.rodata`** 里（`.rodata` = `0xaea0 ~ 0x37f14`）。实际内容：

```
0x1da70:  a8 4e fd bb 74 b3 2f a6 35 3e 6b 7c 2c c0 58 00
          70 30 20 00 00 00 00 00 00 00 00 00 00 00 00 00 ...
0x1da9c:  26 b4 00 00 01 dc 10 38 38 80 f0 20
```

「随机字节 + 零填充 + 小整数」的布局，像**结构化字节码容器头部**。

**修正后的段用途表：**

| 段 / 区域 | 大小 | 真实用途 |
|---|---|---|
| `.ncx` (0x913fc) | 0x1ac0 | 少量真实代码（`0x91400` 等）+ **大量诱饵密文** |

| `.nck` (0x37fe4) | 0x60 | 待确认（疑似密钥碎片） |
| **`.rodata+0x1da70`** | ? | **字节码主体** ← 修正 |

### 16.7 本课方法论

**① 常量识别比算法识别快 10 倍。**
`0x9E3779B97F4A7C15` → splitmix / Fibonacci hashing
`0xEDB88320` → CRC-32
`6A09E667 BB67AE85` → SHA-256 IV

1 份 = 普通实现，`bl` 一下就能 hook。

## 第 17 课 一个检验决定了解密成本

### 17.1 问题

第 13 课解出 `0x4c834` 的密钥流公式：

```
KS[i] = ROL64(K, i*13) ^ (i*GOLDEN) ^ (i ror 47) ^ (i >> 7)
keybyte[i] = fold64_to_8(KS[i])
```

**但「公式里有 `buf[i]` 参与运算」这件事，可能意味着两种截然不同的密码：**

| 类型 | 特征 | 解密成本 |
|---|---|---|
| **纯 XOR 流密码** | `c[i] = b[i] ^ KS[i]`，`KS` 只依赖 `(K, i)` | 任一点可独立解密，随机访问 |
| **反馈式（CBC 类）** | `c[i] = f(b[i], c[i-1], KS[i])` | **必须从头顺序解** |

差别巨大：前者可以只解 `.ncx` 里需要的 20 字节；后者必须从段首开始完整跑完。

### 17.2 用"差分检验"判定

如果 `KS[i]` 与明文无关，那么对任意两个明文 `P1`、`P2`：

```
Enc(P1)[i] ^ Enc(P2)[i]
  = (P1[i] ^ KS[i]) ^ (P2[i] ^ KS[i])
  = P1[i] ^ P2[i]
```

**密文差分 == 明文差分** —— 这是纯 XOR 流的充要特征。

```python
M = (1<<64)-1
def keybyte(K, i):
    G = 0x9E3779B97F4A7C15
    r = (i*13) % 64
    ks = ((K<<r)|(K>>(64-r))) & M if r else K      # ROL64
    ks ^= (i*G) & M
    ks ^= ((i>>47)|(i<<17)) & M                    # ror 47
    ks ^= (i>>7) & M                               # lsr 7
    v = (ks ^ (ks>>32)) & 0xffffffff
    v = (v ^ (ks>>16)) & 0xffffffff
    v = (v ^ (ks>>8))  & 0xffffffff
    return v & 0xff

K = 0x123456789abcdef0
P1 = bytes(range(32))
P2 = bytes((b*7+3) & 0xff for b in range(32))
C1 = bytes(P1[i] ^ keybyte(K,i) for i in range(32))
C2 = bytes(P2[i] ^ keybyte(K,i) for i in range(32))

all((P1[i]^P2[i]) == (C1[i]^C2[i]) for i in range(32))
```

结果：

```
纯XOR流密码(可分离): True
```

**结论：`0x4c834` 是纯 XOR 流密码，可以随机访问、跳着解。**

### 17.3 但还有第二层

`0x4c888` 之后对每个解出的字节又做了位重组：

```asm
0x4c89c  sub  w11, w12, w11
0x4c8a0  and  w12, w11, 0xf8
0x4c8a4  lsr  w12, w12, 2
0x4c8a8  orr  w12, w12, w11, lsl 6
0x4c8ac  bfxil w12, w11, 2, 1
0x4c8c8  tbnz w12, 7, 0x4c84c      ; ★ 高位为 1 就回循环
```

`tbnz w12, 7` —— 用最高位决定是否继续读下一个字节。**这是 LEB128 变长整数解码。**

所以实际数据布局是：

```
.nc / .rodata 密文 ──XOR 流解密──▶ 变长 token 流 ──LEB128 解码──▶ 字节码指令
```

**两层叠加意味着：**
- 第 1 层（XOR）：可随机访问 ✅
- 第 2 层（LEB128）：**必须从头顺序解** ❌

**所以整体仍然必须从段首开始解。** 第 17.2 节的检验只证明"第一次解密无需顺序"，不能省掉 LEB128 的顺序成本。

> 这是个典型的**逆向中"证明了一半"的场景**：
> 局部结论成立（XOR 层可分离），但对整体目标（解密字节码）没有帮助，因为第二层强制顺序。
> **必须把这个限制如实记下来，而不是拿"可分离"去误导后续工作。**

### 17.4 字节码区的实际观感

```python
seg = libnc[0x1da70 : 0x1da70+0x200]
# 非零字节 158 / 512
```

稀疏、有大片 0x00。这不像"高熵密文"，更像**结构化容器**：

```
0x1da70: a8 4e fd bb 74 b3 2f a6 35 3e 6b 7c 2c c0 58 00   ← 疑似头部
0x1da80: 00 × 16
0x1da90: 00 00 00 00 00 00 00 00 00 00 00 00 26 b4 00 00   ← 疑似长度字段
0x1da9c: 01 dc 10 38 38 80 f0 20
```

`26 b4 00 00` = `0xb426` = 46118。可能是**字节码总长度或条目数**。
这需要解密后才能确认，属于下一步工作。

### 17.5 本课方法论

**在按下"开始写解密脚本"之前，先做一个 10 行代码的可行性检验。**

花 2 分钟就能判断：
- 是不是纯 XOR（能跳着解）
- 有没有反馈（必须顺序解）
- 有没有二层编码（顺序成本更高）

**这个检验的价值在于：避免花 3 小时写一个跑不通的解密器。**

## 第 18 课 密码算法完全复原（含两个变体）

### 18.1 发现：同一套算法有两个版本

追踪 `0x4c9fc` 时发现它调用的是 `0x4c96c`，而**不是** `0x4c834`。两个函数**几乎逐行相同**，只差一段：

```asm
; ───────── 变体 A @ 0x4c834 ─────────
0x4c888  lsr  x12, x11, 0x20
0x4c88c  eor  w12, w11, w12          ; 折叠 64→32
0x4c890  eor  w12, w12, w11, lsr 16
0x4c894  eor  w11, w12, w11, lsr 8   ; 折叠 32→8
0x4c898  eor  w12, w13, w11          ; ★ t = c ^ key
0x4c89c  sub  w11, w12, w11          ; ★★ t = t - key     ← A 独有
0x4c8a0  and  w12, w11, 0xf8         ; ┐
0x4c8a4  lsr  w12, w12, 2            ; │
0x4c8a8  orr  w12, w12, w11, lsl 6   ; ├ 位重排        ← A 独有
0x4c8ac  bfxil w12, w11, 2, 1        ; │
0x4c8c8  tbnz w12, 7, 0x4c84c        ; ┘ LEB128 控制

; ───────── 变体 B @ 0x4c96c ─────────
0x4c9c0  lsr  x12, x11, 0x20
0x4c9c4  eor  w12, w11, w12
0x4c9c8  eor  w12, w12, w11, lsr 16
0x4c9cc  eor  w11, w12, w11, lsr 8   ; 折叠 32→8
0x4c9d4  eor  w11, w13, w11          ; ★ 直接 x = c ^ key
0x4c9d8  and  x13, x11, 0x7f         ; 取 7 位
0x4c9dc  lsl  x13, x13, x12          ; << shift
0x4c9e4  orr  x10, x14, x13          ; 累积
0x4c9ec  tbnz w11, 7, 0x4c984        ; LEB128 控制
```

**变体 A 多了「减 key」和「位重排」两步。**

### 18.2 那层"位重排"到底是什么

`0x4c8a0` ~ `0x4c8ac` 看着很绕，我用 Python 逐位验证：

```python
def perm(t):
    t &= 0xff
    a = ((t & 0xF8) >> 2) | ((t << 6) & 0xC0)
    a = (a & ~1) | ((t >> 2) & 1)
    return a & 0xff

len(set(perm(i) for i in range(256))) == 256    # True → 是双射
```

位映射表：

```
out[0] <- in[2]      out[4] <- in[6]
out[1] <- in[3]      out[5] <- in[7]
out[2] <- in[4]      out[6] <- in[0]
out[3] <- in[5]      out[7] <- in[1]
```

**就是把字节循环右移 2 位（ROR8 by 2）。** 作者用 4 条指令写了个 `ror`，还掺了 `bfxil`，纯粹是为了让人一眼看不出来。

### 18.3 完整算法（可执行代码）

```python
M64 = (1 << 64) - 1
GOLDEN = 0x9E3779B97F4A7C15

def keybyte(K, i):
    """索引 i 处的 8 位密钥流字节"""
    r = (i * 13) % 64
    ks = ((K << r) | (K >> (64 - r))) & M64 if r else K   # ROL64(K, i*13)
    ks ^= (i * GOLDEN) & M64                              # 混合乘法
    ks ^= ((i >> 47) | ((i << 17) & M64)) & M64           # ^ (i ror 47)
    ks ^= (i >> 7) & M64                                  # ^ (i >> 7)
    v = (ks ^ (ks >> 32)) & 0xffffffff                    # 折叠 64→32
    v = (v ^ (ks >> 16)) & 0xffffffff
    v = (v ^ (ks >> 8))  & 0xffffffff
    return v & 0xff                                       # 折叠 32→8

def dec_A(c, K, i):        # 变体 A：0x4c834
    k = keybyte(K, i)
    t = ((c ^ k) - k) & 0xff
    return ((t >> 2) | (t << 6)) & 0xff      # ROR8 2

def dec_B(c, K, i):        # 变体 B：0x4c96c
    return c ^ keybyte(K, i)
```

**互逆性验证通过：**
```python
enc_A = lambda p,K,i: ((((p << 2) | (p >> 6)) & 0xff) + keybyte(K,i)) & 0xff ^ keybyte(K,i)
all(enc_A(dec_A(x,K,i),K,i) == x for x in range(256) for i in [0,7])   # True
```

### 18.4 两者的分工

| 变体 | 地址 | 额外变换 | 用途推断 |
|---|---|---|---|
| **A** | `0x4c834` | `-k` + `ROR8 2` | 解释器主循环（`0x4d160`）—— 解操作码 |
| **B** | `0x4c96c` | 无 | `0x4c9fc` 循环调用 —— 解**变长整数/表项** |

`0x4c9fc` 的逻辑：

```asm
0x4c9fc  sub  sp, sp, 0x40
0x4ca24  bl   0x4c96c              ; 先读 1 个（拿"总长度"）
0x4ca28  cmp  x19, x0
0x4ca2c  b.hs 0x4ca60              ; 目标偏移 >= 总长度 → 直接返回

loop:
0x4ca40  bl   0x4c96c              ; 再读 1 个
0x4ca44  ldr  x8, [sp, 8]          ; 当前偏移
0x4ca48  cmp  x8, x19
0x4ca4c  b.eq 0x4ca5c              ; 到达目标 → 保存并返回
0x4ca50  add  x8, x8, 1
0x4ca58  b    0x4ca30              ; 继续
```

**这是"跳转到第 N 个 token"的函数。** 变体 B 用于**索引/导航**，变体 A 用于**取指令**。

### 18.5 为什么用两个变体

这是个相当聪明的设计：

1. **导航必须能跳着做**（变体 B 简单快速）
2. **取指令需要更强的混淆**（变体 A 加了减法 + 旋转）
3. **两个变体共享同一份密钥流** —— `keybyte(K,i)` 完全相同

**结果：** 你即使破了变体 B（简单的那个，更容易看出来），也解不出指令——因为指令用的是变体 A。

> **这是一个"分层打破"的陷阱**：让分析者以为"算法就这么简单"，然后在关键处换一版。

### 18.6 关键技术总结

| 项 | 结论 |
|---|---|
| 算法类型 | 纯 XOR 流密码 + 可选的 `-k` / `ROR8 2` |
| 密钥流 | `keybyte(K,i)`，与明文无关（可分离、可随机访问） |
| 常量 | `GOLDEN = 0x9E3779B97F4A7C15` |
| 差异因子 | `i*13` 旋转 + `i*GOLDEN` 乘法 + `i ror 47` + `i >> 7` |
| 折叠 | 64 → 32 → 8，三次异或移位 |
| 变体 A | `ROR8((c^k)-k, 2)` |
| 变体 B | `c ^ k` |
| 外层 | LEB128 变长编码（`tbnz w11, 7` 控制续读） |
| 剩余未知 | **只有 64 位种子 `K`** |

### 18.7 现在只差 K

算法 100% 复原了。剩下的唯一未知量是 **64 位种子 `K`**。

**两个获取路径：**

**路径 1（静态）**：读 `0x4ca78` 函数（`0x4ca94` 是它的序言）开头的 KDF 那 13 份副本，把 `x25`/`x28` 的值算出来。难点是那份 KDF 里混了 `x0`（疑似 `JNIEnv*`），需要找到"消掉运行时随机性"的那一步。

**路径 2（动态，更稳）**：在 `0x4d154`（`orr x2, x25, x28`）下单点断，直接读 `x2`。
```python
# Frida 伪代码
Interceptor.attach(ptr(base + 0x4d154), {
    onEnter: function() { console.log("K = 0x" + this.x25.or(this.x28).toString(16)); }
});
```
或者更简单：hook `0x4c834` 的调用点，直接 dump 解密后的 buffer。

**推荐路径 2。** 理由：K 的 KDF 被拆成 13 份 + 混入运行时值，静态还原是纯体力活且容易出错；动态一句话就拿到了。

## 第 19 课 VMP 确认：以及我的三次自我纠正

### 19.1 铁证一：dispatch 表 2510 项，只有 94 个唯一 handler

```python
offs = [u16(so, 0xef08 + i*2) for i in range(0x9ce)]
uniq = sorted(set(0x4d134 + o*4 for o in offs))
```

```
表项数（操作码空间）   2510
唯一 handler 数        94
复用比                26.7x
handler 地址范围      0x4d134 ~ 0x50738
```

**其中 1510 项（60.2%）指向同一个地址 `0x50738`** —— 那是 `0x4d14c b.hs` 的越界/失败出口。

**这是 VMP 的经典手法**：人为把操作码空间撑到 2510，让逆向者以为要分析 2510 个 handler，实际只有 94 个，且 60% 是垃圾填充。

被复用最多的几个 handler：

```
0x50738  被 1510 个操作码映射（60.2%）  ← 陷阱/退出
0x4d180  被 116 个映射（4.6%）
0x4d134  被 114 个映射（4.5%）          ← 空操作/loop 头
0x4ee8c  被 111 个映射（4.4%）
0x4faf8  被 103 个映射（4.1%）
```

### 19.2 铁证二：操作码是 LEB128 变长，不是 1 字节

派发序列（`0x4d160` ~ `0x4d17c`）：

```asm
0x4d160  bl   0x4c834          ; 解出 1 个字节
0x4d164  sub  x8, x0, 1
0x4d168  cmp  x8, 0x9cd        ; 与表长比较
0x4d16c  b.hi 0x50738          ; 越界 → 退出
0x4d170  adr  x9, 0x4d134      ; handler 基准
0x4d174  ldrh w10, [x24, x8, lsl 1]  ; 16 位相对偏移
0x4d178  add  x9, x9, x10, lsl 2
0x4d17c  br   x9               ; ★ 二次间接跳转
```

而 `0x4c834` 的解码尾部：

```asm
0x4c8b4  and  x13, x12, 0x7f      ; 取低 7 位
0x4c8b8  lsl  x13, x13, x11       ; << shift（起始 0）
0x4c8bc  add  x11, x11, 7         ; shift += 7
0x4c8c0  orr  x10, x14, x13       ; 累积到 x10
0x4c8c8  tbnz w12, 7, 0x4c84c     ; 最高位=1 → 继续读
0x4c8cc  ldr  x0, [sp, 8]         ; 返回
```

**`x11` 从 0 起每次 +7，`tbnz` 高位控制续读 —— 这是标准 LEB128。** 操作码宽度 = 1~5 字节，所以 2510 个操作码完全合理。

### 19.3 铁证三：VM 状态对象在堆上，不是栈上

`0x4ca94` 开头 `sub sp, sp, 0x610`（1552 字节栈帧），但指令里出现：

```
str x8, [x19, 0x1330]
```

**`0x1330` 远超 0x610 帧大小。** 说明执行过程中 `x19` 被重新指向了一个**堆分配的 VM 状态对象**（0x1300+ 字节）。

VM 状态里的关键字段（Unicorn 实测）：

```
ctx+0x0a8 = 0x11
ctx+0x0c0 = 0xb
ctx+0x0d0 = 0x8
ctx+0xe0  = 0x1eb     ← 当前 PC（VM 指令指针）
ctx+0xe8  = 0x1e4     ← 上一 PC
```

`str x8, [x19, 0xe0]` 就是主循环里更新 PC 的那句，完全对应。

### 19.4 我这一轮推翻了自己三个判断

| 之前的判断 | 实际 | 依据 |
|---|---|---|
| "操作码是 1 字节，2509 个是夸大" | ❌ 是 **LEB128 变长 1~5 字节**，2510 个确认 | `0x4c8b4` 的 7 位累积 + `tbnz` 续读 |
| "629 KB 太小，没有虚拟化引擎" | ❌ 有，VMP 特征完整 | 2510 项表 + 94 handler + 堆状态对象 |
| "`0x9cd` 筛不出东西所以无约束" | ❌ 它是**表长边界**，约束 LEB128 解码后的值 | `sub x8,x0,1; cmp x8,0x9cd; b.hi` |

> **教训**：`cmp xN, K` 不能想当然理解成"比较操作码值"。要看 `xN` 此刻是什么、`K` 在这段代码里扮演什么角色。这里 `K` 是数组长度边界，不是值域上界。

### 20.3 关键一步：应用 R_AARCH64_RELATIVE

```python

```

应用 **1572 条**之后：

```
GOT[0x98fe0]     -> 0x60000300            (open 桩)
```

```asm
0x6eb4c  mov  x9, 0x2231
```

**这也是我第 13 课"算法 100% 复原"的真实成色**：公式的形状对了，但**最关键的一个参数（索引语义）错了**。套错参数等于没解出。

### 21.4 下一步很明确

按 `0x4c834` 里 `ldr x10, [x3]` 的真实含义重标定索引，重新验证那 16 条轨迹。**16/16 对上，就等于拿到了可离线运行的字节码解码器。**

## 第 22 课 libc 桩：VM 的第一条指令是 `open()`

### 22.1 VM 跑起来之后的调用链

应用重定位后，VM 主循环终于执行：

```asm
0x4d134  ldr  x8, [x19, 0xe8]     ; 取 PC
0x4d140  cmp  x8, x21             ; 越界?
0x4d14c  b.hs 0x50738
0x4d150  add  x0, x20, x27        ; 密文基址 + 偏移
0x4d154  orr  x2, x25, x28        ; ★ 钥匙
0x4d158  add  x3, x19, 0xe0       ; 流状态
0x4d160  bl   0x4c834             ; 解出 1 个操作码
0x4d164  sub  x8, x0, 1
0x4d168  cmp  x8, 0x9cd
0x4d16c  b.hi 0x50738
0x4d170  adr  x9, 0x4d134
0x4d174  ldrh w10, [x24, x8, lsl 1]
0x4d178  add  x9, x9, x10, lsl 2
0x4d17c  br   x9                  ; 派发
```

派发后走到：

```
0x4c430  str x30, [sp, #-0x10]!
0x4c434  bl  #0x4bca4
0x4bca4  sub sp, sp, #0xd0 ... 序言
0x4bcc4  mov x20, x1              ; x1 = 参数
0x4bcc8  mov w1, wzr              ; x1 = 0
0x4bccc  bl  #0x93e00             ; ★ open(x0, 0)
0x93e00  adrp x16, 0x98000
0x93e04  ldr  x17, [x16, 0xfe0]   ; GOT[open]
0x93e08  add  x16, x16, 0xfe0
0x93e0c  br   x17
```

**`0x93e00` 是 `open` 的 PLT 桩**（不是我一开始以为的 `.ncxh` 加密代码）。

### 22.2 而参数是错的，而且错得很有信息量

```
open(a0 = 0x10102464c457f)
```

拆开这 8 字节：

```
0x7f 0x45 0x4c 0x46 0x02 0x01 0x01 0x00
      └────┴────┴───── "ELF"
                            EI_CLASS=2  EI_DATA=2 ... "ELF" 头
```

**这是 libnc.so 自己的 ELF 头前 8 字节。** VM 把"文件内容首 8 字节"当成了路径名传给 `open`。

来源：

```asm
0x4f80c  add  x8, x19, #0x508        ; VM 虚拟寄存器堆
0x4f814  ldr  x0, [x8, x11, lsl #3]  ; x0 = 虚拟寄存器[x11]
```

**VM 虚拟寄存器里的值应该是路径指针，但它是 0**，于是读到了 so 基址（文件偏移 0 = ELF 头）。

### 22.3 根因：我漏了 x2 参数块

VM 寄存器是在 KDF 阶段从 `x2` 指向的结构体初始化的：

```asm
0x4d078  ldr  x15, [x2, 0x10]
0x4d08c  str  x15, [x19, 0x518]
0x4d0b4  ldur q0, [x2, 0x18]
0x4d0c0  ldr  x14, [x2, 0x28]
0x4d0fc  ldp  x11, x14, [x2, 0x50]
0x4d104  ldp  x15, x10, [x2, 0x60]
0x4d10c  ldp  x9,  x8,  [x2, 0x70]
```

**我从 `0x4ca78` 直接起跑，从没设过 `x2`。** 所以 V0~V7 全是垃圾。

正确入口应该是 `0x4baac`（它 `sub x2, x29, 0x10` 造出参数块，调 `0x6eb3c` → `0x4ca78`）：

```asm
0x4baac  sub  sp, sp, 0x150
0x4bac4  mov  x19, x2
0x4bad8  adr  x9, .ncks             ; 0x37f74
0x4bae4  逐字节拷 .ncks[0:8] → x19
0x4baf8  adr  x20, .ncks
0x4bb00  adr  x1, 0xeef8
0x4bb08  bl   0x6ed74               ; 魔数比对
0x4bb0c  cbz  w0, 0x4bb38           ; 相等 → 拷 0x70 字节
0x4bb10  mov  w0, -1                ; 不等 → 失败
0x4bb1c  sub  x2, x29, 0x10         ; ★ x2 = 栈上参数块
0x4bb20  mov  x0, x22
0x4bb24  mov  x1, x21
0x4bb28  bl   0x6eb3c
```

### 22.4 libc 桩的做法

给 `.got.plt` 的 84 个槽位逐一重定向到桩页，桩页面填 `RET`，再挂 code hook：

```python
for slot, name in jmpslots.items():
    stub = STUB_BASE + i * 0x10
    mu.mem_write(slot, pack('<Q', stub))
    handlers[stub] = name
mu.mem_write(STUB_BASE, RET_ENC * 0x4000)   # 填 RET
```

**一次踩的坑**：`readelf -rW` 的 `R_AARCH64_JUMP_SLOT` 行，`rest` 字段形如 `"0000000000000000 open + 0"`，直接 `split('@')[0]` 会把 `Symbol's Value` 列一起吞进来。要遍历 token 找第一个合法标识符。

## 第 23 课 战略复盘：为什么"一个段都没解开"

### 23.1 死磕最终段，是顺序错误

用户纠正了我一个致命战略错误：**`.ncx` 是最终段（代码体），`.ncxh` 要先解其他段才能解。**

依赖链实际是：

```
.ncks（锚点/魔数 112B）
   ↓
.nck（96B，疑似密钥）
   ↓
.ncxr（96B，疑似重定位参数）
   ↓
.ncx / .ncxh（最终代码体）
```

我从**链尾**开始攻，四小时零进展；链头的 `.ncks` 我反而只当"候选密钥原料"试了 141 个组合。

### 23.2 三个可以直接避免的错误

| 错 | 正确做法 |
|---|---|
| 拿段属性推"是不是代码"（因为 0 重定向 → 判它非代码） | 信指令里的 `adr`/`bl` 数据引用。我推反了：**纯代码反而 0 重定向**（全 PC 相对）|
| 拿"熵 4.00"当"结构化明文"证据 | 16 字节样本的最大熵就是 4.0，小样本熵没有判别力 |
| 拿整段密文去爆破 K，拿到算法却套错索引 | 先用 Unicorn 抓**真实 (keybyte, cipher, idx) 三元组**校准，再离线解 |

### 23.3 Frida 为什么指望不上

无 root 环境下：

| 方式 | 可行性 | 原因 |
|---|---|---|
| `frida-server` | ❌ | 启动需 root |
| `frida -U -f` attach | ❌ | ptrace 需 `CAP_SYS_PTRACE`，untrusted_app 无 |
| `frida-gadget` 重打包 | ⚠️ | 改 so 触发 CRC32 自校验；且 `0x933a0` 反调试 |
| gadget 注入自己进程 | ✅ 但 | 只能 hook 自己，碰不到 `com.xixin.box` |

**Frida 要操作别的进程，没 root 就拿不到 ptrace —— 这是内核级限制。** Unicorn 不需要，所以它是这个局面下的正确选择。

### 保护强度评价

**整体：中高。** 这是 **自研的保护方案**（`nc` 系列），不是爱加密/梆梆/顶象，但**比一般壳强**。

**它做对了什么：**

1. **代码虚拟化 2509 个操作码** —— 这是 VMP 级别，不是简单加密。能跑 Compose 主题框架说明 ISA 很完整
2. **自研流密码 + LEB128 双层** —— 不是现成算法，工具链无法直接识别
3. **`.ncx` 起始伪造合法指令** —— 主动误导反汇编器
4. **字符串用完即焚** —— 对抗内存取证
5. **`RegisterNatives` 可裁剪 + 自杀式陷阱** —— 让"置空指针"这种偷懒改法失效
6. **`brk #1` 而非 `abort`** —— 伪装成调试器断点
7. **函数指针走 GOT** —— 注册内容运行时可变

**它做错了什么：**

1. **Java 侧零混淆** —— `NativeGuard`/`NcLink` 语义化命名，直接暴露了调用链、`59` 魔数、双重 SHA-256 结构
2. **字符串用单字节 XOR** —— 最强的单字节混淆也只需 256 次尝试
3. **段名 `nc*` 暴露作者** —— 顶级壳会用中性名
4. **`.rodata` 明文留下 `nc: ok` / `Invalid access!` / `Couldn't find class`**
5. **体积仅 629 KB** —— VMP 只覆盖了部分代码，不是全量保护
6. **XOR 密钥 `0x5a` 与流密码种子都是编译期常量** —— 静态可得

**核心结论：**
> 这个壳的**强度瓶颈在代码虚拟化**，其余全是"挡业余选手"的门槛。
> 一旦解密 `.ncx`，拿到字节码，剩下的就是**写一个字节码反汇编器**——工作量问题，不是难度问题。

## 破解路线图（下一步）

```
┌─ 路线 A（静态）：找流密码种子 K
│   0x4d154  orr x2, x25, x28
│   → 回溯 x25/x28 赋值点
│   → 得到 K

│   在 0x4c834 返回处下断点，拿解密后的 buffer
│   或 hook mprotect(0x4c654/0x4c800/0x4c824) 看哪个段被改可写

└─ 路线 C（绕过）：不破解，直接改
```
