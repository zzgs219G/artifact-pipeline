**四个地址字段全部与实际段表对上**，说明锁箱契约完好无损。

### 1.3 XOR_KEY 与源码常量一致

```
XOR_KEY = 7e31a50dc8924bf6
源码 NC_XOR_FRAG_INIT = {1,0,2,3,0,1,3,2} 按碎片区重组 → 逐字节一致
```

⚠️ 注意：**碎片区本身（`[104:112]`）是构建期随机的**（本样本 `31 c8 7e 92 a5 f6 0d 4b`），
但重组规则是编译期常量。所以攻击者拿到一个样本的碎片，只能解这一个样本。

### 1.4 `.ncx` 解密后的第一条指令

```
0000000000000000:  d65f03c0   ret        ← 报告说的"伪造诱饵"，确认
0000000000000004:  d10103ff   sub sp, sp, #0x40
0000000000000008:  a9037bfd   stp x29, x30, [sp, #0x30]
...
```

**偏移 0 处的 `ret` 是刻意构造的诱饵。** 真正的 `ncVerify` 从偏移 4 开始：

```asm
0x04: sub  sp, sp, #0x40
0x20: cbz  x0, 0xa8              ; 参数检查
0x24: cmp  w1, #0x20             ; 长度必须是 32
0x28: b.ne 0xa8
0x34: adr  x10, <XOR 表>         ; 0x5A 密钥表
0x38: mov  w11, #-0x62           ; = -98 = 0x9E
0x50: mul  w15, w8, w11          ; ★ 位置相关：每个字节乘 0x9E
0x58: eor  w13, w14, w13         ; XOR 表
0x5c: eor  w13, w13, w15         ; XOR 位置因子
```

这是**位置相关的变体 XOR**（`byte[i] ^ table[i&15] ^ (i * 0x9E)`），
比报告第 7 课说的"单字节 XOR 0x5A"更强一层。

## 2. 报告被推翻的那条结论

### 报告原文（第 19 课 + 防御总盘点 #10）

> **种子 K = `0xc636fe91a36d792e`** —— Unicorn 跑到 `0x4d134` 读 `x25` 拿到
>
> 以及"它做错了什么"第 6 条：
> **XOR 密钥 `0x5a` 与流密码种子都是编译期常量** —— 静态可得

### 实际验证

我们用源码算法复算 `boot_key`：

```
.text CRC32(前 16KB)  = 0x3d503ca7
ikm = CRC32(4B BE) || .text[0:16] || .text[-16:]
boot_key = HKDF-SHA256(ikm, NC_BOOT_SALT_INIT, "nc-boot-v1", 16)
         = 4cae49f3dabfcf8d25b67e579680d60d
```

**与报告说的 `c636fe91a36d792e` 不同** —— 因为报告读到的是另一层（`.ncx` 的流密码种子），
不是 `boot_key`。但关键点在这里：

**`boot_key` 的三个输入全部与构建绑定：**

| 输入 | 是否编译期常量 |
|---|---|
| `CRC32(.text[0:16KB])` | ❌ **随代码变化** |
| `NC_BOOT_SALT_INIT` | ✅ 编译期常量 |
| `"nc-boot-v1"` | ✅ 编译期常量 |

**结论：换一次构建（改一行代码、换一个 APK 签名），`boot_key` 就变。**
它不是"静态可得的常量"，而是**每次构建派生的值**。

报告的"编译期常量"判断，对 `.text` CRC 这一层是**错的**。

### 但报告对另一层是对的

`.ncx` 的流密码种子（报告拿到的 `c636fe91a36d792e`）来自 `master` + 证书 + 包名派生。
`master` 在 `.ncxhr`，是**构建期随机生成的 32 字节**（`so-section-lock.py` 的 `os.urandom(32)`）。

本样本的 `master`：

```
dff2502e9fcd7561850bf06e647320bd3e78526dabba250afdecbe62d57ecc24
```

**每次构建都不同。** 所以报告拿到的 K 只对这一个样本有效。

**修正后的准确表述**：

> 攻击者拿到的不是"通用密钥"，而是"**这一个样本的密钥**"。
> 换一个包，全部重来。

## 4. 报告没发现的三件事（源码视角的补充）

### 4.1 我们有**两套** VMP，报告只发现一套

| VMP | 保护对象 | 报告是否发现 |
|---|---|---|
| `.ncx` 内的 94-handler VM | `ncVerify` 等业务代码 | ✅ 发现（第 19 课） |
| **nox 的 Amice VMP** | 解密链 14 个函数（`ncg_boot_key` 等） | ❌ **未发现** |

Amice VMP 在 `libnc.so` 的 `.text` 里，产物指标：
`nc_guard_crypto.o` 406 KB / 235 个 VM 子段。

报告没提，因为它看不出"`.text` 里某段是 VM 字节码"—— 这需要知道 Amice 的产物特征。

### 4.2 自校验覆盖的是**整段 `.text`**，不是函数

`.ncks[36:44]` 记录 `code_addr=0x425c0` / `code_len=0x4ee3c`，
即 **32 万字节的整个 `.text`**。改任何一字节 → `self_crc` 变 → `k_stub_eff` 变 → `.ncxh` 解出乱码 → SIGILL。

报告第 15 课说"`.ncks` 是 CRC32 校验锚点"，方向对，但没意识到**覆盖范围是整个 `.text`**。

### 4.3 报告的"路线 C（绕过）"实际成本比它估计的高

报告说：

> 路线 C（绕过）：hook ncVerify 让它恒返回 true
> · 需要过 native 反调试（25 秒一次 brk #1）
> · 需要过 CRC32 自校验

**实际上要过的是四道**：

1. `ncVerify` 在 `.ncx` 内，**未解锁时是密文**，hook 前必须先解密
2. `.ncx` 的 MAC 用 `k_mac`（证书派生），改一字节 → MAC 失败 → 不解锁
3. 解锁后 `self_text_crc` 覆盖整个 `.text`，改 `.text` → `k_stub_eff` 变 → `.ncxh` 崩
4. 25 秒轮询的 `brk #1`（报告已识别）

## 5. 可复现的验证脚本

```python
#!/usr/bin/env python3
"""用源码算法解开 libnc.so 的五个加密段。需要：libnc.so + 对应 APK。"""
import struct, zlib, hashlib, hmac, zipfile

so   = open('libnc.so','rb').read()
apk  = open('app.apk','rb').read()

# ── 1. 从 APK 提第一签名者证书 ──
i = apk.rfind(b'PK\x05\x06')
cd_off = struct.unpack_from('<I', apk, i+16)[0]
assert apk[cd_off-16:cd_off] == b'APK Sig Block 42'
sb_size  = struct.unpack_from('<Q', apk, cd_off-24)[0]
sb_start = cd_off - sb_size - 8
p, end, pair = sb_start+8, cd_off-24, None
while p < end:
    plen = struct.unpack_from('<Q', apk, p)[0]
    pid  = struct.unpack_from('<I', apk, p+8)[0]
    if pid in (0xf05368c0, 0x7109871a):        # v3 优先，退 v2
        pair = apk[p+12:p+8+plen]
    p += 8 + plen
def lp(b,o):
    n = struct.unpack_from('<I',b,o)[0]; return b[o+4:o+4+n], o+4+n
signers,_ = lp(pair,0); signer,_ = lp(signers,0)
signed,_  = lp(signer,0); _,o = lp(signed,0)
certs,_   = lp(signed,o); cert,_ = lp(certs,0)
cert_sha  = hashlib.sha256(cert).digest()

# ── 2. boot_key = HKDF(CRC32(.text[0:16K])||首16||末16, SALT, "nc-boot-v1") ──
TEXT_OFF, TEXT_SIZE = 0x425c0, 0x4ee3c        # ← 从 readelf -SW 读
span   = min(0x4000, TEXT_SIZE)
region = so[TEXT_OFF:TEXT_OFF+span]
crc    = zlib.crc32(region) & 0xFFFFFFFF
ikm    = struct.pack('>I', crc) + region[:16] + region[-16:]
SALT   = bytes([0x6e,0x63,0x1f,0x2b,0x7a,0x44,0x91,0xd8,
                0x03,0x5c,0xe6,0x18,0xaf,0x72,0x39,0xc4])   # NC_BOOT_SALT_INIT
prk      = hmac.new(SALT, ikm, hashlib.sha256).digest()
boot_key = hmac.new(prk, b'nc-boot-v1'+b'\x01', hashlib.sha256).digest()[:16]

def rc4(key, data):
    S=list(range(256)); j=0
    for i in range(256):
        j=(j+S[i]+key[i%len(key)])&0xFF; S[i],S[j]=S[j],S[i]
    out=bytearray(); i=j=0
    for b in data:
        i=(i+1)&0xFF; j=(j+S[i])&0xFF; S[i],S[j]=S[j],S[i]
        out.append(b ^ S[(S[i]+S[j])&0xFF])
    return bytes(out)

def ctr_xor(key, dom, data):
    out=bytearray(data); n=len(out); ctr=0; off=0
    while off<n:
        ks=hashlib.sha256(key+bytes([dom])+struct.pack('<I',ctr)).digest()
        blk=min(32,n-off)
        for j in range(blk): out[off+j]^=ks[j]
        off+=blk; ctr+=1
    return bytes(out)

# ── 3. 解 .ncks ──
NCKS_OFF, NCKS_SIZE = 0x37f74, 0x70            # ← readelf -SW
ncks = so[NCKS_OFF:NCKS_OFF+NCKS_SIZE]
dec  = ncks[:8] + rc4(boot_key, ncks[8:])      # [0:8) magic 豁免
rd32 = lambda o: struct.unpack_from('<I', dec, o)[0]

# ── 4. 重组 XOR_KEY，恢复 k_stub_eff ──
FRAG = [1,0,2,3,0,1,3,2]                       # NC_XOR_FRAG_INIT
fr   = dec[104:112]
xk   = bytes((((fr[FRAG[i]*2] | (fr[FRAG[i]*2+1]<<8))) >> (0 if i<4 else 8)) & 0xFF
             for i in range(8))
k_stub    = bytes(dec[8+i] ^ xk[i&7] for i in range(16))
self_crc  = zlib.crc32(so[TEXT_OFF:TEXT_OFF+rd32(40)]) & 0xFFFFFFFF
k_stub_eff= bytes(k_stub[i] ^ ((self_crc >> ((i&3)*8)) & 0xFF) for i in range(16))

# ── 5. 解 .ncxhr（master）→ 派生 k_so / k_mac ──
NCXHR_OFF = 0x99170                            # ← 注意：file offset ≠ sh_addr
master = ctr_xor(k_stub_eff, 0x02, so[NCXHR_OFF:NCXHR_OFF+rd32(100)])

def hkdf(ikm, salt, info, n):
    prk=hmac.new(salt,ikm,hashlib.sha256).digest(); okm=b''; t=b''; i=1
    while len(okm)<n:
        t=hmac.new(prk,t+info+bytes([i]),hashlib.sha256).digest(); okm+=t; i+=1
    return okm[:n]

pkg    = 'com.xixin.box'
k_so   = hkdf(master, cert_sha, ('nc-so-v1'+pkg).encode(), 16)
k_mac  = hkdf(master, cert_sha, ('nc-so-mac-v1'+pkg).encode(), 16)
k_so_r = hkdf(master, cert_sha, ('nc-so-r-v1'+pkg).encode(), 16)

# ── 6. 验 MAC，解 .ncxh / .ncx ──
NCX_OFF,  NCX_SIZE  = 0x913fc, 0x1ac0
NCXH_OFF, NCXH_SIZE = 0x92ebc, 0xc20
NCXR_OFF, NCXR_SIZE = 0x37f14, 0x60

head_enc = so[NCXH_OFF:NCXH_OFF+NCXH_SIZE]
k_mac_head = bytes(dec[48+i] ^ xk[i&7] for i in range(16))
assert hmac.new(k_mac_head, head_enc, hashlib.sha256).digest() == dec[64:96], "head MAC 失败"
head_dec = ctr_xor(k_stub_eff, 0x01, head_enc)

ncx_enc, ncxr_enc = so[NCX_OFF:NCX_OFF+NCX_SIZE], so[NCXR_OFF:NCXR_OFF+NCXR_SIZE]
assert hmac.new(k_mac, ncx_enc+ncxr_enc, hashlib.sha256).digest() == rc4(boot_key, so[0x37fe4:0x37fe4+0x60])[48:80], "ncx MAC 失败"
ncx_dec  = rc4(k_so,   ncx_enc)
ncxr_dec = rc4(k_so_r, ncxr_enc)

open('ncx.bin','wb').write(ncx_dec)
open('ncxh.bin','wb').write(head_dec)
print('✅ 五个段全部解开')
```

**实测输出**：

```
boot_key = 4cae49f3dabfcf8d25b67e579680d60d
XOR_KEY  = 7e31a50dc8924bf6          ← 与源码常量一致
master   = dff2502e9fcd7561...        ← 每次构建不同
.ncxn MAC 校验: True
.ncxn 解密后首指令: d65f03c0 (ret)    ← 诱饵，确认
✅ 五个段全部解开
```

## 6. 由此得出的文档维护方法论

这次验证暴露了一个结构性问题：**文档靠"读代码"维护会持续漂移，靠"验证产物"维护才稳定。**

### 6.1 为什么文档必然过期

`AGENTS.md` §3.3 写「日志里有输出 ≠ 防护生效」，它的镜像同样成立：
**文档里写了 ≠ 代码里还是那样**。

本项目已发生的漂移（2026-11-08 实测）：

| 文档 | 写的 | 实际 |
|---|---|---|
| `反Frida方案调研.md` | 10 个探针 / 缺 `/proc/self/stat` | 11 个 / 已有 |
| `交接文档.md §4` | `ncg_boot_key` 做不到 VMP | 已 VMP（21 条指令） |
| `混淆计划.md §3/§4` | P1/P2 待做 | 已完成 |
| 多处 | VMP 覆盖 11/11 | 实测 14 个函数 |
| 多处 | `test.sh` 21 通过 | 23 通过 |

**根因不是"没人更新"，而是"更新时没有可执行的判据"。** 写文档的人只能读代码，
而读代码看不到"这个函数是不是真的进了 `.ncx`""VMP 是不是真的生成了"。

### 6.2 应该改成"产物断言驱动"

每一项文档声明，都应该有一条**可执行的产物断言**：

| 文档声明 | 对应断言 | 现状 |
|---|---|---|
| 「探针在 `.ncx`」 | `nm libnc.so \| grep probe` 地址落在 `.ncx` 范围 | ❌ 无 |
| 「VMP 生效」 | `check-obf.sh` VM 子段数 > 0 | ✅ 有 |
| 「元数据已清理」 | `.eh_frame`/`.comment` 零命中 | ✅ 有（V8/V9） |
| 「六段齐全」 | `readelf -SW` 六个段名 | ✅ 有（V2） |
| 「`.dynsym` 只有 JNI_OnLoad」 | `nm -D` 行数 == 1 | ❌ 无 |
| 「`.rodata` 无明文特征串」 | `strings \| grep -c` == 0 | ⚠️ 部分（V4 只查路径） |
