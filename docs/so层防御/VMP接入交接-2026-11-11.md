## 3. 八条硬纪律（每条都有真机事故垫底）

### ① 代码进 `.ncx`，数据进 `.ncxr`

```c
/* 函数 */  __attribute__((section(".ncx")))     // AXR = R-X
/* 数据 */  __attribute__((section(".ncxr")))    // AWR = RW-
```

**混放 → 链接器生成 `RWE` 段 → Android 14+ `dlopen` 直接拒绝**：

```
UnsatisfiedLinkError: "libnc.so" has load segments that are both
writable and executable
```

这是 `nox/AGENTS.md` §2.2 的规则，但只写给"改 nox 的人"看。**消费方必记。**

### ② `used, retain` 不能删

想让 VMP 处理函数，会撞上「`@llvm.used` 让 Amice 跳过」。**正确解法是让 amice 豁免 `@llvm.used`，不是删属性。**

删了 `used` 的后果（实测）：

```
--gc-sections 把函数当死代码 → .ncx 里留下没人调用的副本
→ 真正执行的是 .text 里另一份
→ 现象：「VMP 报成功但加密段毫无变化」，so 白涨 92KB
```

**判据是「有没有被引用」，不是「有没有 section 属性」。**

### ③ `AMICE_VM_VIRTUALIZE` 和 `AMICE_VM_ONLY_ANNOTATED` 必须成对

```bash
export AMICE_VM_VIRTUALIZE=true       # 让 pass 装上
export AMICE_VM_ONLY_ANNOTATED=1      # 但只处理带 annotate 的函数
```

- 少了前者 → pass 不装，annotate 写了没人读（`.ncx` 只涨 36 字节）
- 少了后者 → 所有函数当候选，dex2c 的 87 个辅助函数各生成一份 runtime（so 从 466KB → 1,397KB + 栈溢出）

### ④ `runtime.entry` 必须是 `call`，不能 `inline`

`inline` 把解释器内联进每个被保护函数，栈帧叠加。`DefaultDispatch` 是 ART
线程池线程，**栈只有约 1MB**（主线程 8MB），直接 `SEGV_ACCERR` 栈溢出。

### ⑤ 要 VMP 的函数不能调 varargs

**两个都要避开**：

| 调用 | 为什么 |
|---|---|
| `siglog(prio, fmt, ...)` | `llvm.va_start` intrinsic |
| `__android_log_print(prio, tag, fmt, ...)` | 同样是 varargs 签名 |

用 `siglog_fmt1` + `LOGI_V1/LOGE_V1/LOGI_S/LOGE_S`（内部用
`__android_log_write`，签名是三个指针）。

**报错文案是 `LLVM intrinsic calls are not supported`，不提 varargs** —— 极易查错方向。

### ⑥ 寄存器超限是工程问题，拆函数就能解决

`values=21` 不是原理限制。nox 的 `ncguard_stub_recover` 当初 `values=22`，拆了四次才过。

**拆的纪律**：
- 一次拆不够是常态，**拆完必须重新看 `values`**
- 所有子函数都要 `SIG_SEC_MARKED`（含 `noinline`），否则 `-Oz` 内联回去

### ⑦ 判断 VMP 是否生效，不看 `.ncx` 大小

dex2c 产物混在 `.ncx` 里会误导。可靠判据：

| 判据 | 方法 |
|---|---|
| `.ncx` 里有 wrapper | 180B 级小函数 + `bl` 到 `.text` 的 VMP 区 |
| 目标常量消失 | `0xBF58476D1CE4E5B9` 在 so 里 0 处 |
| skip 日志 | `RUST_LOG=amice=debug` 里没有该函数名 |

### ⑧ 换 bundle 必须同时改 cache key

```yaml
key: amice-r29-v0.1.6-nox5    # ← 不改会命中旧缓存，静默用旧版
```

两处 URL + 两处 cache key（`protect-modules.yml` 和 `nox/release.yml`）。

### 4.2 「两套 VMP」都验到了

用户说的「两种 VMP」是指 **nox 的锁箱** 和 **Amice 的指令虚拟化**，
两者是不同机制，可以独立开关：

| 机制 | 是什么 | A(vmp) | B(novmp) | 证据 |
|---|---|---|---|---|
| **① nox 锁箱** | `.ncx` 段整体加密，运行时由 `.ncks` 派生密钥解锁 | ✅ | ✅ | `.ncx`=44,792B / `.ncxh`=3,104B / `.ncxr`=104B /`.ncks`=112B，段 flag `AX`/`WA`（**无 WX**） |
| **② Amice 指令虚拟化** | 函数体编译成 VM 字节码，执行时走解释器 | ✅ **6 个函数** | ❌ **0** | A 的 `.text` 多 94KB、`.rodata` 多 107KB，`br x?` 119 vs 106、`ldrb[w,[x,x]]` 122 vs 59；B 的 CI 日志里 `VmVirtualize` 出现 **0 次** |

**B 组的 `.ncx` 是 45,032B，比 A 还大 240B** —— 这正好印证了 §3⑦：
**看 `.ncx` 大小判断 VMP 会得出完全错误的结论**（B 没 VMP 但 .ncx 更大）。

### 4.3 A 组的 VMP 明细（来自 `RUST_LOG=amice=debug`）

**VMP 成功（sigcheck 侧 7 个）**：


⚠️ **这个 7 是「10 个目标 − 3 个跳过」推出来的，不是日志直接报的。**
Amice 只打 skip 日志，**成功不打日志** —— 想看成功清单得靠产物对比（见下）。

**stringenc 侧（chacha20 档）**：`nc_mix64` 因 `#if NC_STRDEC_ALGO != CHACHA20`
**根本没编译进去**（`nc_strdec.c:78`），所以只有 `nc_block_ks` 是候选。
`nc_chacha20_keystream64` 已确认被跳过；`nc_block_ks` 未出现在 skip 日志里，
**大概率成功，但没直接证据** —— 它可能被 `-Oz` 内联进 `nc_strdec_decrypt` 了。

或者用 `vmpcheck.py` 解出 `.ncx` 再看。

### 4.3.1 怎么证明 VMP 真的发生了（三条独立证据）

因为 Amice 不打成功日志，而且两版都被锁箱，常规判据全失效。本轮实际用到的：

| 证据 | A(vmp) | B(novmp) | 说明 |
|---|---|---|---|
| **① `VmVirtualize` 日志出现过** | ✅ 4 次 | ❌ **0 次** | 最硬的证据：B 的 pass 根本没跑 |

| **③ `.rodata` 体积** | 258,980 | 151,860 | +107,120B = VMP 的字节码 + descriptor 表 |
| ④ `.ncx` 体积 | 44,792 | **45,032** | ⚠️ **B 更大** —— 这个判据在这里反向，不能用 |

**「两套 VMP」的准确表述**：nox 锁箱（`.ncx` 加密）**两版都有**；
Amice 指令虚拟化**只有 A 有**。用户问的「两种 VMP」如果指的是这两者，
答案是 A 组两者齐全。

## 5. VMP 对启动速度的影响：**测不出来**

### 5.1 数据（冷启动，`am start -S -W` 的 `TotalTime`）

```
A(带 VMP)   n=13   143 159 160 162 171 172 184 187 200 212 221 247 253
B(不带 VMP) n=8    152 176 180 184 189 194 197 200
```

| 指标 | A(带 VMP) | B(不带 VMP) | 差 |
|---|---|---|---|
| 中位数 | **184 ms** | **186 ms** | **−2 ms（−1.3%）** |
| 均值 | 190.1 ms | 184.0 ms | +6.1 ms（+3.3%） |
| 最小 | 143 ms | 152 ms | −9 ms |
| 最大 | 253 ms | 200 ms | +53 ms |
| 标准差 | **34.6 ms** | **15.4 ms** | — |

### 5.2 结论：**VMP 对启动速度没有可测影响**

**理由**：

1. **中位数差 2ms，方向还是负的** —— 完全在噪声里。
2. **A 组标准差 34.6ms > 组间差 6ms** —— 组内波动比组间差异大 5 倍。
   这说明测到的差异主要来自**系统调度/温度/后台**，不是 VMP。
3. **VMP 只作用于 8 个函数，且都不在启动热路径上** ——
   `derive_expected` / 签名块解析链（每次启动跑一次，1ms）、
   `nc_block_ks`/`nc_mix64`（解密被加密的字符串时才调）。
   App 启动的耗时大头是 ART 类加载 + dex2c 的 JNI 注册，VMP 不参与。

### 5.3 但 VMP 确实有成本，只是不在启动路径上

| 成本 | 量级 | 位置 |
|---|---|---|
| **包体积** | so **535KB → 741KB**（+206KB，+38.5%） | 装包/更新，一次性 |
| **磁盘占用** | 同上 | — |
| **首次调用延迟** | 解释执行 vs 原生，约 **10–50 倍** | 每个被 VMP 函数首次/每次调用 |
| **内存** | 解释器 10KB 级 + 每函数字节码 | 常驻 |

**这对本项目无影响**：被 VMP 的函数要么每次启动只跑一次（签名校验链，1ms → 解释后最多几十 ms，实测没测出差异），
要么在字符串解密路径上（已经在 L1 缓存后面了）。

**但如果将来 VMP 覆盖到热路径（比如渲染、网络循环），必须重新测。**
判断标准：被 VMP 的函数的**每秒调用次数**。>100 次/秒就要警惕。

### 5.4 测量方法（复现用）

```bash
export PATH=~/逆向工具/bin:~/逆向工具/android-tools:$PATH
D=192.168.1.5:45435
for i in $(seq 1 5); do
  adb -s $D shell am force-stop com.xixin.box
```

## 6. 已知未解

### 6.1 VMP 的字节码和解释器在明文段

```
.ncxa 的 wrapper（密文） → bl .text 的 dispatcher（明文 10KB）
                                    → 读 .rodata 的字节码（明文）
```

`emit_runtime_bytecode_global` / `emit_descriptor_table` 是**模块级 global，无 section 属性**。
攻击者不用解 `.ncxa`，读 `.text` + `.rodata` 就能拿到 VMP 的全部内容。

**为什么没修**：dispatcher 是关键（字节码没有它读不懂），但把 dispatcher 搬进
`.ncx` 会撞上「锁箱自己的 VMP 也在 `.ncx`」的时序问题（详见
`amice-fork改造记录.md` §7.1）。**需要先想清楚两套 VMP 的隔离。**

### 6.2 sig_verify 三件套仍被跳过

`LLVM intrinsic calls are not supported`，本地 IR 查不出 callee 是哪个（已给 amice
加诊断，`v0.1.6-nox5` 会打出 callee 名）。

**但价值评估：拆完这三个只剩流程控制，秘密在已 VMP 的子函数里。收益≈0，可以不管。**

### 6.3 v7a 上 VMP 不完整

| 特征 | arm64 | v7a |
|---|---|---|
| `0x7F4A7C15` 明文 | 0 处 | **18 处** |
| `.text` | 648,176 | 1,325,220 |

ARM32 上代码被膨胀了，但原始常量没被虚拟化。**没查过原因。**

## 7. 下一步该做什么（按 ROI）

| 优先级 | 事项 | 说明 |
|---|---|---|
| **P0** | `v0.1.6-nox5` bundle 换到消费方 | 已换（两处 URL + 两处 cache key），**但本轮 A/B 构建用的还是 nox4**，nox5 只多一条诊断信息，行为等价 |
| **P1** | 常量构建期随机化 | `混淆计划.md` §10.4 第一条。让"读公开仓库复现"失效 |
| **P2** | 运行环境进密钥派生 | 让"拿 APK 静态解"失效。**VMP 这时才变成必由之路** |
| P3 | 把 dispatcher/字节码搬进加密段 | 要先解决两套 VMP 的隔离 |
| P4 | 查 v7a 常量泄漏（§6.3） | 如果还在发 32 位包，这是个真漏洞 |
| 不做 | 继续提升 VMP 覆盖率 | 边际收益已到顶（§5、§6.2 有数据） |

**关键认知（`混淆计划.md` §10 的结论）：**
> VMP 抬高了「读懂实现」的成本，抬不高「复现算法」的成本。

真正的杠杆是**让解锁链依赖包里没有的东西**（运行环境 / 服务端），不是加 VMP 覆盖。
