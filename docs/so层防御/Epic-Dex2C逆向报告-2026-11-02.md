# Epic Dex2C 逆向报告 + 与 libnc.so 防御对比

> 编写日期：2026-11-02
> 样本：`简盒_signed_10_46_14.apk`（Epic 保护，`https://epic.t60.top/`）
> 工具：radare2 6.x、unicorn 2.1.4、llvm-objdump（NDK r29）、androguard
> 目的：**横向对比两种 so 层防御实现**，提炼可迁移的改进点

---

## 0. 结论先行

### 0.1 这不是"同一个东西的两种实现"

Epic 和我们**不是同类方案的不同做法**，是**两条平行路线**：

```
Epic  = 混淆派（Obfuscation-first）
        代码始终明文在 .text，目标是让「读懂」变难
        · 常量拆分 7715 处 · 字符串全加密 · 符号全擦 · 动态注册
        · 短板：只要肯花时间，代码可以完整读出来（我做到了）

我们  = 加密派（Encryption-first）
        磁盘上是密文，目标是让「拿到」变难
        · 6 段 RC4+HMAC · 二级锁箱 · 证书绑定密钥 · 代码自绑定
        · 短板：符号表没擦，业务方法名直接暴露（nm -D 可见）
```

**两套设计哲学互相看不出对方的必要性**——这正是它们的价值：
Epic 解决了"读得懂"，我们解决了"拿得到"，彼此都缺对方那一半。

### 0.2 分项速览

| 防御层 | Epic | 我们 | 差距性质 |
|---|---|---|---|
| **L1 符号表** | 681 函数全匿名，6 个导出 | 11 个导出，**含业务方法名** | Epic 领先 |
| **L2 字符串** | 全 `.rodata` `XOR(i+1)` | SHA256 密钥流 | **我们领先**（Epic 的 10 秒可破） |
| **L3 常量** | 7715 处 `movk` 拆分，零明文魔数 | 魔数常量直接落地 | Epic 领先 |
| **L4 代码本体** | `.text` **完全明文** | 6 段密文 + 二级锁箱 | **我们领先**（本质差距） |
| **L5 控制流** | 1374 `orn` + 768 `blr` + 100 PAC | 无混淆 | Epic 领先 |
| **L6 元数据** | `.comment` 清空 | `.comment` **泄露 clang 版本** | Epic 领先 |
| **L7 转译策略** | 3 方法 + **障眼法**（native 声明但零调用） | 全 LAUNCHER 类，真实执行 | 各有千秋 |
| **L8 失败处置** | `pause()` 单点挂起 | 三档延时杀，seed 不相关 | **我们领先** |
| **L9 反分析** | 反多开 + `getauxval` 反 hook | 10 探针 + 心跳保活 | 各有千秋 |
| **L10 加载健壮性** | 三级回退 | 单次 `loadLibrary` | Epic 领先 |

### 0.3 一句话总结

> **Epic 把"读懂"的成本抬到了小时级，我们把"拿到"的成本抬到了破壳级。**
>
> 但 Epic 的`.text`我可以完整逆出来，我们的 `nm -D` 也会直接吐出业务方法名。
> **双方都该补对方那一半。**

## 1. Epic 的完整防御架构

### 1.1 整体结构

```
classes2.dex（3KB，纯壳）
├── LEpic/Dex2C;        extends Application
│     ├── <clinit>       → sl() 加载 so
│     ├── sl()/rs()/sp() → 三级加载回退
│     ├── initDcc()        native（空实现，跳板到 ret）
│     ├── applyXposedRegistration()  native
│     ├── setXposedPrefix()          native
│     ├── setLibxposedPrefix()       native
│     ├── setLibxposedPrefixMap()    native
│     └── triggerXposed()  → 反射调用上面几个
└── LEpic/D2CXpMap;     Xposed 原始/运行时类名映射

lib/arm64-v8a/libEpicD2C.so（509KB）
```

### 1.2 so 加载回退链（Android 层，`Epic/Dex2C`）

```java
static boolean sl() {
    try {
        System.loadLibrary("EpicD2C");   // ① 标准路径
        return true;
    } catch (Throwable t) {
        Log.e("D2CX", t.toString());
        if (rs()) return true;            // ② ClassLoader.getResource
        String lp = System.getProperty("java.library.path");
        if (lp != null) {
            for (String dir : lp.split(":"))
                if (sp(dir)) return true;  // ③ java.library.path 逐个 load
        }
        return false;
    }
}

static boolean rs() {
    // lib/<abi>/libEpicD2C.so，用 Class.getClassLoader().getResource() 反推实际路径
    URL u = EpicDex2C.class.getClassLoader().getResource(
                 "lib/" + ab() + "/libEpicD2C.so");
    if (u == null) return false;
    System.load(u.getPath().substring(5));  // 去掉 "file:"
    return true;
}
```

**为什么值得学**：`extractNativeLibs=false` 时 so 在 APK 内（`base.apk!/lib/...`），`loadLibrary` 走 zip 映射；`true` 时 so 解压到 `lib/<abi>/`。两条路径的符号解析行为不同，回退链能覆盖异常场景。

## 2. Epic 的签名校验（本次逆向核心）

### 2.1 调用链

```
JNI_OnLoad (0x14c78)
 └─ 0x2d31c  初始化
      ├─ bl 0x31f94          → 取 D2CSIG1 / D2CKA1 双槽指针，写入全局
      │     全局 [0x86a60] = &"D2CSIG1" 结构
      │     全局 [0x86a68] = &"D2CKA1" 结构
      │     全局 [0x86a70] = 第三指针
      ├─ bl 0x2d6f0          → md5 分支：检查 D2CSIG1[+0x18].bit0
      ├─ 0x2d3f0             → tee 分支：检查 D2CKA1[+0x28].bit0
      ├─ w8 = w0 | w20       → 任一武装即触发
      ├─ 非 0 → 打印 "SEC-ARMED md5=%d tee=%d"
      └─ bl 0x2d85c          → 真正的校验
```

### 2.2 双槽数据结构（`.rodata`）

```
0x89a5: "D2CSIG1\0"
        [16 字节 sig 数据]        ← +0x08
        01 00 00 00               ← +0x18  md5 分支武装标志
        "D2CKA1\0\0"
        [32 字节 key 数据]        ← +0x24
        01                        ← +0x28  tee 分支武装标志
```

**设计意图**：两个独立武装开关，编译时可分别关闭某一分支。

### 2.3 APK 定位（`0x2d85c`）

```c
// 路径 1

### 2.4 路径白名单（`0x2df14`）—— 反多开

```c

// 还要含 "<pkg>-<suffix>/"
```

### 2.6 APK Signing Block 解析（`0x2dd60`）

```c
// 用 mov/movk 拼字符串，不存明文
// x12 = "APK Sig B" + x10 = "lock 42"
if (*(uint64_t*)(p-0x10) != 0x20676953204b5041ULL ||   // "APK Sig "
    *(uint64_t*)(p-0x08) != 0x3234206b636f6c42ULL)      // "Block 42"
    return -1;

// 遍历 ID-value 对
for (each pair) {
    uint32_t id = *(uint32_t*)p;

    if (id == 0x1B93AD61) { /* v3.1 */ check(p, len, expect_md5); }
}
```

## 3. 破解过程（可作为通用方法论）

### 3.1 关键突破口

| 阶段 | 手段 | 结果 |
|---|---|---|
| 找加密算法 | 用两条已知明文反推 XOR 密钥 | `plain[i] = cipher[i] ^ (i+1)`，**递增 i+1** |
| 找校验点 | 搜 `pause`/`exit`/`abort` 的调用点 | `0x2deec` = log + pause |
| 找 APK 解析 | 搜 `/proc/self/maps` + `base.apk` | `0x2d85c` |
| 找 Signing Block | 搜 `mov/movk` 拼出的字符串 | `"APK Sig Block 42"` |
| 找 MD5 | 搜 MD5 IV（`0x67452301` LE） | `0x6a10`，引用点 `0x2e0a0` |

### 3.2 走过的弯路（教训）

| 错误假设 | 实际情况 |
|---|---|
| “没搜到 `signature`/`PackageManager` 字符串 = 没签名校验” | 它**不调 Java API**，直接读 APK 二进制 |
| “没搜到 `PK\x05\x06` 魔数 = 不解析 ZIP” | 它**逐字节比较** `0x50/0x4b/0x05/0x06` |
| “没搜到 SHA-256 常量表 = 没哈希” | 它用 **MD5**，IV 在 `0x6a10` |
| “`adr x16, 0x6a10` 扫不到 = 没引用” | `adr` 是 PC 相对，需按指令解码，非 `adrp+add` |
| “`0x2deec` 是 fail-closed 死循环，改成 ret 即可” | 它是 **noreturn**，改 ret 破坏栈平衡 → SIGSEGV |
| “返回 1 = 校验通过” | **返回 1 = 校验失败** |

### 3.3 最终补丁（3 处，9 字节）

| 地址 | 原值 | 补丁 | 含义 |
|---|---|---|---|
| `0x89e9` | `01` | `00` | `D2CKA1[+0x28]` —— 关闭 tee 分支武装 |
| `0x2d6f0` | `adrp x8,0x86000` | `mov w0,#0` | md5 分支恒返回“未武装” |
| `0x2d6f4` | `ldr x8,[x8,#0xa60]` | `ret` | 同上 |

**验证**：装机后 `CLINIT-SL-OK`，无 `SEC-ARMED`/`SEC-DENY`，进程存活。

### 3.4 打包必须注意

`zip` 重打包会导致 `resources.arsc` 被压缩 → **安装报 124**（`Targeting R+ requires resources.arsc stored uncompressed and 4-byte aligned`）。

**正确流程**：
```bash
apktool d -f -r -o dec app.apk
cp patched.so dec/lib/arm64-v8a/
apktool b -o unsigned.apk dec
zipalign -f -p 4 unsigned.apk aligned.apk
apksigner sign --ks xxx.keystore --out final.apk aligned.apk
```

## 4. 与我方 libnc.so 的详细对比

> **最重要的一句话**：Epic 和我们走的是**两条完全不同的技术路线**。
>
> - **Epic = 混淆派**：代码始终在 `.text` 明文，目标是**让"读"变难**
> - **我们 = 加密派**：磁盘上是密文，目标是**让"拿到"变难**
>
> 拿一张表对比会误导。下面按**技术路线**拆开看。

### 4.0 两条路线的本质差异

```
Epic 的防御栈（从上到下都是"增加阅读成本"）
┌─────────────────────────────────────────────┐
│ 1. 符号表擦除     .symtab 删净，681 个函数全匿名  │
│ 2. 常量拆分       7715 处 movk，魔数/字符串不落地  │
│ 3. 字符串加密     全 .rodata XOR(i+1)             │
│ 4. 动态注册       RegisterNatives，业务名不进符号表 │
│ 5. 双槽武装标志   编译期开关，静态看不到启用哪条  │
│ 6. 间接调用       768 处 blr，控制流不可静态追       │
│ 7. 栈保护 + PAC   100 处 paciasp/autiasp           │
└─────────────────────────────────────────────┘
      ↓ 但 .text 始终明文，只要肯花时间就能读完

我们的防御栈（每一层都是"减少可得性"）
┌─────────────────────────────────────────────┐
│ 1. 段加密        6 段 .ncx/.ncxh/.ncxr… RC4+HMAC │
│ 2. 二级锁箱      unlock 本体自己也被加密(.ncxh)    │
│ 3. 运行期派生    证书 DER → HKDF → k_so，磁盘无钥  │
│ 4. 代码自绑定    k_stub ^ crc32(.text)，改码即毁   │
│ 5. 密钥碎片化    4×uint16 volatile 散落 .data      │
│ 6. 段名中性化    .ncx 无语义，readelf 看不出用途   │
└─────────────────────────────────────────────┘
      ↓ 但符号表没擦净，nm -D 直接看到业务方法名
```

**结论**：Epic 的静态阅读成本远高于我们，我们的磁盘密文强度远高于 Epic。
两者的短板恰好是对方的长板。

### 4.1 层 1：符号表与函数可见度

| | Epic | 我们 |
|---|---|---|
| `.symtab` | ✅ 删除（`nm` = "no symbols"） | ✅ 删除 |
| `.dynsym` 导出 | **6**（全 `Epic_Dex2C_*` 框架） | **11**（含业务方法） |
| 函数总数 | 681（全部匿名） | 未统计 |
| 业务方法名 | **零暴露** | ❌ 全暴露 |

**我们的实际导出（实测）**：

```
T Java_com_nc_link_NcLink_heartbeat           ← 框架，可接受
T Java_com_nc_link_NcLink_ncVerify            ← 框架
T Java_com_nc_link_NcLink_selftest            ← 框架
T Java_com_xixin_box_MainActivity_k__Landroid_os_Bundle_2                    ← ⚠️
T Java_com_xixin_box_MainActivity_onConfigurationChanged__Landroid_content_res_Configuration_2  ← ⚠️
T Java_com_xixin_box_MainActivity_onCreate__Landroid_os_Bundle_2             ← ⚠️
T Java_ex_sf_jv_wg_b2__Ljava_lang_String_2    ← ⚠️ StrDec 壳
T Java_ex_sf_jv_wg_dn__Ljava_lang_String_2    ← ⚠️ StrDec 内核
T Java_ex_sf_jv_wg_keyByte__JJ                ← ⚠️ 密钥流
T Java_ex_sf_jv_wg_mix64__J                   ← ⚠️ splitmix64
```

**危害是双重的**：

1. **dex2c 抽了哪些方法一目了然** —— `nm -D` 一条命令
2. **StrDec 桩随机化被废一半** —— 类名每包随机（`ex_sf_jv_wg`），但方法名
   `dn`/`mix64`/`keyByte` 是**对拍契约锚点，固定不变**，直接暴露在符号表。
   攻击者不需要脱壳、不需要找桩，就知道：
   - 桩算法有哪 4 个方法、分别叫什么
   - 哪些业务方法被抽进了 so

**Epic 怎么解决的**：`RegisterNatives(env, cls, methods, 3)` 动态注册。
`.got+0x2a8/0x2b0/0x2b8` 三个槽位（`.rela.dyn` 填入）指向：

```
slot0 0x14d28  → k(Bundle)V                    (1924 B)
slot1 0x159bc  → onConfigurationChanged(Config)V (7656 B)
slot2 0x1a258  → onCreate(Bundle)V             (25836 B)  ← 真正的体量
```

方法名/签名在 `0x3a34c` 解密后才用，`.rodata` 里全是密文。

---

### 4.2 层 2：字符串保护

| | Epic | 我们 |
|---|---|---|
| 覆盖 | 全 `.rodata`（15320 B） | LSGS 标记串 |
| 算法 | `cipher[i] ^ (i+1)` | `SHA256(key ‖ msg_id ‖ counter)` |
| 密钥 | **无**（编译期固定模式） | `os.urandom(32)` 每构建随机 |
| 已知明文 | ⚠️ **10 秒破解**（我用 3 组已知明文反推） | ✅ 推不出 |
| 相同前缀 | ⚠️ 密文前缀相同 | ✅ 每消息独立 |
| 明文残留 | 325 个（libc++ 异常名） | 需实测 |

**Epic 弱在哪**：`^ (i+1)` 是**递增 XOR**，本质是固定模式。我拿到
`java/lang/Boolean`、`<init>`、`valueOf` 三条已知明文，反推
逐字节密钥 `01 02 03 ... 16`，然后**一次性解开全部 8550 个候选串**。

**我们强在哪**：`SHA256(key ‖ msg_id ‖ counter)` 是**每消息独立密钥流**，
即使拿到一条明文，也推不出下一条的密钥。

> 这是本次对比里我们**唯一压倒性领先**的项。

---

### 4.3 层 3：常量与魔数

| | Epic | 我们 |
|---|---|---|
| 魔数落地 | ❌ 全拆分（`mov`/`movk` 7715 处） | — |
| 例 | `"APK Sig Block 42"` 拆成 2 个 `movk` 链 | — |
| ZIP EOCD | **逐字节比较** `0x50/0x4b/0x05/0x06` | 魔数常量 `0x06054B50` |
| Signing Block | `mov x12,#0x5041; movk #0x204b...` | 常量 |
| MD5 IV | 加载到寄存器（`adr x16,0x6a10`）后再用 | — |

**这就是我 7 次误判"没有签名校验"的根因**：

- 搜 `PK\x05\x06` → 找不到（它是 4 条 `cmp` 指令）
- 搜 `"APK Sig Block 42"` 字符串 → 找不到（`movk` 拼的）
- 搜 SHA-256 常量 → 找不到（它用 MD5）

**我们的弱点**：`sig_check.c` 用魔数常量 `0x06054B50`，`strings` 或
`objdump` 直接就能定位 EOCD 解析逻辑。

---

### 4.4 层 4：代码保护（本质差异最大的地方）

| | Epic | 我们 |
|---|---|---|
| `.text` 磁盘形态 | **明文** | `.ncx` 段密文（44040 B） |
| 加密算法 | 无 | RC4 + HMAC-SHA256 |
| 二级锁箱 | 无 | ✅ `.ncxh`（unlock 本体也被锁） |
| 密钥派生 | 无 | HKDF(master, SHA256(certDER), "nc-so-v1"+pkg) |
| 代码自绑定 | 无 | ✅ `k_stub ^ fold(crc32(.text))` |
| 密钥存储 | 无 | 4×`volatile uint16` 散落 `.data` |
| 换证书重签 | 无影响 | ❌ **直接起不来**（-12） |

**Epic 的 `.text` 是完全可读的**。我能在几小时内逆向出完整签名校验链，
就是因为代码一直是明文。它的防御全在"增加理解成本"，不在"阻止获取"。

**我们的优势是实质性的**：

```
攻击者拿到 libnc.so，不运行、不脱壳，能做什么？
  Epic:  objdump 直接读全部逻辑  ← 我可以，已证明
  我们:  .ncx 是密文，需要先解：碎片→XOR_KEY→k_stub(+crc32(.text))
        →解 .ncxh→解 .ncxhr→master→证书→HKDF→k_so→RC4 解 .ncx
        而且 k_so 依赖运行期从已安装 APK 读证书 —— **没有 APK 就卡在第 4 步**
```

> `流程文档.md` §3.12.9 的结论：「这是『更贵』不是『解不开』。
> 真正不可静态还原的是 P1-a 的运行期证书派生。」

### 4.5 层 5：控制流混淆

| 手法 | Epic | 我们 |
|---|---|---|
| 常量拆分 | ✅ 7715 处 `movk` | ❌ |
| 按位取反组合 | ✅ 1374 处 `orn` | ❌ |
| 状态位反混淆 | ✅ 2 处 `cset`（我前面误判为"平坦化"，实为简单布尔还原） | ❌ |
| 间接调用 | ✅ 768 处 `blr`（JNI 表 + 函数指针） | 仅 JNI 必需 |
| 间接跳转 | ✅ 80 处 `br` | — |
| 指针认证 | ✅ 100 处 `paciasp`（ARMv8.3 PAC） | 需实测 |
| OLLVM 平坦化 | ❌ **没有**（`br` 仅 80 次，`csel` 2 次） | ❌ |
| 反调试 | `getauxval` 伪造位递归自检 | `TracerPid`/`ptrace` |

**修正我之前的判断**：Epic **不是** OLLVM。它用的是**手写常量混淆**：

```
mov w12, #0x883a          ← 拆成 2 条
movk w12, #0xeac0, lsl 16
mov w13, #0xf6bb
movk w13, #0x59e3, lsl 16
mvn w8, w8                ← 取反
orr w8, w8, 0xfffffffe    ← 组合
cmn w8, 1                 ← 判等
cset w8, eq               ← 还原布尔
```

这套手法**强度低于 OLLVM，但对人肉分析足够有效**——我在模拟执行时被它
绊了好几轮（虽然有 `movk` 的地方都是可控的常量运算，理论上可以符号执行）。

### 4.7 层 7：dex2c 转译策略

| | Epic | 我们 |
|---|---|---|
| 抽了几个方法 | **3 个**（`MainActivity.onCreate/onConfigurationChanged/k`） | 全 LAUNCHER 类 |
| 代码体量 | 1924 + 7656 + **25836** B = 35 KB | 328 KB（全模块） |
| 注册方式 | `RegisterNatives` + `.got` 表 | JNI 短名绑定 |
| 是否真被调用 | ❌ **零调用点**（障眼法） | ✅ 真实执行 |

**Epic 的"障眼法"是本次最值得学的设计**：

```
MainActivity.onCreate     声明 native，无实现，**全包零调用点**
MainActivity.<init>       12 字节，转 Lef0.<init>
Lef0.onCreate             43 字节，**真实逻辑还在 dex 里**
```

它让逆向者以为"核心代码进了 so"，去啃 509KB 的库（里面全是 Xposed 检测
和 35KB 的 3 个转译方法），而**业务逻辑就在混淆后的父类 `Lef0` 里**。

我前 7 次判断"没找到转译产物"，根因就是默认了"native 方法必有实现、
必被调用"——它恰好利用了这一点。

### 4.8 层 8：失败处置

| | Epic | 我们 |
|---|---|---|
| 校验失败 | `Log.e("D2CX","SEC-DENY")` + **`pause()` 永久挂起** | 延时杀（三档 seed） |
| 延迟 | 立即 | 1~4s（`killvar` 三档） |
| 崩溃指纹 | SIGSEGV（pause 后栈被破坏） | SIGABRT（`tgkill`） |
| 后台线程 | `pthread_create` 打印 DENY | `delayed_kill_*` detached 线程 |
| 双签名线 | ❌ | ✅ `sig_check.c` + `sig_guard2.c` |

**Epic 的 `pause()` 方案很脆**：它只是挂起主线程，攻击者 `kill -9` 或
跳过该调用即可。**我们的延时杀三档**（seed 不同、崩溃时机不相关）在
"防单点 patch"上更强。

### P1：so 加载三级回退（工作量：改 `artifact-pipeline`，半天）

> 这一项**不在 nox**，在 `artifact-pipeline/scripts/inject/inject-loadlib.py`。

当前只插 `System.loadLibrary("nc")`，失败即崩。Epic 的三级回退：

```java
try { System.loadLibrary("nc"); }
catch (Throwable t) {
    // ② ClassLoader.getResource 反推绝对路径
    try {
        java.net.URL u = NcLoader.class.getClassLoader()
            .getResource("lib/" + abi() + "/libnc.so");
        if (u != null) { System.load(u.getPath().substring(5)); }
        else throw t;
    } catch (Throwable t2) {
        // ③ java.library.path 逐个试
        String lp = System.getProperty("java.library.path");
        if (lp == null) throw t2;
        for (String d : lp.split(":")) {
            try { System.load(d + "/libnc.so"); return; } catch (Throwable t3) {}
        }
        throw t2;
    }
}
```

**收益**：`extractNativeLibs` 行为差异、多 ABI 目录异常等场景不直接崩。

**风险**：⚠️ 可能弱化"承重墙" —— 当前设计是"so 缺失必须死不能静默"。
如果回退成功反而让攻击者更容易绕过，需权衡。**建议先讨论再动手。**

## 6. 我们做得更好的地方（别改坏了）

> 这些是**加密派路线**的核心资产。任何"简化/重构"都会直接削弱它们，
> 因为这些能力不是代码量堆出来的，是**设计取舍**换来的。

### 6.1 代码保护（Epic 完全没有）

| 项 | 我们的实现 | 为什么 Epic 做不到 |
|---|---|---|
| **段加密** | 6 段（`.ncx`/`.ncxr`/`.ncxh`/`.ncxhr`/`.nck`/`.ncks`）RC4+HMAC | Epic 的 `.text` 是明文，没有"可加密的容器" |
| **二级锁箱** | `.ncxh` 装 unlock 本体，自己也被加密 | Epic 的"开锁器"就是 `.text` 里普通函数 |
| **运行期证书派生** | `k_so = HKDF(master, SHA256(certDER), "nc-so-v1"+pkg)`，**磁盘无钥** | Epic 的 MD5 期望值明文躺在 `.rodata` |
| **代码自绑定** | `cipher_key = k_stub ^ fold(crc32(.text))`，**改码即自毁** | Epic 打补丁后照常运行（我改 9 字节就跑起来了） |
| **密钥碎片化** | 4×`volatile uint16` 散落 `.data`，`ncg_xor_key()` 现算不缓存 | Epic 无密钥概念 |

**6.2 节的对比最值得记住的一条**：

> 我改 Epic 的 so 只用 **9 字节**（3 处），装上去就跑起来了。
> 如果改我们的 `libnc.so`，`.text` 一变 `crc32` 就变 → `k_stub` 错 →
> `.ncxh` 解不开 → 解锁失败 → **直接起不来**。

这就是"加密派"的核心价值：**补丁成本不是"找到位置"，而是"重算整条密钥链"**。

### 6.2 字符串保护

| | 我们 | Epic |
|---|---|---|
| 算法 | `SHA256(key ‖ msg_id ‖ counter)` | `cipher[i] ^ (i+1)` |
| 密钥 | `os.urandom(32)` 每构建随机 | **无密钥**（固定模式）|
| 已知明文 | 拥有者才可解 | **3 条已知明文 → 全表破解** |
| 相同前缀 | 密文不同 | 密文前缀相同 |
| 跨包 diff | 失效（每包不同） | 有效（同版本同样式）|

我破 Epic 的字符串**用了不到 1 分钟**——拿到 `java/lang/Boolean`、
`<init>`、`valueOf` 三条明文，逐字节异或就得出密钥 `01 02 03 ...`，
然后一次性解开 8550 个候选串。

### 6.3 签名校验的双线设计

| | 我们 | Epic |
|---|---|---|
| 第一线 | `sig_check.c`：maps 定位 + 独立解析 + 延时杀 | 一条（`0x2d85c`）|
| 第二线 | `sig_guard2.c`：**独立派生**（`sig_guard2.h`）+ **独立处置**（`syscall(tgkill)` + watchdog），与第一线**零代码共享** | 无 |
| 打掉第一线的后果 | 第二线照常判定 | — |

Epic 只有一条链：patch 掉 `0x2d85c` 或者 `0x2deec` 就够了。

### 6.4 失败处置的分散度

| | 我们 | Epic |
|---|---|---|
| 汇聚点 | **3 个独立函数体** `delayed_kill_0/1/2`，seed 各异（`^0x51` / `*7^0xA3` / `*13^0x7C`）| **1 个** `pause()` |
| 延迟 | 1~4s，崩溃时机互不相关 | 0（立即挂起）|
| 崩溃指纹 | SIGABRT（`tgkill` 直投 `svc`，不经 PLT）| SIGSEGV（`pause` 后栈被破坏的副作用）|
| 单点 patch | ❌ 需要改 3 处 | ✅ **改 1 处即可** |

> `流程文档.md` §3.12.11 的原则："必须是三个独立函数体，不能参数化——
> 共用函数 = 一处 patch 全废。"

我在 Epic 上验证了这条原则：`0x2deec` 一个点被打掉，整个签名校验就失效了。

### 6.5 心跳保活

| | 我们 | Epic |
|---|---|---|
| 机制 | Java 层 `heartbeat()` 喂食 → `env_watchdog` 检测 | 无 |
| 参数 | 90s 宽限 + 8s 保活 + 5s 轮询 | — |
| 防什么 | 攻击者删掉 Java 层校验调用 → so 层发现"没喂食" → 杀 | — |

这是"Java 层与 so 层双向绑定"的机制，Epic 完全没有这一维。

## 8. 本次逆向的方法论总结

### 8.1 有效的手段

1. **用已知明文反推加密算法** —— 比模拟执行快 100 倍
2. **搜 `pause`/`exit`/`abort` 调用点** —— 直接定位 fail-closed 处置
3. **搜系统路径字符串**（`/proc/self/maps`、`base.apk`）—— 定位文件读取逻辑
4. **搜哈希初始常量**（MD5 IV `0x67452301`、SHA256 `0x6a11e667`）—— 定位哈希实现
5. **逐字节 A/B 验证补丁** —— 静态推演不可靠，必须真机验证
6. **看崩溃栈** —— `#00/#01/#02` 三层就够定位

### 8.2 无效/低效的手段

1. **纯字符串搜索找 `signature`/`PackageManager`** —— so 层校验根本不碰 Java API
2. **用 unicorn 硬模拟含 mutex/分配器的函数** —— 状态难以构造，容易误判
3. **只读代码不验证** —— 我对 `csinv` 的方向判断错了 3 次

### 8.3 最重要的教训

> **“静态找不到” ≠ “不存在”。**
>
> 本次我 7 次错误判断“没有签名校验”，根因都是**用错了搜索维度**：
> - 找 Java API 字符串（它用 C）
> - 找 ZIP 魔数常量（它逐字节比较）
> - 找 SHA-256（它用 MD5）
>
> 正确做法：**先确定“这个功能应该有什么行为特征”，再按特征反推实现形式**，
> 而不是按自己熟悉的实现去套。
