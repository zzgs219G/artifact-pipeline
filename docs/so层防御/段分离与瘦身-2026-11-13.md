## 2. 体积瘦身（已上线，净收益最大的一项）

### 2.1 做了什么

**① 顶掉 libc++abi 的 demangler**

新增 `scripts/guard/src/nc_demangle_stub.c`，用同名强符号覆盖 `__cxa_demangle`。

因果链（照抄 dpt-shell 2026-11-10 的结论）：

```
APP_STL := c++_static
  → libc++abi.a 的 cxa_default_handlers.cpp.o（导出 __cxa_terminate_handler）
  → 它引用 __cxa_demangle
  → cxa_demangle.cpp.o（606 个符号，.text 里近 100KB）整块被拉进 so
```

**② 关异常/RTTI**

`lib-ndk.sh` 的 `APP_CPPFLAGS` 加 `-fno-exceptions -fno-rtti -fno-unwind-tables`。

### 2.2 效果

```
libnc.so:  662,712 → 528,536 B   (-166KB, -25%)
APK:       6,235,479 → 5,263,547 B  (-972KB)
  .text     307,964 → 207,788      (-100,176)
  .rela.dyn  33,312 →  4,320       (-28,992)   ← RTTI/异常表
  .data.rel.ro 12,104 → 1,240      (-10,864)   ← vtable
```

### 2.3 ⚠️ 试过但**失败**的：`APP_STL := c++_shared`

`libnc.so` 确实降到 454,328 B（-42KB），**但 NDK 会把 `libc++_shared.so`
整个复制进 APK 的 `lib/<abi>/`（1,794,776 B = 1.7MB）**。

净效果：APK 反而大 1.75MB。**已回滚，并在 `lib-ndk.sh` 注释里记下实测数据防止重试。**

### 2.4 代价（如实）

- 崩溃提示从 `std::bad_alloc` 变成 `St9bad_alloc`（只影响开发者可读性）
- libnc.so 内不能再写 `try/catch` / `typeid().name()`
  （现在没有：sig_check/env_check/nc_link 全是 C；dex2c 用 `EX_LandingPad` +
  显式 `goto` 分发，不依赖 `.eh_frame`）
- **⚠️ 将来若加 try/catch，必须删掉 stub 文件和那两个 flag**

## 4. 段分离：做到了什么、卡在哪

### 4.1 目标

用户想要：**一眼看出 VMP 数据在哪、有多大**，进而对它做锁箱加密。

### 4.2 已经做到的（nox12/nox13 真机验证）

**`.ncr` 段成功分离，`readelf` 可见：**

```
[29] .ncr  PROGBITS  ...  146,904 B  WA
```

**一个命令就看到 VMP 数据在哪、多大。**

### 4.3 加密失败的真因（这次找到了）

**关键实测：`.ncr` 里有 83 个 `R_AARCH64_RELATIVE` 重定位，全部集中在
`0xc350 ~ 0x23548`（descriptor_table + native_call_table 区间），几乎每 8
字节一个。**

```
offset  0xc350, 0xc358, 0xc360, ... （80 个间隔都是 8）
```

**这些位置在文件里是占位符，`dlopen` 时由动态链接器填入真实地址。**

**如果整段加密，解锁时把解密结果写回 → 覆盖掉链接器填好的指针 → 垃圾指针
→ 解释器跳错地址 → 真机 SIGILL。**

这就是"加密就崩、不加密不崩"的机制。

### 4.4 之前的误判（记下来防止重犯）

| 我的判断 | 实际 |
|---|---|
| "段名 `.ncr` 导致崩溃" | 部分对：nox9 崩是因为它加密了（含指针），不是段名 |
| "删掉 set_section 才正常" | **错**：nox10 那次构建实际用的是 nox9 的 bundle（CI 缓存/URL 没换），结论无效 |
| "Amice 的 set_section 有缺陷" | 不成立：nox12 用 set_section 且真机能跑 |

### 4.5 `.ncr` 内部结构（供后续加密参考）

```
0x00000 ~ 0xc350    字节码 + const_pool + metadata   ← 纯数据，可加密
0xc350 ~ 0x23548    descriptor_table + native_table  ← 含 83 个指针，不能加密
0x23548 ~ 0x23dd8   尾部
```

## 5. nox14 拆两类段 + `.nct` 加密（2026-11-13 当天续做）

### 5.1 思路（已实现）

按「是否含指针」把 5 类 global 拆成两类段：

| 段 | 装什么 | 实测属性 | 可加密 |
|---|---|---|---|
| `.ncr` | 字节码 / const_pool / metadata | `WA` | ✅ |
| `.ncd` | descriptor_table / native_call_table | `WA` | ❌ 必须明文（含重定位） |

### 5.2 段名不再硬编码（用户提出的质疑，已改）

```bash
AMICE_VM_DATA_SECTION=".ncr"   # 纯数据段，默认 .ncr
AMICE_VM_PTR_SECTION=".ncd"    # 指针段，默认 .ncd
```

值非法（非 `.` 开头）时回退默认并告警。

### 5.3 实测：拆段生效（nox14 首轮）

```
段          nox13        nox14        变化
.rodata     260,380      131,260      −129,120
.ncr        146,904      275,448      +128,544
.ncd        —            1,120        新增
```

`.rodata` 少掉的 12.9 万正好等于 `.ncr` 多出的 12.9 万 —— 消费方的
VMP 数据这次真的搬出来了。

**`.ncr` 内部分层（由重定位分布反推）**：

```
[0x00000, 0x1F620)  128,544 B  消费方纯数据      重定位 0 个   ← 可加密
[0x1F620, 0x433F8)  146,904 B  libnox.a 旧数据   重定位 83 个  ← 不可加密
.ncd                    1,120 B 消费方指针表      重定位 68 个  ← 不可加密
```

**但只拆了一半**：`tools/nox.zip` 里的 `libnox.a` 是 11-12 用旧 amice
编的，它的数据还整坨混在 `.ncr` 里、含 83 个重定位。要让 `.ncr` 里
只剩第一套纯数据（明文，符合循环依赖），必须用 nox14 重新编 `libnox.a`。

### 5.4 `.nct` 加密方案（nox 侧已实现，待真机验证）

消费方编译时把 `AMICE_VM_DATA_SECTION` 覆盖成 `.nct`，于是：

| 段 | 内容 | 状态 |
|---|---|---|
| `.ncr` | 第一套纯数据（libnox.a） | 明文（循环依赖，无解） |
| `.ncd` | 两套指针表 | 明文（含重定位，必须） |
| **`.nct`** | **第二套纯数据（sigcheck）** | **密文** |

**nox 侧改动**（commit `fad6ebc`，v0.9.31-nct）：

1. `nc_guard_layout.h` 新增 `NC_SEC_VMP`/`NC_SEC_VMP2`/`NC_SEC_VMPPTR`
2. `nc_guard_key.c/.h` 新增 `ncg_derive_k_nct[from_der]`，label `"nc-insn-v1"`，
   第 5 张 label 密文表（生成脚本产出）
3. `nc_guard_boot.c` `segs[]` 2 段 → 3 段，**`.nct` 排最前**
4. `so-section-lock.py` `_SEG_KEYS` 从「按位置下标」改为「按段名映射」
5. `test.sh` 新增 V11（5 项）

### 5.5 为什么 `.nct` 必须最先解密

`.ncx` 里的函数带 VMP wrapper，wrapper 第一条就 `bl` 到解释器、读
`.nct` 里的字节码。若 `.nct` 仍是密文 → 解释器把密文当 opcode →
跳无效地址 → 真机 SIGILL（2026-11-12 实测，崩溃点
`libnc.so+0x82598`，落在 `.ncx` 段内，**完全不指向 `.nct`**）。

而 `k_nct` 只需 master（来自 `.ncxhr`，二级锁箱已解），与 `.ncx`
无依赖 → 先解不构成循环依赖。

### 5.6 段序必须动态（`.nct` 是可选段）

```
有 .nct： 0=.nct(k_nct)  1=.ncx(k_so)  2=.ncxr(k_so_r)
无 .nct： 0=.ncx(k_so)   1=.ncxr(k_so_r)
```

曾写死「0→k_nct / 1→k_so / 2→k_so_r」，无 `.nct` 时把 k_nct 用在
`.ncx` 上 → 解出乱码 → V6 报「正常包也会挂」。

现 `has_nct` 标志传入 `ncg_decrypt_one_seg`，索引动态算；Python 侧
同步改为按段名映射（`_KEY_BY_NAME`），与位置无关。

### 5.7 加密收益（如实，别高估）

**能隐藏**：VM 字节码本身 —— 攻击者要理解 VM 语义，得先解这 12.8 万字节。

**不能隐藏**：
- 有多少函数被 VMP（`.ncd` 里的 descriptor 表数量）
- 每个 handler 的地址（`.ncd` 是明文指针表）
- 段名、段尺寸（`readelf -S` 一眼看到 `.nct` 有多大）

**上限不变**：`k_nct` 由 master 派生，攻击者过了解锁链就能自己解
`.nct`。它防的是「拿到 APK 直接搜字节码」这类低成本逆向，**不防会跑
代码的对手**。与 `.ncx` 加密同一档次，不更高。


### 6.2 段名抽取的正则要允许数字

`so-section-lock.py` 的 `_load_layout_contract()` 用
`#define\s+(NC_SEC_[A-Z_]+)` 抽段名 —— **匹配不到 `NC_SEC_VMP2`（带数字 2）**。

症状：`_LAYOUT` 缺键 → `lock()` 抛 `KeyError` → 一级锁箱整体失败。

已改为 `[A-Z0-9_]+`。

### 6.3 可选段的段序必须动态决定

`.nct` 是可选段（没开第二套 VMP 的产物没有它）。写死段序会导致：

```
有 .nct： 0=.nct  1=.ncx   2=.ncxr
无 .nct： 0=.ncx  1=.ncxr           ← 写死索引时把 k_nct 用在 .ncx 上
```

症状：解出乱码 → `test.sh` 的 V6 报"正常包也会挂"。

修法：引入 `has_nct` 标志，`kso_idx`/`ksor_idx` 动态计算。

### 6.4 跨语言 label 长度必须对齐

`NCGL_INSN` 曾写成 11，而 `"nc-insn-v1"` 实际长度是 **10**。

C 侧按 11 读表 → 还原出 `"nc-insn-v1\x??"` → HKDF info 错 → `k_nct` 错。

**已加 `_Static_assert(sizeof("nc-insn-v1") - 1 == NCGL_INSN, ...)` 钉死。**

**教训：Python 侧能解只证明文件加密正确，不证明 C 侧能解。两边要分别验。**

现已固化成 `scripts/so-guard/test-k-nct-parity.py`（V11a 调用）：编译一个只
link `nc_guard_key.c` 的小程序，把 C 侧算出的 `k_nct` 与 Python 侧
`derive_app_keys()['insn']` 对拍。

**反向验证做过两次**（AGENTS §3.2 要求）：
- 把 `NCGL_INSN` 改回 11 → `_Static_assert` 编译期就红
- 把 label 改成 `nc-insn-v2` → 三组对拍全红

### 6.5 `git push | tail -1` 的退出码是 `tail` 的，永远 0

```bash
git push origin main 2>&1 | tail -1 && echo PUSH_OK   # ← 假成功，永远打印
```

**这次真的被坑了**：连续几轮 push 都打印 `PUSH_OK`，但远程 HEAD 一直停在
旧 commit。于是：
- 改了 `protect-modules.yml` 的 bundle 版本 → CI 用的还是旧的
- 构建出来的产物没有 `.ncd` → 我据此判断「拆段没生效」

**这与 §6.1 的漏改 URL 是同一类错误的两个变体：都让「我以为测的是 A，
实际测的是 B」。**

正确写法：

```bash
git push origin main > "$LOG" 2>&1
rc=$?
[ $rc -eq 0 ] || { tail -2 "$LOG"; }
# 并且校验远程真的变了：
git ls-remote origin main | head -1
git rev-parse HEAD
```

**注意 `/tmp` 在 Termux 上不可写**（Permission denied），日志放 `$HOME`。

### 6.6 熵值断言必须先确认明文熵够低

`test.sh` 的 V11c 验「`.nct` 加密后熵 > 6.0」。第一版样本用的是 64 个
**互不相同**的字节 —— 明文熵已经是 `log2(64) = 6.0`，密文再压也压不出
差距，断言变成恒假。

现改为 240 字节 `0x00` + 16 字节标记，并**新增 V11e 反向验证**：
未加密的 `.nct` 熵必须 < 3.0。实测明文 0.572 / 密文 7.151，判据有区分度。

这与 AGENTS §3.2 记的「恒真断言」是同一类错误。
