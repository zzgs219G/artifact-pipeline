## 0. 触发原因（为什么现在必须改）

2026-10-28 有一份**独立第三方逆向**（未读源码，纯静态 + unicorn 模拟），**28 分钟**产出报告。
其成本分解（对方实测，文件系统时间戳）：

```
定位（拿到结构认知）        16 分 20 秒
  ├ rabin2 -S 看段表         ~0 秒    ← 本项目最大失分项
  ├ 导出符号 vaddr 归属       ~0 秒
  ├ .init_array 重定位        ~1 分
  ├ .rodata 常数指纹(SHA256)  ~0 秒    ← 10 秒识别出 SHA-256
  └ 跨段 xref 找解密器        ~15 分   ← 唯一真正花时间的
解密（拿到 .ncxh 明文）       2 分 02 秒
```

对方的结论（维护者接受）：

> **壳的有效防御成本 ≈ 0。我的 28 分钟里，壳贡献的阻力不到 5 分钟。**

**根因判断（维护者）：不是"解密难算"，是"定位零成本"。**
因此本轮目标不是加密码学强度，而是**让定位变贵**。

### 0.1 对方的成果与未竟（用于校准强度）

| 项 | 状态 | 证据 |
|---|---|---|
| 段布局、非标准 flags | ✅ 全摸清 | `rabin2 -S` 一条命令 |
| `.init_array` 6 项、解密器 `0x1b780` | ✅ 全摸清 | 扫 `.rela.dyn` RELATIVE |
| SHA-256/HMAC 位置 | ✅ 全摸清 | `.rodata` 常数指纹 |
| `key8` 派生规则 | ✅ **正确复现** `7e31a50dc8924bf6` | 维护者核实一致 |
| `.ncxh` 解密 | ✅ **成功**，3100 B，775 条合法指令 | 维护者核实首 4 字节 `ffc304d1` 正确 |
| **`.ncx` 解密** | ❌ **未成功** | 其 `ncx_*.bin` 文件首字节 `564ec510`，非明文 |
| 卡点 | `__open_2` GOT 被运行时改写，模拟器桩语义不符 | 非设计防御，属构建副产物 |

**结论：`.ncxh`（引导层）已失守，`.ncx`（业务代码）未失守。**

## 1. 本轮目标与不做的

### 1.1 目标（可量化）

| 指标 | 现状 | 目标 |
|---|---|---|
| 定位到"这是自研壳" | ~0 秒 | **数分钟**（需反汇编才知） |
| 定位到解密器 | ~15 分（xref） | **1 小时+** |
| `.ncxh` 解密 | 2 分 02 秒 | **30 分钟+** |
| 定位到 SHA-256 | ~10 秒 | **5 分钟+** |

**不追求"解不开"**（自解谜悖论：程序自己启动所需的全部材料必在文件里）。

### 1.2 明确不做

| 方案 | 拒绝理由 |
|---|---|
| **剥离 section header** | ❌ **实测不可行**：Android bionic linker 强制校验 `e_shentsize` / `e_shstrndx`，清零即 `DLOPEN_FAIL`（见 §2.1） |
| 服务端下发密钥 | 用户明确拒绝（破坏离线可用） |
| 设备指纹绑定 | 换机即失效，不可接受 |
| 纯 VMP / 控制流平坦化 | 与 dex2c 产物冲突，体积爆炸 |

## 2. 实测先行的可行性验证（已完成）

> 原则：**先证明方案在本平台可行，再动生产代码。** 以下均为 Termux aarch64 实测。

### 2.1 剥离 section header —— 不可行（否决对方建议）

| 变体 | 结果 |
|---|---|
| `e_shentsize=0`（全清零） | `unsupported e_shentsize: 0x0 (expected 0x40)` → DLOPEN_FAIL |
| `shoff=0, shnum=0, shstrndx=0`（保留 shentsize） | `invalid e_shstrndx` → DLOPEN_FAIL |
| `shnum=1, shstrndx=0` | `invalid e_shstrndx` → DLOPEN_FAIL |

**结论：Android linker 要求段表完整。该建议在桌面 Linux 成立，在 Android 不成立。**
→ 采用替代方案 **A：段名清空**（保留段表结构，只让名字失去信息）。

### 2.2 段名清空 —— 可行

把 `shstrtab` 全清零后：

```
改前 rabin2 -S:
  .ncxr  .ncx  .ncxh  .ncxhr  .ncks  .nck       ← 一眼看出家族关系

改后 rabin2 -S:
  [1] NOTE      [2] DYNSYM   [3] GNU_VERSYM
  [4] GNU_VERNEED ...
  33 个段，名称为空 / _1 / _2 / _3                ← 只剩 type/flags/size 可看
```

**后果（必须配套改造）**：`ncg_find_section()` 按名字查找会失败 → `selftest` 无法解锁。
→ 必须同步实施 **B：改按固定偏移定位**。

## 4. 任务 A：段名清空 + 按偏移定位

### 4.1 目的

让 `rabin2 -S` / `readelf -S` 从"一张免费地图"变成"33 个无名段的清单"。
攻击者必须反汇编 `find_section` 的替代实现，才能知道哪个段是加密体。

### 4.2 改什么

#### A-1 常量侧（`nc_guard_layout.h`）

段名常量**保留**（内部索引用），但新增**偏移契约**：

```c
/* 段定位改用固定偏移（2026-10-28）。
 * 为什么不用段名：段名已清空（见 so-section-lock.py 的 strip_section_names），
 * 按名字查找会全部失败。偏移在锁箱期由 so-section-lock.py 写入并校验，
 * 运行期读 .ncks 头部的 offset 表 —— 这样即使段表被重排也能对上。 */
#define NC_OFF_SEC_MAX      8       /* 最多支持的段数 */
/* 偏移表存在 .ncks 头部 [0:8)？——不可行，[0:8) 是 magic。
 * 改放 .ncks[16:24)？——[16:24) 是 wrapped_k_stub 的一部分。
 * 结论：新增独立段承载偏移表，或用 .nck 的 reserved 区。
 * ⚠️ 待 A-1 详细设计确认（见 §4.4 未决问题） */
```

> ⚠️ **A-1 存在未决设计问题**，见 §4.4。这是本任务的最大风险点。

#### A-2 运行期（`nc_guard_boot.c`）

`ncg_find_section()` 从"遍历段表比对 `strcmp(name)`"改为"读段表第 N 项"。

关键：段表**索引**必须稳定。锁箱期按索引写，运行期按索引读。

```c
/* ncg_find_section_by_index(fd, idx, out) —— 替代按名查找 */
static int ncg_section_by_index(int fd, int idx, Elf64_Shdr *out) {
    /* 读 ehdr → 校验 e_shoff/e_shnum → pread 第 idx 项 */
    /* idx 由锁箱期写入 .ncks 的偏移表提供，不写死 */
}
```

#### A-3 构建期（`so-section-lock.py`）

1. 锁箱完成后，把各关键段的**段表索引**写入 `.ncks` 的偏移表区
2. 最后一步执行 `shstrtab` 清零（**必须在锁箱之后**，否则锁箱侧也找不到段）

```python
def strip_section_names(elf: 'Elf') -> None:
    """把 shstrtab 全清零 → 所有段名为空。

    ⚠️ 必须在【所有锁箱动作完成后】执行：
    lock() / lock_head() 都依赖按名查找段，先清名会直接失败。
    ⚠️ 不能清 e_shentsize/e_shstrndx：Android linker 会拒载（实测见 §2.1）。
    ⚠️ e_shstrndx 必须仍指向一个【存在且可读】的段，哪怕内容是全零。
    """
```

### 4.3 验证

| 项 | 方法 |
|---|---|
| 段名确已清空 | `rabin2 -S new.so` 中 `.ncx`/`.ncks`/`.nck` 零命中 |
| so 仍可加载 | `dlopen` 成功，无 `unsupported e_shentsize` |
| 解锁仍工作 | `selftest == 59` |
| 真机 | **必须**验证（本地 linker 与真机不同，历史报错五十已踩过） |
| 回归 | `test-so-lock.sh` T2/T3/T20/T21/T22 全绿（需先改断言，从按名改按索引） |

### 4.4 未决问题（必须在动手前定）

**问题：段偏移/索引表存哪里？**

约束：
- `.ncks` 已满（112 B，8 个字段全占用，无空闲区）
- `.nck` 已满（96 B，[88:96) 是 reserved 8 B，只够放 2 个 u32）
- 扩尺寸会触发契约迁移（历史上 80→96→104→112 每次都有同步风险）
- 写进 `.text` 会被 CRC 自绑定算进去（改一次全局变）

**候选方案：**

| 方案 | 优点 | 缺点 |
|---|---|---|
| ① 扩 `.ncks` 到 128 B，新增 [112:128) 存 8 个 u16 索引 | 语义清晰 | 又一次尺寸迁移，`_Static_assert`/blob 断言/Python 抽取全要改 |
| ② 复用 `.nck[88:96)`（8 B）存 4 个 u16 | 零尺寸变更 | 只够 4 段，且 `.nck` 语义变混 |
| ③ 硬编码在 C 代码里（`#define NC_IDX_CODE 18`） | 零成本、不可被改 | **但锁箱期若段顺序变化就错**；需锁箱期校验并 fail-fast |
| ④ 用段表自身**顺序**（如"从后往前第 3 个 PROGBITS+AXR"） | 无名也能定位 | 依赖链接器行为，脆弱 |

**维护者倾向：③ + 锁箱期校验。**
理由：索引在链接期确定后只要不改链接脚本就稳定；锁箱期若发现实际索引与硬编码不符 → **直接 fail-fast**，不会静默出错。零尺寸变更、零契约迁移。

**代价**：若未来改动链接脚本/段顺序，需同步改 `nc_guard_layout.h` 的索引常量。已有 `test-so-lock.sh` T21（段名/常量登记检测）可作为防线扩展。

> **需用户确认采用 ③**，或指定其它方案。

### 4.5 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 段索引在不同 NDK 版本下漂移 | **高** | 锁箱期校验 + fail-fast；CI 加断言 |
| 真机 linker 拒绝空名段表 | 中 | 必须真机验证；Termux 已验证可加载 |
| `protect.sh` / `make-sig-hash.sh` 的段名探测失效 | 高 | 同步改为按索引；这是必改项 |
| 历史产物不兼容 | 中 | 用户已确认无历史包袱 |

## 5. 任务 B：消除明文 `adr` xref

### 5.1 目的

对方 `RETROSPECTIVE.md` §5 实测：

> 第二件事：让"跨段 xref"失效——加密段不要有固定的 vaddr 引用点，
> 改用运行时计算基址（现有 `adr x19, 0x118bc` 是明文立即数，一次 xref 就命中）。

实测确认：`0x1b7c4` 处 `adr x19, .ncks`（`0x118bc`），`0x1b87c` 处同样。
**攻击者用"谁引用了加密段 vaddr"一条查询就能定位解密器。**

### 5.2 改什么

把 `.ncks` / `.nck` / `.ncxh` 的地址改为运行期计算：

```c
/* 现在（明文立即数，一次 xref 命中） */
const volatile unsigned char *slot = ncg_stub_slot;   /* adr x19, 0x118bc */

/* 改为（运行期算，无立即数可 xref） */
void *base; char path[512];
ncg_resolve_self(&base, path, sizeof(path));          /* dladdr */
const volatile unsigned char *slot =
    (const volatile unsigned char *)base + ncg_off_ncks();  /* 偏移运行期算 */
```

`ncg_off_ncks()` 从 `.ncks` 索引表 + 段表动态读，或由 `dladdr` 基址 + 硬编码偏移。

⚠️ **约束**：`ncg_resolve_self` 用 `dladdr`（libc），当前纪律是"stub 只能调 `.text` 里的函数"。`dladdr` 在 `.text` 链路上可用（`ncg_head_unlock` 已在用），但 **stub 里不能引入新的 libc 依赖**。
→ 需要在 stub 里用 `&自身符号 - 链接期地址` 的 PC 相对技巧（现有 `ncg_stub_recover` 已用此手法求 base）。

### 5.3 验证

| 项 | 方法 |
|---|---|
| 立即数 xref 消失 | `rabin2 -A` / `r2 /r 0x118bc` 命中数 = 0 |
| `selftest == 59` | 端到端 |
| 真机冷启动正常 | 必须 |

## 6. 任务 C：SHA IV/K 表运行期还原

### 6.1 目的

对方 10 秒识别 SHA-256：

```
0xe640 / 0xe650 → IV（逆序存储）
0xe660 → K 表
```

只要常数裸放，识别成本恒为 0，且一旦识别，`0x1c0f0/0x1c168/0x1c338/0x1c4d0` 四个函数**不需要读**。

### 6.2 改什么

常数在 `.rodata` 存**变换后形态**，首次使用前还原到 `.bss`：

```c
/* 构建期：K'[i] = K[i] ^ MASK[i % 16]，MASK 由构建期随机生成写入 .ncks */
/* 运行期：首次调用前 K[i] = K'[i] ^ MASK[i % 16]，还原到 .bss 后清零 K' */
```

**注意**：`.bss` 里的还原结果可被 dump。但静态分析者看到的 `.rodata` 无标准常数。
`nc_guard_key.c` 有多份 SHA-256 实现（`nc_guard_key.c` / `sig_check.c` / `sig_guard2.c`），**都要改**。

### 6.3 验证

| 项 | 方法 |
|---|---|
| K 表魔数零命中 | `python3 -c "d=open('so','rb').read(); print(d.count(bytes.fromhex('428a2f98')))"` = 0（注意小端 `98 2f 8a 42`） |
| IV 零命中 | 同上，搜 `6a09e667` 小端 |
| SHA-256 正确性 | 必须跑 NIST 向量（"abc" → `ba7816bf...`），否则会静默算错 → 所有产物解不开 |

### 6.4 风险

**中高。** 密码学常数改错 → 静默产出错误 hash → MAC 永不匹配 → 所有包打不开。
缓解：**先跑 NIST 向量再合入**，且保留原实现作为 fallback 开关。

## 7. 任务 D：加密 `.ncks` / `.nck`（原 T4）

### 7.1 目的

把"读数据"变成"读算法"。根因见第一轮报告 §三：**明文槽是 16 分钟摸清结构的真因**。

### 7.2 设计（沿用第一轮方案，含修正）

```
boot_key = HKDF-SHA256(
    ikm  = CRC32(.text 按 4KB 分段, 全部段的 CRC 大端拼接),
    salt = NC_SEED_BOOT,
    info = "nc-boot-v1",
    len  = 16
)
.ncks[0:112] = 流密码(boot_key, 原 112 字节)
.nck[0:96]   = 流密码(boot_key, 原 96 字节)
```

**零尺寸变更**（加密是 size-preserving），`_Static_assert` 全不动。

**实测已完成的验证**（第一轮原型）：
- 全段抽样篡改 15 处，boot_key 全部变化，盲区 0
- 锁箱侧/解密侧两次独立派生一致
- `.text` 内重定位数 = 0（文件内容 == 内存内容，前提成立）

### 7.3 风险

| 风险 | 说明 |
|---|---|
| `boot_key` 依赖 `.text` 内容 | 与现有 CRC 自绑定**同一前提**，已验证；不引入新风险 |
| 段索引硬编码（若 A 采用方案③） | A 与 D 的索引来源要统一 |
| 攻击者仍可反汇编复现 | **如实说明**：这是"提高成本"不是"不可解" |
