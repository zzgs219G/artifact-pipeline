# 模块联动关系全景（2026-11-02 建立，2026-11-05 补联动⑥）

> **给下一个接手的 AI / 人。** 本项目的模块不是独立的——它们之间有 **5 条
> 隐式联动**，全部藏在代码里，光看 schema 完全看不出来；外加一条**横切的
> 第 6 条**（nox 段加密设施，对所有 so 产物生效）。
>
> 我（2026-11-02 接手时）就因为不知道这些，把「`dex2c_stub` 勾了却没生效」
> 误判成 dex2c 的 bug，查了很久。
>
> **读本文前先记住一句话：`dex2c` 有两个身份——「模块」和「接口」。**

---

## 0. 先分清：dex2c 模块 vs dex2c 接口

这是理解所有联动的前提。

| | dex2c **模块** | dex2c **接口** |
|---|---|---|
| **给谁用** | 客户端（用户勾选） | 内部模块（我们自己调） |
| **输入** | 未加固的**原始 APK** | 任意时刻的 APK（含中途改过的） |
| **能抽什么** | 只能抽原始 dex 里**已存在**的类 | 能抽**流水线中途注入**的类 |
| **类名来源** | 用户规则 / 自动抽主类 | 固定目标，不接受用户类名 |
| **执行时机** | STEP2（流水线早期） | 随时，由调用方决定 |

**为什么必须分开**：解密桩不存在于原始 APK（是 stringenc 中途注入的）。
dex2c 模块跑在注入**之前**，看不到它；而模块跑完后已结束，无法再调。
→ 想在中途用转译能力，只能有一个「随时可调」的接口。

代码里：
```bash
WANT_TRANSPILE=$WANT_DEX2C          # 「抽用户指定的类」← 模块身份
WANT_ENGINE=0                        # 「引擎要跑」← 含接口调用
if [[ $WANT_DEX2C -eq 1 || $WANT_DEX2C_STUB -eq 1 ]]; then WANT_ENGINE=1; fi
```

## 1. 五条联动 + 一条横切层，总览

> ⚠️ **严格说还有第 6 条：nox 的 so 段加密设施**。它不是"两个模块之间的联动"，
> 而是**横切的第三层**——只要产物里有 so，`so-section-lock.py` 就会把
> `.ncx`/`.ncxr`/`.ncxh`/`.ncxhr`/`.nck`/`.ncks` 六段加密写回。
> 详见下文「联动⑥」。所以 `libnc.so` 里除了下表这些，还静态链接了
> `libnox.a`（`-Wl,--whole-archive`，上游仓库详见 `上游仓库-nox.md`）。

```
                      ┌─────────────────────────────────┐
                      │  签名校验 sigcheck               │
                      │   · 纯 C（sig_check/env_check）  │
                      │   · 与 dex2c 产物【同编进一个 so】│
                      └────────────┬────────────────────┘
                                   │ 联动①：地基（同 so）
                                   ▼
   ┌───────────────────────────────────────────────────────┐
   │                    libnc.so                            │
   │  sig_check.c + env_check.c + nc_link.c                 │
   │  + dex2c 转译产物(*.cpp) + 解密桩内核（若勾 stub）      │
   │  + nox 的 so 段加密设施（静态库 libnox.a，见联动⑥）     │
   └───────────────────────────────────────────────────────┘
              ▲                              ▲
              │ 联动②：接口                   │ 联动③：密钥搬进壳
              │ （桩内核 → so）               │ （SEED → 壳 JniBridge）
              │                              │
   ┌──────────┴──────────┐        ┌──────────┴──────────┐
   │ 字符串加密 stringenc │        │ 壳 packer (dpt)      │
   │  · 注入解密桩 StrDec │───────▶│  · 桩类搬进壳 dex    │
   │  · 加密 const-string │ 联动④  │  · 提供 JniBridge    │
   └─────────────────────┘（桩搬壳）└──────────────────────┘
                                            │
                                            │ 联动⑤：壳吃 dex2c 产物
                                            ▼
                                    dex2c 转译后的业务 dex
```

## 2. 逐条详解

### 联动①：签名校验 + dex2c —— **同编进一个 so**（"地基"）

**触发**：同时勾 `sigcheck` 与 `dex2c`。

**做什么**：两者的产物**编译进同一个 `libnc.so`**。

```
sig_check.c / env_check.c / nc_link.c   ─┐
dex2c 转译产物 jni/nc/*.cpp              ─┼→ libnc.so
nox 的 so-guard（段加密设施）            ─┘
```

**关键**：**不是「A 调用 B 的接口」**，是「A 和 B 住同一个房子」。

**常见误解**：
> "签名校验不是也调 dex2c 抽了心跳吗？"
> ❌ 不是。心跳（`nc_heartbeat_touch`）是**纯 C 实现**，本来就在 so 里，
> 不经过 dex2c。sigcheck 唯一与 dex2c 的交互是：规则留空时它**提供
> filter 来源**（自动抽 LAUNCHER 主类）：
> ```bash
> elif [[ $WANT_SIGCHECK -eq 1 ]]; then
>     python3 scripts/filter/make-filter-from-apk.py ... → DCC_FILTER
> ```

**代码位置**：`lib-ndk.sh` 的 `ndk_write_mk`（决定编译哪些源文件进同一 so）。

---

### 联动②：字符串加密 → dex2c 接口 —— **桩内核抽进 so**

**触发**：勾 `stringenc` + `stringenc.dex2c_stub`（**不需要**勾 dex2c 模块）。

**做什么**：把解密桩的 4 个方法（`d` / `dn` / `mix64` / `keyByte`）转译进 `libnc.so`，
dex 侧只剩 native 声明 + try/catch 壳。

**为什么需要**：
```
威胁：攻击者 dump 出 StrDec 类，反编译就拿到 splitmix64 + 密钥流算法
对策：算法搬进 so，dex 里只留 native 声明
```

**执行链路**（这是最容易看错的时序）：
```
STEP 2a  前置轮：解包原始 APK → 注入解密桩 → 回编成 pre-encrypted.apk
         ↓ 同时产出 stub_filter.txt（4 条规则，桩名每包随机）
STEP 2b  dex2c 接口：filter = 用户规则 + stub_filter → 转译
         ↓ compiled_methods.txt 里出现桩类条目
STEP 5  主轮：桩在壳 dex 里被改成 native 声明（方法体丢弃）
```

**⚠️ 曾经的坑（2026-10-31 `961d446` → 2026-11-02 修）**：
那次为修「不勾 stub 时桩被无条件 native 化 → ULE」，加了
`_stub_transpiled(compiled_methods)` 判断。但它没注意 **`emit_stub_dex`
跑在前置轮（dex2c 之前）**，那时 `compiled_methods.txt` 还不存在 →
判断恒 False → 桩永远不 native 化。

症状：日志里同时出现两句自相矛盾的话——
```
ℹ️ 桩未被 dex2c 转译 → 保持明文 Java（不 native 化，不需要 libnc.so）
🧹 compiled_methods 剔除桩条目 4 条（桩已进壳 dex，无需 native 化）
```
第一句错、第二句对。**用户勾了「解密桩也抽进 so」，算法进了 so，但壳 dex
里仍留一份明文方法体** —— 看起来就像"没抽"。

修法：新增 `--assume-stub-transpiled`，由 protect.sh 在
`WANT_STRINGENC && WANT_DEX2C_STUB` 时传入。判据从「dex2c 是否已转译完」
（时序上拿不到）改为「本次是否有桩的转译请求」（输入侧确定事实）。

---

### 联动③：字符串加密 → 壳 —— **SEED 搬进壳 so**（自动，无开关）

**触发**：勾 `stringenc` + `packer`（**无独立开关，自动发生**）。

**做什么**：桩的 `SEED` 从「dex 里的字面量」改成「运行期从壳取」：

```java
// 改造前：脱壳者读壳 dex 就拿到密钥
private static final long SEED = 0x1234567890abcdefL;

// 改造后：<clinit> 里调壳的 JNI
private static final long SEED = JniBridge.gseed();
```

**为什么需要**：联动②把算法搬进了 so，但如果 SEED 还留在 dex 里，
脱壳者读壳 dex 就拿到密钥 —— **联动②白做**。

**代码位置**：
- `encrypt-strings.py:1109 _patch_stub_seed_from_shell()`
- 触发条件：`--stub-seed-from-shell`（protect.sh 在 `WANT_PACKER=1` 时传）
- 配套：`--emit-seed "$WORK/stub_seed.txt"` → dpt 打包时吃这个种子

**这就是你说的"字符串加密和壳的独特联动"** —— 它没有 schema 开关，
是 packer 与 stringenc 之间的自动配合。

---

### 联动④：壳 → 字符串加密 —— **桩类搬进壳 dex**

**触发**：勾 `stringenc` + `packer`。

**做什么**：把整个解密桩**类文件**从业务 dex 摘除，改由壳 dex 承载。

```
业务 dex：只剩 invoke-static Lcom/xxx/StrDec;->d(...) 调用点
壳 dex  ：StrDec 类本身（方法体已是 native 声明，见联动②）
```

**为什么**：dpt 加壳会把业务 dex 的方法体抽空/搬进 `xixin_data`。
桩若留在业务 dex，脱壳者 dump 出来就能直接读它的算法与种子。

**代码位置**：
- `protect.sh` 的 `remove-stub`（STEP5，条件 `LINK_STUB && WANT_PACKER`）
- `encrypt-strings.py:1199 emit_stub_dex()`

**⚠️ 只在勾 packer 时搬**：不勾时没有壳 dex 承载桩，搬了 = 运行期 ClassNotFound。

---

### 联动⑤：壳 → dex2c —— **壳吃转译后的业务 dex**

**触发**：勾 `dex2c` + `packer`。

**做什么**：dpt 加壳的对象是**dex2c 已转译完**的业务 dex。

**顺序强制**：`protect.sh` 的固定步骤序
```
sigcheck → dex2c → stringenc → anti-diff → envcheck → packer
                                                        ↑ 必须最后
```

原因：加壳会整体加密 dex，之后任何 dex 改动都失效。

---

### 联动⑥（横切层，不属于"两模块之间"）：nox 段加密设施

**触发**：只要有 so 产物（`--sigcheck` / `--dex2c` / `--envcheck` 任一），
**不是开关，自动发生**。

**做什么**：`protect.sh` STEP5 在 so 编译完、**还没进 APK 之前**，跑三次
`$GUARD_SRC/so-section-lock.py`：

```
① 一级锁箱  .ncx（代码段）+ .ncxr（常量表段）  ← 密钥 HKDF 绑定 APK 证书
② 二级锁箱  --lock-head                        ← 把 unlock 本体锁进 .ncxh
③ 元数据清理 --strip-meta                      ← 删 .eh_frame/.comment/.debug_*
```

**顺序不可调换**：`objcopy` 会重写 ELF，而 `lock`/`lock-head` 已把链接期
`sh_addr` 写进 `.nck`/`.ncks` 槽，任何挪动都会让运行期基址计算全错
（崩溃点落在 `.ncxh` 里的 SIGILL，症状完全不指向 objcopy）。

**为什么它算"联动"**：它是**横切的第三层**——所有模块的 so 产物都吃同一套
锁箱，而设施本体（`nc_guard_*.c` / `so-section-lock.py`）**在上游 nox 仓库**，
不在本仓库。改它 = 改一个会波及全部模块的外部仓库。

**验收**：`test-so-lock.sh`（52 项，读 `../nox` 源码形态）+
产物侧断言 `nox/test.sh` 的 V8（元数据零命中 / 段地址不变 / 幂等）。

详见 `上游仓库-nox.md` 与 `流程文档.md` §3.12 / §3.13。

---

### 联动⑦：C 桩的三段前置（`--stringenc-native` 专属）

**触发**：`stringenc` 勾选 + `stringenc.stub_impl = "c"`（下拉框选「纯 C 桩」，
schema 2026-11-09 前是布尔 flag，旧快照的 `true` 仍被兼容映射）。

C 桩有个 Java 桩没有的顺序死结：

```
C 侧 RegisterNatives 需要【真实桩类名】
  ↓
而桩是 stringenc 在 STEP5 才注入的（桩名每包随机生成）
  ↓
编 so 的 STEP3 拿不到它
```

**解法**：`encrypt-strings.py emit-stub-decl` —— **只算桩名、不注入**。

```
STEP3 前 ① 生成本轮种子          → $WORK/stub_seed_for_decl.txt
        ② emit-stub-decl        → 预算出桩名 → $WORK/cstub_decl.txt
STEP3   ③ 用①②生成 nc_strdec_cfg.h（类名/NKEYS/密钥）
           和 nc_strdec_bind.c（Java_<mangled>_<随机方法名>）
STEP5   ④ encrypt-strings.py --stub-impl native
                             --seed-hex <①> --stub-name <②>
```

**这四处的值必须一致**，任何一处不同 → 类名对不上或密钥对不上 →
运行期 `No implementation found` 或全部静默 fail-closed。

**为什么不把 stringenc 整体提前**：会破坏 STEP2 的 dex2c 顺序
（dex2c 要从 APK 读 dex）。只提前"名字"这一个信息，代价最小。

## 5. 历史教训（写下来防止重踩）

**① 「模块」和「接口」混为一谈，会让合法组合直接报错**
`dex2c_stub` 曾被要求「必须同时勾 dex2c」，理由是"桩要交给 dex2c 转译"——
把模块当成了接口。结果「只勾字符串加密 + 解密桩抽 so」这个合法组合
直接 `exit 1`。

**② 判断时机必须在数据可得之后**
`_stub_transpiled` 靠 `compiled_methods.txt` 判断，但它在文件生成**之前**
就被调用 → 恒 False。**任何"读某个产物来判断"的逻辑，先确认产物此刻已存在。**

**③ 联动是隐式的，schema 看不出来**
`packer + stringenc` → SEED 搬壳（联动③）**没有任何开关**，也不在 schema 里。
只看配置项永远发现不了它。改 packer 或 stringenc 的代码前，
**先 grep `stub_seed_from_shell` / `emit_stub_dex` / `remove-stub`**。

**④ 日志里的两句话可能自相矛盾，且都"看起来合理"**
`桩未被 dex2c 转译` 与 `剔除桩条目 4 条` 同时出现 —— 前者是错的判断，
后者是事实。**当日志出现互相矛盾的陈述时，信"有具体数字"的那句。**
